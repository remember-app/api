# Подъём и запуск

## Требования

- Node.js **≥ 22.18** (TypeScript выполняется движком напрямую, шага сборки нет).
- Docker — для локального Postgres и локального хранилища (MinIO).

## Запуск с чистой машины

```bash
npm install

# 1. Поднять локальный Postgres 16 (localhost:5432) и MinIO (localhost:9000)
docker compose up -d --wait

# 2. Задать окружение
cp .env.example .env

# 3. Накатить миграции
npm run migrate

# 4. Запустить сервер
npm run dev

# 5. Проверить
curl -i http://localhost:3000/health
# HTTP/1.1 200 OK
# content-type: application/json; charset=utf-8
# {"status":"ok"}
```

## `GET /health`

Без авторизации. Контракт зафиксирован между репозиториями — мобильное приложение проверяет
ровно это, поэтому форма ответа не меняется:

```
200 OK
content-type: application/json; charset=utf-8

{"status":"ok"}
```

Тело — ровно `{"status":"ok"}`. Content-type Fastify всегда отдаёт с `; charset=utf-8` и убрать
его без onSend-хука нельзя, поэтому клиент сверяет заголовок **по префиксу**, а не на равенство.

Это liveness-проба: она отвечает `ok`, пока жив процесс, и ничего не говорит о базе. Связь с
Postgres проверяется один раз на старте — сервер не поднимется, если база недоступна.

## Локальный Postgres

`docker-compose.yml` в этом репозитории — **канонная локальная база всего продукта**: на неё
смотрят и `api`, и `montage`. Не поднимайте себе вторую.

```bash
docker compose up -d --wait   # поднять и дождаться готовности
docker compose down           # остановить (данные остаются в volume)
docker compose down -v        # остановить и стереть данные
```

Postgres 16, `localhost:5432`, база / пользователь / пароль — `remember` / `remember` / `remember`,
то есть:

```
DATABASE_URL=postgres://remember:remember@localhost:5432/remember
```

## Локальное хранилище

Тот же `docker-compose.yml` поднимает **MinIO** — это локальная замена боевого хранилища, Google
Cloud Storage. Протокол один и тот же (S3), поэтому код в `src/media/r2.ts` не знает, с кем
говорит: меняются только значения `R2_*` в окружении.

- API хранилища — `http://localhost:9000`, бакет `remember` (заводится сам при первом старте
  контейнера), ключ / секрет — `remember` / `remember-secret`.
- Веб-консоль — `http://localhost:9001`, вход теми же ключами. Через неё видно, что реально
  долетело в бакет.
- Данные лежат в volume `miniodata`; `docker compose down -v` стирает их вместе с базой.

Подписанные ссылки собираются из `R2_ENDPOINT` как есть, и телефон идёт по ним сам. С реального
устройства `localhost` — это оно само, поэтому там нужен IP машины в сети:
`R2_ENDPOINT=http://192.168.1.10:9000`. На симуляторе и эмуляторе `localhost` работает.

## Боевое хранилище — Google Cloud Storage

В бою оригиналы, превью и ролики лежат в Google Cloud Storage. api говорит с ним тем же
S3-протоколом, что и с MinIO, — через совместимый XML API Google, — и переменные те же, со своими
значениями:

```
R2_ENDPOINT=https://storage.googleapis.com
R2_BUCKET=<бакет>
R2_ACCESS_KEY_ID=<HMAC access id>     # вида GOOG1E…
R2_SECRET_ACCESS_KEY=<HMAC secret>
R2_REGION=auto                        # Google принимает в подписи любое значение
```

Имена `R2_*` остались от Cloudflare R2, где хранилище жило раньше; их читает стенд на маке, поэтому
они не переименовываются. Бакет и ключи заводит человек, в коде и в репозитории их нет.

- **Адрес — путём**: ссылки вида `https://storage.googleapis.com/<бакет>/<ключ>`. Google отдаёт и
  этот вид, и бакет в имени хоста; код строит первый.
- **Ключ** — HMAC-пара сервисного аккаунта (Cloud Storage → Settings → Interoperability). Аккаунту
  на бакет нужна роль `roles/storage.objectUser`: в ней и объекты (создать, прочитать, удалить), и
  все права multipart-загрузок. `roles/storage.objectCreator` мало — в ней нет удаления.
- **Класс хранения — Standard.** У классов холоднее есть минимальный срок хранения: удалённое раньше
  него, брошенные куски загрузок в том числе, всё равно оплачивается.

Два свойства бакета надо выставить руками — у R2 было иначе:

1. **Брошенные multipart-загрузки.** R2 сам обрывал их через 7 дней после начала; Google не
   обрывает никогда, а уже отправленные куски хранит и берёт за них деньги. api обрывает загрузку,
   когда удаляют её запись, воркер — через сутки простоя (`sweep_stale_uploads`), но свой трек
   организатора (`music/…`) не подметает никто, как и загрузку, чья запись пропала мимо них. Поэтому
   у бакета правило жизненного цикла — семь дней, как было у R2:

   ```json
   {"lifecycle": {"rule": [
     {"action": {"type": "AbortIncompleteMultipartUpload"}, "condition": {"age": 7}}
   ]}}
   ```

   ```bash
   gcloud storage buckets update gs://<бакет> --lifecycle-file=lifecycle.json
   ```

   Правило начинает действовать в течение суток.
2. **Мягкое удаление.** По умолчанию бакет Google держит удалённый объект ещё 7 дней — невидимым,
   но оплачиваемым. Для api удалённое исчезает сразу (прочитать его нельзя), а байты у Google
   остаются неделю. Нужно ли это, решает человек; выключается так:
   `gcloud storage buckets update --clear-soft-delete gs://<бакет>`.

Чем XML API Google расходится с S3 по каждому обращению api и что с этим сделано — в
`docs/media.md`, «Хранилище: Google Cloud Storage».

### Живой контроль хранилища

`npm run storage:check` проходит по настоящему бакету все обращения api к хранилищу в том порядке,
в каком их проживает файл: начало загрузки → кусок по подписанной ссылке → недостающий кусок по
выданной заново ссылке → завершение (куски нарочно в обратном порядке) → размер → скачивание по
ссылке со сверкой байтов → просроченная ссылка отвечает `403` (на этот ответ телефон просит новые
ссылки) → обрыв незавершённой загрузки и проверка, что кусков она больше не берёт → удаление и
проверка, что объекта нет → повторные обрыв и удаление не считаются ошибкой. Каждый шаг — строка
`ok …`; первый не прошедший — строка `error: <шаг>: <ответ хранилища>` и код выхода `1`.

Пишет только в бакет для проверок и только под `<STORAGE_CHECK_PREFIX>/<id прогона>/` и за собой
убирает — в том числе обрывает свои незавершённые загрузки, даже если шаг упал. Что убрать не
удалось, печатается строкой `left behind under <префикс>/`. На бакет, которым живёт продукт, не
идёт: совпали `STORAGE_CHECK_ENDPOINT` и `STORAGE_CHECK_BUCKET` с `R2_ENDPOINT` и `R2_BUCKET` —
выходит, ничего не тронув. Переменные у него свои, а не `R2_*`, чтобы рабочий бакет из `.env` не
попал в контроль по ошибке:

| Переменная                        | Обязательна | По умолчанию    | Что это                              |
|-----------------------------------|-------------|-----------------|--------------------------------------|
| `STORAGE_CHECK_ENDPOINT`          | да          | —               | `https://storage.googleapis.com`     |
| `STORAGE_CHECK_BUCKET`            | да          | —               | бакет для проверок, не рабочий       |
| `STORAGE_CHECK_ACCESS_KEY_ID`     | да          | —               | HMAC access id с правами на него     |
| `STORAGE_CHECK_SECRET_ACCESS_KEY` | да          | —               | его секрет                           |
| `STORAGE_CHECK_REGION`            | нет         | `auto`          | регион в подписи                     |
| `STORAGE_CHECK_PREFIX`            | нет         | `storage-check` | под каким префиксом писать           |

```bash
STORAGE_CHECK_ENDPOINT=https://storage.googleapis.com \
STORAGE_CHECK_BUCKET=<бакет для проверок> \
STORAGE_CHECK_ACCESS_KEY_ID=<HMAC access id> \
STORAGE_CHECK_SECRET_ACCESS_KEY=<HMAC secret> \
npm run storage:check
```

Льёт один кусок размера `MEDIA_UPLOAD_PART_BYTES` (8 МиБ) и столько же скачивает; три секунды из
прогона — ожидание, пока протухнет ссылка. Процесс, убитый посреди прогона, убрать за собой не
успеет — поэтому бакету для проверок то же правило жизненного цикла, что и рабочему, можно с
`"age": 1`. Тот же порядок шагов гоняет `npm test` на MinIO (`src/media/r2.test.ts`), так что
сам контроль не ломается между прогонами.

## Окружение

Одна обязательная переменная. Сервер и мигратор падают сразу, если её нет. Всё остальное имеет
значение по умолчанию — для загрузки не нужно ничего, кроме `DATABASE_URL`.

| Переменная                         | Обязательна | По умолчанию | Что это                                   |
|------------------------------------|-------------|--------------|-------------------------------------------|
| `DATABASE_URL`                     | да          | —            | строка подключения к Postgres             |
| `PORT`                             | нет         | `3000`       | порт HTTP-сервера                         |
| `NODE_ENV`                         | в бою — да  | —            | `production` запрещает обход почты на `/auth/email/start` при любых других настройках |
| `EMAIL_LOGIN_DEV_BYPASS`           | нет         | —            | `1`/`true` — обход почты для адресов на `test.test`; в бою не задавать |
| `SESSION_TTL_DAYS`                 | нет         | `30`         | срок жизни сессии                         |
| `EMAIL_LOGIN_TTL_MINUTES`          | нет         | `15`         | срок жизни кода входа                     |
| `EMAIL_LOGIN_MAX_ATTEMPTS`         | нет         | `5`          | попыток ввести код, прежде чем он умрёт   |
| `EMAIL_LOGIN_RATE_MAX`             | нет         | `5`          | заявок на вход за окно — на один ящик     |
| `EMAIL_LOGIN_RATE_MAX_PER_IP`      | нет         | `50`         | то же на один IP — грубый заслон          |
| `EMAIL_LOGIN_RATE_WINDOW_MINUTES`  | нет         | `15`         | длина этого окна                          |
| `SMTP_HOST`                        | для входа по email | —     | почтовый сервер, через который уходит письмо с кодом |
| `SMTP_PORT`                        | нет         | `587`, при `SMTP_SECURE=true` — `465` | его порт                  |
| `SMTP_SECURE`                      | нет         | `false`      | `true` — соединение шифруется сразу (порт 465); `false` — шифрование включается после соединения, STARTTLS (порт 587). На порту 465 шифруется сразу при любом значении |

| `MAIL_FROM`                        | для входа по email | —     | адрес отправителя, вида `Remember <…@…>`  |
| `APPLE_CLIENT_ID`                  | нет         | —            | наш client id у Apple — `aud` id-токена   |
| `GOOGLE_CLIENT_ID`                 | нет         | —            | то же у Google                            |
| `EXPO_PUSH_URL`                    | нет         | `https://exp.host/--/api/v2/push/send` | куда уходят пуши; пустая строка — пуши выключены |

| `R2_BUCKET`                        | для загрузки | —           | бакет, куда кладутся оригиналы            |
| `R2_ACCESS_KEY_ID`                 | для загрузки | —           | ключ доступа                              |
| `R2_SECRET_ACCESS_KEY`             | для загрузки | —           | секрет                                    |

| `JOURNAL_RECORD_RESPONSES`         | только для тестов | —      | `1` — `src/montages/journal.golden.test.ts` перезаписывает записанные ответы вместо сверки; см. `docs/testing.md` |

Четыре `R2_*` без значения по умолчанию работают как пара client id: не заданы (или пустые) —
хранилища нет, и эндпоинты загрузки честно отвечают `503 {"error":"storage not configured"}`
вместо того, чтобы делать вид, что виноват клиент. Всё остальное работает и без них.

`EMAIL_LOGIN_MAX_ATTEMPTS` и `EMAIL_LOGIN_RATE_MAX` двигают только вместе: код из шести цифр — это
миллион вариантов, и перебор ограничивает их произведение. Пять попыток на код и пять кодов за
окно — двадцать пять догадок из миллиона за пятнадцать минут; поднять любую из двух вдвое значит
вдвое облегчить подбор. Попытки считаются на код, а не на адрес: кончились — код мёртв целиком,
даже для верных цифр, и нужен новый запрос.

`SMTP_HOST`, `SMTP_USER`, `SMTP_PASSWORD` и `MAIL_FROM` — то же правило для почты: нет хотя бы
одного (или пустой) — письмо слать нечем, и `POST /auth/email/start` отвечает
`503 {"error":"mail not configured"}`. Сервис при этом поднимается как обычно: вход по Apple и
Google, сессии и всё остальное почты не касаются. Ящик и пароль заводит человек; в коде и в
репозитории их нет, в бою они приходят в окружение из инфраструктуры.

Письмо уходит только зашифрованным, и сертификат сервера проверяется. На 587 сервер обязан принять
STARTTLS — не принял, и отправка обрывается раньше, чем уходит пароль. У Gmail `MAIL_FROM` —
это сам ящик `SMTP_USER` или его подтверждённый псевдоним: чужой адрес Gmail молча заменит на ящик.
Сервер молчит дольше пяти секунд — отправка обрывается; и отказ, и молчание дают человеку `502`, а
причина уходит в лог строкой уровня `error`.

`EMAIL_LOGIN_DEV_BYPASS` — единственная дверь мимо письма, и она узкая: обход срабатывает, только
если переменная задана (`1` или `true`, регистр не важен), адрес на домене `test.test` и режим не
боевой. Нет хотя бы одного из трёх — запрос идёт обычным путём: письмо, а без настроек почты `503`
(см. «Как войти в разработке»). Домен выбран не случайно: `.test` — зона, которую RFC 2606
резервирует навсегда, её нельзя зарегистрировать, и почтового сервера там не будет ни у кого.
Настройки почты на обход не влияют — письму на `test.test` всё равно некуда прийти. Значение, которого
переменная не понимает (`0`, `no`, пустое), значит «выключено»: это единственная переменная,
которая открывает, а не запирает, поэтому непонятое значение оставляет дверь закрытой.

Раньше эту дверь держал открытой один лишь незаданный `NODE_ENV` — то есть забытая на чужой машине
переменная превращала вход по email в раздачу кодов на любой адрес. Теперь незаданное значит
«закрыто» по всем трём условиям. `NODE_ENV=production` остаётся жёстким запретом сверху: в боевом
режиме обход невозможен, что бы ни стояло в `EMAIL_LOGIN_DEV_BYPASS`, поэтому в боевом окружении
`NODE_ENV` обязан быть задан. Значение сверяется без учёта регистра и лишних пробелов и по началу
слова — `Production`, `production ` и `prod` тоже считаются боевым режимом.

Лимиты — предложенные числа. Они в окружении, а не в коде,
потому что их будут двигать, когда придёт настоящий материал, и админки для этого нет. Границы
длины ролика читаются один раз, при сборке приложения: ajv компилирует схему тела запроса заранее,
так что переменную нужно задать до старта, а не менять на живом процессе.

`INTERNAL_WORKER_TOKEN` — единственный ключ от `/internal/*`, куда стучится montage-воркер. Не
задан (или пустой) — маршрут закрыт для всех, и любой стук получает `401`: незаданный секрет это
«вход заперт», а не «вход свободен». Значение кладут в окружение обоих сервисов, и оно должно
совпадать до символа. Придумывать его руками не нужно и не стоит: маршрут висит на том же открытом
наружу порту, что и все остальные, и частота стуков ничем не ограничена — значит секрет должен быть
случайным: `openssl rand -base64 32`.

У `APPLE_CLIENT_ID` и `GOOGLE_CLIENT_ID` значения по умолчанию нет и быть не может: не задан
(или пустой — это та же опечатка) — значит провайдер выключен, и его эндпоинт отвечает `501`.
Пустая строка в роли `aud` сняла бы проверку аудитории вовсе, то есть приняла бы токен, выписанный
для чужого приложения.

Числовые значения проверяются: не число, ноль, отрицательное или дробное — это опечатка, а не
намерение, поэтому берётся значение по умолчанию. Иначе `EMAIL_LOGIN_RATE_WINDOW_MINUTES=-15` молча
снял бы ограничение частоты с единственного неавторизованного эндпоинта — а `=0.5` сделало бы ровно
то же самое, только выглядя осмысленно: все эти значения целые, и дробь округляется вниз до нуля.

Скрипты читают `.env` через встроенный `--env-file-if-exists` — никакого `dotenv`.
Значения из окружения перекрывают файл. `.env` в git не попадает.

## Миграции

Инструмент — [postgrator](https://github.com/rickbergfalk/postgrator): обычные `.sql`-файлы,
никакого DSL, состояние в таблице `schema_migrations`.

```bash
npm run migrate
```

Файлы лежат в `migrations/` и называются `<версия>.<do|undo>.<имя>.sql`:

```
migrations/001.do.init.sql     # применить
migrations/001.undo.init.sql   # откатить
```

Новая миграция — следующий номер и пара `do`/`undo`. Postgrator считает md5 применённых файлов,
поэтому **применённую миграцию не редактируют** — добавляют следующую.

Файл целиком уходит в Postgres одним запросом, то есть выполняется как одна неявная транзакция:
упавшая на середине миграция не оставит половину схемы. Отметка о версии пишется отдельным
запросом следом — если процесс убить ровно между ними, миграция окажется накатанной, но не
записанной, и следующий прогон её повторит. Поэтому миграции пишем идемпотентными
(`IF NOT EXISTS`).

### Таблица `jobs` — не наша

Очередь `jobs` принадлежит **montage** (`schema.sql`, `python -m montage init`); схему её API не
меняет. Своих строк у API три вида: `insert` задачи `media_preview` при завершении загрузки,
`delete` этой же задачи, когда удаляемое медиа перестало существовать (гнать воркера за тем, чего
уже нет, незачем), и `insert` задачи `montage` — при заказе ролика и при повторе упавшего.
Миграции на неё здесь нет и быть не должно — вместо этого `npm run migrate` в конце
**применяет файл соседа** (`../montage/schema.sql`, путь переопределяется `MONTAGE_SCHEMA_SQL`).
Так у схемы очереди остаётся один источник, а локальная база и `npm test` таблицу всё же имеют.
Файл идемпотентен, повторный прогон ничего не меняет.

Если соседа рядом нет (репозиторий API склонирован сам по себе), `npm run migrate` печатает об
этом строку и идёт дальше — таблицу тогда заводит montage сам, своей командой.

## Команды

| Команда             | Что делает                                                |
|---------------------|-----------------------------------------------------------|
| `npm run dev`       | сервер с перезапуском по изменениям                       |
| `npm start`         | сервер без вотчера                                        |
| `npm run migrate`   | накатить миграции                                         |
| `npm test`          | vitest, один прогон                                       |
| `npm run storage:check` | живой контроль хранилища на бакете для проверок — см. выше |
| `npm run lint`      | Biome — линт и проверка формата                           |
| `npm run format`    | Biome — переформатировать                                 |
| `npm run typecheck` | `tsc --noEmit` (движок типы не проверяет, только срезает) |

## Как это исполняется

Шага сборки нет: Node исполняет `.ts` напрямую, срезая типы. Значит, `enum`, `namespace` и
параметры-свойства конструктора не работают — `tsconfig.json` включает `erasableSyntaxOnly`,
так что `npm run typecheck` поймает это раньше рантайма.

Сервер слушает `0.0.0.0`, чтобы телефон или симулятор в той же сети мог до него достучаться.

## Боевой образ

`Dockerfile` в корне. CI (`.gitlab-ci.yml`) собирает его на каждый пуш в `dev`, кладёт в
`git.dapp-devs.com:5050/nox-labs/nox/remember/api:<полный SHA коммита>` и выкатывает на
dev-контур — см. «Выкатка на dev» ниже. `main` к CI не привязана.

```bash
docker build -t remember-api .

# миграции — та же команда, что и локально
docker run --rm -e DATABASE_URL=… remember-api npm run migrate

# сервер — команда по умолчанию, указывать ничего не нужно
docker run --rm -p 3000:3000 -e DATABASE_URL=… remember-api
```

| Что             | Значение                                                                  |
|-----------------|---------------------------------------------------------------------------|
| сервер          | команда по умолчанию: `node src/server.ts` (то же, что `npm start`)       |
| миграции        | `npm run migrate`                                                         |
| порт            | `3000` (`PORT`)                                                           |
| проба           | `GET /health` → `200 {"status":"ok"}`                                     |
| пользователь    | `node`, uid/gid `1000`; код принадлежит root и процессу не доступен на запись |
| файловая система| обе команды работают с корнем только на чтение, писать им некуда          |
| окружение       | только переменные из «Окружение»; `.env` в образе нет и не нужен          |

- **Секретов в образе нет.** Все значения, включая `DATABASE_URL`, приходят переменными окружения
  при запуске. Строка `.env not found. Continuing without it.` в логе — норма.
- **`NODE_ENV=production` задан в самом образе**, так что обход почты закрыт, даже если чарт
  забудет эту переменную.
- **Без базы сервер не поднимается**: нет `DATABASE_URL` или база недоступна — процесс падает с
  ошибкой в логе и кодом `1`. Мигратор ведёт себя так же.
- **Миграции — один раз на выкатку**, до старта новой версии сервера (например, Job-хуком), а не в
  каждой реплике: одновременные прогоны мигратора не проверялись.
- **Таблицы `jobs` мигратор в образе не создаёт**: `schema.sql` соседа в образ не входит, и
  `npm run migrate` печатает об этом строку. Таблицу заводит montage своей командой — и завести её
  нужно до того, как сервер примет первую загрузку или заказ ролика.
- **Остановка**: процесс под `tini` и завершается по SIGTERM сразу. Начатые запросы при этом
  обрываются — дожидаться их сервер пока не умеет.

### Выкатка на dev

На каждый пуш в `dev`:

1. `dev_build` собирает образ и кладёт его в реестр с тегом по полному SHA коммита.
2. `dev_deploy` клонирует репозиторий инфраструктуры `nox-infra-dev`, пишет `image.repository` и
   `image.tag` в `ioc-helm/nox/remember/api/values-dev.yaml`, коммитит
   `deploy remember-api dev <короткий SHA>` и пушит в его `main` (до 5 попыток, если там успели
   запушить другие).
3. ArgoCD (приложение `dev-remember-api`) синкает сам: сначала миграции хуком, потом новый под.

`dev_deploy` падает и ничего не пушит, если изменён не только этот файл, или в нём не только
строки образа, или у других полей поменялись значения. Тот же тег уже в чарте — джоба проходит
без коммита. Ключ SSH для записи в `nox-infra-dev` — переменная CI `SSH_PRIVATE_KEY`, заведённая
на весь GitLab, не в этом проекте.

**Первый запуск упадёт на `dev_deploy`**, пока чарт сервера не слит в `main` `nox-infra-dev`:
файла `values-dev.yaml` там ещё нет (`sed: … No such file or directory`). Это ожидаемо, образ при
этом собран. После слияния чарта — перезапустить джобу или запушить в `dev` снова.

**Как понять, что выкатка прошла.** Зелёный пайплайн значит только, что тег записан в чарт;
разворачивает ArgoCD, обычно за пару минут.

- `curl https://dev-api-remember.noxlabs.xyz/health` → `{"status":"ok"}`. 404 — Ingress ещё не
  создан, 503 — готового пода нет. `ok` отвечает и старый под, поэтому версию смотреть в Prometheus.
- Prometheus https://prometheus.noxlabs.xyz (вход не нужен). Какой образ у пода сервера — в метке
  `image` должен стоять новый SHA:
  `kube_pod_container_info{exported_namespace="default", exported_pod=~"dev-remember-api-.*", container="api"}`.
  Готовность, причины падений, упавшие миграции и логи в Loki — запросы в README чарта
  (`ioc-helm/nox/remember/README.md` в `nox-infra-dev`, раздел «Как наблюдать выкатку без доступа
  к кластеру»).

**Как откатить.** Вернуть прежний тег в `image.tag` файла `ioc-helm/nox/remember/api/values-dev.yaml`
в `main` `nox-infra-dev` — проще всего `git revert` коммита `deploy remember-api dev <SHA>`.
ArgoCD синкнет сам. Прежние SHA — в истории этого файла. Следующий пуш в `dev` снова выкатит
свежий код, так что откатывать или чинить нужно и в `dev`. Схему базы откат не трогает: мигратор
старого образа не знает новых версий и ничего не отменяет, старый код работает на новой схеме.
