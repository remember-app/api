# Ролики

## Ролики — как это устроено

Ролик монтирует не API, а сосед — **montage-воркер** (`projects/montage`). API владеет таблицей
`montages`: заводит строку по заказу организатора, показывает список участникам, рассылает пуш,
когда воркер сказал «готово», и даёт организатору переименовать и удалить ролик. Плюс принимает свой трек организатора,
если тот хочет монтировать под него, — `docs/music.md`. И отвечает на «итог перед монтажом» — что
войдёт в ролик и сколько ждать, — не записывая при этом ничего (`POST …/montages/preview` ниже).

1. `POST /memories/:memoryId/montages` — проверяются права и материал, в `montages` появляется
   строка в статусе `queued`, в `jobs` — задача `montage` со ссылкой на её `id`.
2. Воркер берёт задачу, ведёт строку `queued` → `processing` → `ready` (или `failed`), сам пишет в
   неё `video_key`, `poster_key`, `duration_seconds`, `error_text`.
3. Готово — воркер стучится в `POST /internal/montages/:montageId/ready`, и API шлёт пуш «ролик
   готов» **всем** участникам воспоминания.
4. Упало — у организатора кнопка «повторить»: та же строка возвращается в `queued`, и в очередь
   встаёт новая задача.
5. В любой момент организатор переименовывает ролик (`PATCH …/montages/:montageId`) или удаляет
   его вместе с файлами (`DELETE …/montages/:montageId`); экран готового ролика отмечает, кто его
   открывал (`POST …/montages/:montageId/watched`).

Статусы ролика — те же четыре слова, что у медиа, но своя цепочка: `queued` (заказан, ждёт
воркера), `processing` (монтируется), `ready` (можно смотреть), `failed` (упал, можно повторить).
Ролики живут **отдельно от галереи** и в неё не подмешиваются (doc-03).

### Контракт с воркером

Единственное, что связывает два репозитория, — это оно, и меняется только вместе с ними обоими:

| Что                | Чьё            | Как именно                                                      |
|--------------------|----------------|-----------------------------------------------------------------|
| таблица `montages` | заводит API (миграция) | воркер читает и пишет строку по `id`, как `media.py` уже делает с `media_items` |
| задача в `jobs`    | таблица montage | тип — ровно `montage`, `ref` — `montages.id` строкой            |
| `status`           | пишут оба      | API ставит только `queued`; всё дальше — воркера                 |
| `video_key`, `poster_key`, `duration_seconds`, `size_bytes`, `error_text` | воркер | API их только читает и подписывает ссылки; `size_bytes` — размер готового видео в байтах, пишется вместе с `ready` |
| `params`           | пишет API      | `{"target_seconds": 60, "music_tracks": []}` — эти два есть в каждом новом заказе — плюс `story_text`, `include_media_ids`, `exclude_media_ids`, `music_wishes`, `orientation` — то из них, что назвали. У заказа, отдавшего музыку режиссёру, вместо `music_tracks` стоит `music_director: true` (см. заказ ниже). `music_wishes` — `{"<трек>": "<пожелание>"}`, ключ — элемент `music_tracks` того же заказа. Старые строки не переписываются: у заказов старше `music_tracks` поля нет вовсе, и там встречаются `music_track_id` / `music_track_key`, у заказов старше `music_wishes` может лежать `music_note` — одна строка на весь заказ |
| таблица `music_uploads` | заводит API (миграция) | воркер её не читает: свои треки он берёт из хранилища по ключам `music/…` из `params.music_tracks` |
| `/internal/montages/:id/ready` | API | воркер дёргает его после того, как записал `ready`               |
| `montage_journal_entries`, `montage_stages` | заводит API (миграция) | воркер пишет в них рассказ о сборке — `docs/journal.md` |
| `name`, `template`, таблица `montage_watches` | API | воркер их не читает и не пишет; удалённый посреди сборки ролик воркер отпускает сам («went away mid-assembly») |

Каталог треков (`bright`, `warm`, `calm`, `night`, `road` — в порядке экрана «Под что монтировать»)
общий на оба сервиса: здесь по нему проверяется вход в заказ и подписывается ссылка на
предпрослушку (`GET /music/tracks/:trackId`, `docs/music.md`), сами файлы лежат у воркера
(`projects/montage/tracks/README.md` — источник и лицензия каждого), а копии для прослушивания он же
выкладывает в хранилище под ключами `tracks/<id>.mp3` (`python -m montage tracks`).
Свой трек организатора лежит в том же хранилище, что и материал,
и приходит воркеру ключом в том же списке `music_tracks` — скачать объект по ключу это всё, что с
треком делается.

## `GET /memories/:memoryId/montage-templates`

За `app.authenticate` + `app.requireMembership`. Отдаётся **только `organizer`**: `contributor` и
`viewer` получают `403 {"error":"forbidden"}`, не участник — `404`, как везде за этой проверкой.

Шесть готовых роликов с экрана «Каким будет ролик» (`design/screens/MontageTemplate.html`).
Шаблон — это **заранее заполненное тело заказа** и ничего сверх него: что пришло отсюда, то
приложение и шлёт в `POST /memories/:memoryId/montages`, поправив по дороге всё, что человек
захочет поправить (doc-03, «Автопилот»); `id` карточки при этом едет полем `template`, чтобы ролик
потом помнил, с какого шаблона начался. Своих строк в базе у шаблонов нет.

```
200 OK
[{"id":"for_myself","story_text":"Ролик для себя о «Свадьба Лизы и Марка». 2 сентября 2026 г., …",
  "target_seconds":180,"orientation":"landscape","music_tracks":["calm"],"music_wishes":{}}, …]
```

| Шаблон       | Длина | Формат | Музыка            |
|--------------|-------|--------|-------------------|
| `for_myself` | 3:00  | 16:9   | `calm`            |
| `quick`      | 1:00  | 16:9   | `bright`          |
| `report`     | 2:00  | 16:9   | `calm`            |
| `short_form` | 0:30  | 9:16   | `bright`          |
| `parents`    | 2:30  | 16:9   | `warm`            |
| `dopamine`   | 0:45  | 9:16   | `bright`, `road`  |

Порядок ответа — порядок карточек на экране и меняться не должен. Названия карточек («Для себя»,
«Дофаминовая бомба») и подписи под ними сервер **не отдаёт**: они живут в словаре приложения по
`id` и переводятся вместе с остальным интерфейсом (doc-8). «Настроить самому» — не шаблон, а
пустой заказ, и маршрут про него ничего не знает.

**Длина зажимается по материалу этого воспоминания** — по тем же границам, что проверяет заказ:
шаблон на три минуты в воспоминании с пределом в сорок секунд отдаёт `40`. Считается всё
готовое, кроме отсеянного автоотсевом (как и в заказе без пожеланий): вычеркнутых и возвращённых
кадров на этом шаге ещё нет, и приложение пережмёт длину само, когда они появятся.

**Где заказ всё равно откажут за нехваткой материала, отказывает и список.** Меньше трёх готовых
файлов или предел в ноль секунд — маршрут отвечает тем же `409` и тем же телом, что
`POST …/montages` без вычеркнутых кадров, и по той же проверке:

```
409 Conflict
{"error":"not enough material for a montage","ready_items":2,"need":3}
```

Шести карточек, ведущих к отказу на последнем шаге, приложение не получает. Права проверяются
раньше материала: `contributor` и `viewer` и здесь получают `403`.

**История собирается здесь, а не приложением:** заготовка шаблона плюс то, что сервер знает про
воспоминание, — название (подставляется как есть), даты одним числом или периодом и от скольких
человек в материале готовые кадры. Это ровно `people` из «итога перед монтажом» (`POST
…/montages/preview` ниже) и считается тем же запросом: кто ничего не принёс — участник или зритель, —
в «от N человек» не входит, и тот, чьи кадры все отсеяны, тоже. Вычеркнутых кадров здесь ещё нет,
поэтому шаблон считает всё готовое, кроме отсеянного, а итог — то, что осталось после
`exclude_media_ids` и возвращённого через `include_media_ids`. Язык — `users.language`
того, кто спросил; русский и английский написаны руками, английский не перевод (doc-8). Текст
влезает в поле «История ролика» на экране — не длиннее 600 символов с самым длинным названием.
Ничего, чего сервер не знает — имён, повода, — в тексте нет.

`music_wishes` — пожелания к трекам шаблона, у каждого своё: ключ — трек из `music_tracks` этого же
шаблона, значение — пожелание на языке того, кто спросил. Сейчас они есть у двух: у `parents` — к
`warm`, у `dopamine` — к `bright` и к `road` по отдельности. Где сказать нечего, там `{}`; поле
есть всегда, чтобы приложению не гадать, отдали его или забыли.

## `POST /memories/:memoryId/montages`

За `app.authenticate` + `app.requireMembership`. Заказать ролик может **только `organizer`**:
`contributor` и `viewer` получают `403 {"error":"forbidden"}`. Материал приносят все, а что из него
собрать — решает организатор (матрица прав — `docs/auth.md`).

```
{"target_seconds": 90, "story_text": "Как мы ехали на дачу",
 "include_media_ids": ["8f1c…"], "exclude_media_ids": ["3ab0…"],
 "music_tracks": ["music/7d2e…", "calm"], "music_wishes": {"music/7d2e…": "На сборы, тихо"},
 "orientation": "portrait"}
```

| Поле                 | Обязательно | Что это                                                     |
|----------------------|-------------|--------------------------------------------------------------|
| `target_seconds`     | нет         | желаемая длина, целое число секунд; границы считаются по материалу — ниже |
| `story_text`         | нет         | история ролика словами организатора, до 2000 символов        |
| `include_media_ids`  | нет         | id медиа этого воспоминания, которые войти должны            |
| `exclude_media_ids`  | нет         | id медиа этого воспоминания, которых в ролике быть не должно |
| `music_tracks`       | нет         | треки в порядке проигрывания: id с полки (`bright`, `warm`, `calm`, `night`, `road`) и ключи своих загруженных, вперемешку; до 50, без повторов |
| `music_director`     | нет         | `true` — музыку выбирает режиссёр-нейросеть, а не организатор; тогда `music_tracks` не шлют и не получают (см. «Музыка» ниже) |
| `music_wishes`       | нет         | пожелание к каждому треку отдельно: `{"<трек>": "<пожелание>"}`, ключ — элемент `music_tracks` этого же заказа, до 500 символов на пожелание |
| `orientation`        | нет         | `landscape` или `portrait`; не задана — ролик горизонтальный  |
| `name`               | нет         | имя ролика, до 200 символов: название шаблона из словаря приложения или то, что ввёл организатор |
| `template`           | нет         | `id` шаблона, с которого начали заказ: `for_myself`, `quick`, `report`, `short_form`, `parents`, `dopamine`; не прислан — «Настроить самому» |

**Шаблон.** Пишется в строку как есть и отдаётся в каждом ответе о ролике — по нему лист сведений
говорит, каким шаблоном заказан ролик. Не пришёл — в строке пусто, это «Настроить самому»; пусто и
у всех роликов, заказанных до появления поля. Что шаблон заполнил, уже лежит в остальном теле, и
поправленное по дороге руками шаблон не отменяет: поле говорит, с чего начали. В `params` не
попадает, итог перед монтажом его принимает и ничего о нём не говорит — как и `name`.

**Имя ролика.** Пришло — пишется в строку, обрезанное по краям. Не пришло или пустое («Настроить
самому») — в строке пусто, а наружу ролик отдаётся с подписью по заказанной длине: «Ролик на 1:30»
тому, кто читает по-русски, «Movie of 1:30» — по-английски (`users.language` спрашивающего; те же
слова, что у приложения на карточке). Подпись в строку не пишется: это не имя, а заглушка до
него, и каждый участник читает её на своём языке. В `params` имя не попадает — воркеру оно не
нужно. Итог перед монтажом поле принимает и ничего о нём не говорит.

Оба списка — про **`ready`-медиа этого же воспоминания**: id из чужого воспоминания,
несуществующий и тот, чьё медиа ещё грузится или обрабатывается, отклоняются с перечнем
виноватых, а не пропускаются молча — ролик без кадра, на котором настояли, выглядит собранным, и
никто не скажет обратного. Один и тот же id в обоих списках — тоже отказ: «обязательно и ни в коем
случае» это два распоряжения, и выбрать за организатора одно из них не наше дело. Регистр id не
важен — записывается нижний, тот, в котором их отдаёт база. Один id можно прислать и без массива:
схема свернёт его в список из одного.

**Длина — число секунд в пределе воспоминания.** Предел — это ролик, который воркер соберёт из
всего материала целиком: сумма длительностей готовых видео плюс 2,5 секунды на каждое готовое фото
**минус полсекунды на каждую склейку** (кадров N — склеек N − 1), но не больше десяти минут. Склейки
вычитаются, потому что воркер накладывает каждый кусок на предыдущий на полсекунды и ролик из всего
выходит ровно на столько короче суммы (`assembly.CROSSFADE_SECONDS` и `assembly.length_of` в
`projects/montage`): сорок фото — это 80,5 секунды, а не 100. Округляется вниз до целых секунд —
обещать больше, чем выйдет, нельзя. Кадры из `exclude_media_ids` в счёт не идут ни секундами, ни
склейками — ролик собирается из того, что осталось. Видео, длительность которого воркер ещё не
измерил, добавляет ноль (а его склейка — минус полсекунды); ниже нуля предел не опускается, и
предел, вышедший нулём, — это `409` «мало материала», а не ролик на 0 секунд. Нижняя граница —
10 секунд, но если материала меньше, она опускается до верхней: воспоминание из трёх фото
заказывается ровно на 6 секунд (7,5 минус две склейки). Вне границ — `400` с обоими числами, чтобы
приложение поставило ползунок на край, а не угадывало, где он.

**Отсеянное автоотсевом в предел не идёт** — ни секундами, ни склейками. Это кадры с
`screening_rejected = true` (см. галерею): воркер при заказе судит каждый файл заново тем же
анализом на той же копии (`selection.judge`, `projects/montage/screening.py`) и отсеянное не
берёт. Кадр, который организатор вернул — назвал в `include_media_ids`, — считается снова:
«включить» воркер слушается. Кроме отсеянного как `unreadable`: в таком файле нет ни одного кадра,
и воркер не ставит его в ролик даже названным. Кадры, до которых анализ ещё не дошёл (`null`), и
оставленные им (`false`) считаются как раньше: там предел приблизительный, и это честно —
угадывать вердикт, которого ещё нет, API не берётся. Итого предел —
`floor(min(600, Σ длин видео + 2,5 с × фото − 0,5 с × (N − 1)))`, где видео, фото и N — готовые
кадры этого воспоминания, кроме исключённых и отсеянных (возвращённые из отсева — в счёте, кроме
`unreadable`).

**Музыка — список любой длины.** В нём вперемешку id с полки воркера и ключи своих загруженных
треков этого воспоминания; порядок списка — порядок проигрывания и записывается как прислали.
Пустой список или отсутствие поля — ролик **без музыки**. Неизвестный id, ключ из чужого
воспоминания и недогруженный трек отклоняются поимённо. Другого способа назвать музыку нет: старые
`music_track_id` и `music_track_key` отклоняются ошибкой схемы, а не отбрасываются, как выдуманное
поле, — заказ, просивший музыку, не должен молча остаться без неё.

**Музыку можно не выбирать, а отдать режиссёру.** `music_director: true` — это «подбери сам»:
организатор не назвал ни одного трека и передал выбор нейросети, которая ведёт сборку. Это
отдельное поле, а не выдумка внутри списка: `music_tracks` при этом не шлётся и не пишется вовсе, а
в `params` встаёт `music_director: true` — так воркер отличает «режиссёр выберет» от «без музыки»,
которое он читает по пустому `music_tracks`. Пустой список рядом с флагом противоречием не
считается — он говорит ровно то же самое, — а вот непустой: «отдаю выбор» и «играй вот эти» это два
распоряжения об одном и том же, и выбрать за организатора одно из них не наше дело. Такой заказ
отклоняется `400`, как кадр, названный сразу и в `include_media_ids`, и в `exclude_media_ids`.
Пожеланий в этом режиме не бывает сами собой: пожелание живёт только у трека из `music_tracks`, а
треков здесь нет — отдельного правила для этого не заведено. Без флага всё как было: `music_tracks`
пишется всегда, даже пустым, а `music_director: false` — это «не отдал режиссёру» и ничего больше.

**Пожелание — у каждого трека своё.** `music_wishes` ключом называет трек ровно так, как он стоит в
`music_tracks` (id с полки или ключ своего), и воркер отдаёт режиссёру каждое пожелание вместе с его
треком. Пожелание обрезается по краям, как история; пустое после этого — «не сказали» и не пишется,
к какому бы треку ни было. Пожелание к треку, которого в `music_tracks` этого же заказа нет,
отклоняется с перечнем виноватых ключей — без треков, значит, пожеланий не бывает вовсе. Писать
пожелание к каждому треку не обязательно: трек без пожелания в `music_wishes` просто не назван.

Тело целиком необязательно: `{}`, `null` и запрос вовсе без тела — это один и тот же «без
пожеланий». Одна оговорка про третий вариант: «без тела» значит и без заголовка
`Content-Type: application/json`. Заголовок при пустом теле — это `400`
`FST_ERR_CTP_EMPTY_JSON_BODY` от самого Fastify, ещё до нашей схемы; клиенту, который ставит этот
заголовок всегда, надёжнее слать `{}`.

Незаданная длина записывается в строку значением по умолчанию (`MONTAGE_TARGET_SECONDS`, 60 с),
зажатым в границы этого воспоминания: у воспоминания на 6 секунд в строке будет 6. Невыбранная
ориентация не пишется: отсутствие поля воркер читает как `landscape`, ровно как у роликов,
заказанных до того, как поле появилось. Записывается только выбранная. Пустая история и пустой
список кадров — это «не сказали»: клиент, очищающий поле, шлёт его пустым, а не выбрасывает, и в
`params` такой ключ не попадает (история к тому же обрезается по краям). Исключение одно —
`music_tracks` пишется **всегда, даже пустым**: по нему воркер отличает «без музыки» от заказа,
сделанного до появления поля, где музыку он выбирал сам. Единственный случай, когда `music_tracks` не
пишется вовсе, — `music_director: true`: тогда на его месте стоит флаг, и воркер читает «выберет
режиссёр». `music_wishes` — наоборот, только когда в нём есть хоть одно непустое пожелание. Неизвестные поля отбрасываются, в `params` попадает только
то, что здесь описано.

```
201 Created
{"id":"…","memory_id":"…",
 "ordered_by":{"id":"…","username":"anya","name":"Аня"},"status":"queued","duration_seconds":null,
 "params":{"target_seconds":90,"story_text":"Как мы ехали на дачу",
           "include_media_ids":["8f1c…"],"exclude_media_ids":["3ab0…"],
           "music_tracks":["music/7d2e…","calm"],
           "music_wishes":{"music/7d2e…":"На сборы, тихо"},"orientation":"portrait"},
 "error_text":null,
 "created_at":"…","updated_at":"…","name":"Ролик на 1:30","template":null,"size_bytes":null,
 "photos":168,"videos":46,
 "video_url":null,"poster_url":null}
```

| Ответ | Тело                                                        | Когда                          |
|-------|-------------------------------------------------------------|--------------------------------|
| `403` | `{"error":"forbidden"}`                                      | участник, но не организатор    |
| `409` | `{"error":"not enough material for a montage","ready_items":2,"need":3}` | после вычета исключённых и отсеянных остаётся меньше трёх `ready`-медиа или предел длины выходит 0 |
| `400` | `{"error":"a media item cannot be both included and excluded","media_ids":["…"]}` | один и тот же кадр в обоих списках |
| `400` | `{"error":"music_director cannot be combined with music_tracks"}` | `music_director: true` вместе с непустым `music_tracks` |
| `400` | `{"error":"no such ready media in this memory","media_ids":["…"]}` | id не из этого воспоминания или медиа ещё не `ready` |
| `400` | `{"error":"target_seconds out of range","min_seconds":10,"max_seconds":63}` | длина вне предела этого воспоминания |
| `400` | `{"error":"no such music track","music_tracks":["…"]}` | id не с полки, ключ не из этого воспоминания или трек не догружен |
| `400` | `{"error":"music wish for a track not in music_tracks","music_wishes":["…"]}` | пожелание к треку, которого нет в `music_tracks` этого заказа (или треков нет вовсе) |
| `400` | ошибка схемы                                                 | длина не целая, ориентация не `landscape`/`portrait`, шаблон не из шести, имя длиннее 200 символов, история длиннее 2000 символов, пожелание к треку длиннее 500, треков больше 50 или один дважды, `music_director` не булев, в списке кадров не id или один и тот же дважды, старые `music_track_id` / `music_track_key` |

Меньше трёх готовых файлов — отказ **до** записи: ни строки, ни задачи не остаётся. Считаются
только `media_items` в статусе `ready`: то, что ещё грузится или обрабатывается, воркеру нечем
монтировать. Порог держится по тому, что останется в
ролике: из числа `ready`-медиа вычитаются кадры из `exclude_media_ids` и отсеянные автоотсевом
(кроме возвращённых — ровно как в пределе выше), поэтому воспоминание из пяти с тремя
вычеркнутыми или отсеянными — тот же отказ, что и воспоминание из двух, а `ready_items` в ответе —
остаток этого заказа, не всё, что лежит в воспоминании. Так же считает и воркер: его второй порог
после отсева — три годных кадра, где отсеянное идёт в счёт, только если его вернули. Списки проверяются раньше порога: если в
них назван чужой или неготовый кадр, ответом будет `400` про него. Клиент показывает это своими
словами — «недостаточно материала для ролика»; тело ответа, как и везде здесь, английское и с
числами.

Строка, задача в очереди, `memories.montage_count` и `user_usage.montage_count` двигаются **одной
транзакцией**: счётчик считает заказанное, а не смонтированное, и разойтись со строками не может.
Числа роликов на воспоминание не ограничиваем (doc-03).

## `POST /memories/:memoryId/montages/preview`

«Итог перед монтажом» (doc-03): что войдёт в ролик, до какой длины можно и сколько примерно ждать —
**до** нажатия «Начать монтаж». Тот же заказ, только не заказ.

Тело — **ровно то же**, что у `POST /memories/:memoryId/montages`, все поля необязательные. Права
те же (только `organizer`, остальным `403`, не участнику `404`) и проверки те же, в том же порядке
и с теми же телами ответов: итог, который согласился на то, что заказ отклонит, хуже отсутствия
итога. Отличие одно: **ничего не пишется** — ни строки в `montages`, ни задачи в `jobs`, ни
счётчиков. Экран можно открывать сколько угодно раз.

```
200 OK
{"photos":168,"videos":46,"people":5,"min_seconds":10,"max_seconds":443,
 "target_seconds":150,"orientation":"landscape","estimate_minutes":15}
```

| Поле               | Что это                                                                  |
|--------------------|---------------------------------------------------------------------------|
| `photos`, `videos` | сколько фото и видео войдёт: готовые за вычетом `exclude_media_ids` и отсеянного |
| `people`           | от скольких разных людей эти кадры                                        |
| `min_seconds`, `max_seconds` | предел длины по этому же материалу — как в заказе                |
| `target_seconds`   | длина, которую записал бы заказ: названная или умолчание, зажатое в предел |
| `orientation`      | `landscape` или `portrait`; не названа — `landscape`                      |
| `estimate_minutes` | сколько примерно монтировать, в минутах, не меньше одной                  |

Кадры из `include_media_ids` считаются наравне с прочими: «войти должен» закрепляет кадр в ролике,
а к материалу добавляет его, только если возвращает из отсева (кроме `unreadable` — см. предел
у заказа). Медиа не в статусе `ready` не в счёт — воркеру с ними нечего делать.

**`estimate_minutes` — ориентир, а не обещание.** Грубая прикидка по числу кадров и длине ролика
(по три секунды на кадр плюс полторы на каждую секунду готового видео, вверх до целых минут),
выверенная по макету `design/screens/MontageSummary.html` — «214 кадров на 2:30 ≈ 15 минут». Никто
не держит воркера в этих рамках: очередь может быть занята, нейросеть — медленной, а сборка вообще
упасть. Приложение так и говорит: «соберём примерно за столько-то».

Ответы об отказе — те же, что у заказа, той же таблицей: `403` не организатору, `409` «мало
материала», `400` на противоречивые и чужие списки кадров, `music_director` с непустым
`music_tracks`, длину вне предела, неизвестный трек, пожелание к треку не из заказа и ошибки схемы.
Тело ответа совпадает с тем, что на то же самое тело вернул бы сам заказ.

## `GET /memories/:memoryId/montages`

За `app.authenticate` + `app.requireMembership`. Список роликов воспоминания, **новые сверху**.
Читает любой участник, `viewer` в том числе: матрица даёт ему «смотреть галерею и ролики».

```
200 OK
[{"id":"…","memory_id":"…",
  "ordered_by":{"id":"…","username":"anya","name":"Аня"},"status":"ready","duration_seconds":58.5,
  "params":{"target_seconds":60,"orientation":"portrait"},"error_text":null,
  "created_at":"…","updated_at":"…","name":"Дача, лето","template":"short_form","size_bytes":"18350120",
  "photos":168,"videos":46,
  "video_url":"http://…&X-Amz-Signature=…","poster_url":"http://…&X-Amz-Signature=…",
  "stages":null,
  "queue":null,
  "watched_by":[{"id":"…","username":"liza","name":"Лиза"},{"id":"…","username":"mark","name":null}]}]
```

`ordered_by` — кто заказал ролик: `id`, `username`, `name` — те же три поля, что в `watched_by`,
так что «кем собран» подписывается без второго запроса. Заказавший может уже и не быть участником
— ролик остаётся, и подпись тоже.

`name` — данное ролику имя, а у неназванного — «Ролик на 1:00» по заказанной длине на языке
спрашивающего (см. заказ выше). Строка есть всегда.

`template` — с какого шаблона начали заказ (`id` карточки, см. заказ выше); `null` — «Настроить
самому». Название карточки приложение берёт из своего словаря по этому `id`.

`size_bytes` — размер готового видео в байтах, строкой, как у кадров (bigint без округления).
`null` — размер не записан: ролик ещё не готов или собран до того, как воркер начал его писать.

`photos`, `videos` — сколько фото и видео насчитал заказ, теми же числами, что показал «итог перед
монтажом». Пишет заказ при постановке в очередь и больше никто. `null` — ролик заказан до того, как
появились эти колонки (миграция 180), и «что заказано» тогда показать нечем. Из них же API считает
`queue.estimate_minutes` — сколько ждать своей очереди.

`queue` — место ролика в очереди, пока он в ней стоит (`queued`); у всего, что worker уже взял или
ролик ушёл из очереди, — `null`. Экран «в очереди» рисует его целиком («перед нами ещё один ролик,
сборка начнётся примерно через 2 минуты и займёт около 14»), и всё это — от одного поля:

| Поле                 | Что это                                                             |
|----------------------|---------------------------------------------------------------------|
| `ahead`              | сколько роликов стоят в очереди перед ним, **в общей очереди** всего worker'а, а не только этого воспоминания |
| `starts_in_minutes`  | через сколько минут примерно начнётся сборка, `ceil` от суммы ожиданий впереди |
| `estimate_minutes`   | сколько сама сборка займёт — та же прикидка, что у `POST …/montages/preview`; `null`, если `photos`/`videos` не записаны и считать не по чему |

Очередь — таблица `jobs`, и ждёт ролик всех, чья задача уже идёт или стоит раньше. Считается по
роликам, а не по задачам: у повторённого их бывает две — старая, до которой worker так и не дошёл,
и новая. Уже идущему ролику API верит журналу: у него `montage_stages.eta_seconds` незакрытых этапов
и есть «сколько осталось», а прикидка по кадрам — для тех, кто ещё не начал. **Ориентир, а не
обещание**, ровно как `estimate_minutes` в заказе.

`watched_by` — кто из **нынешних** участников уже открывал готовый ролик, в порядке первого
просмотра: `id`, `username`, `name` — те же три поля, что везде, где отдаётся человек. Отмечает
`POST …/watched` ниже. Вышедший из воспоминания в списке не стоит (его отметка остаётся и вернётся
вместе с ним). У неготового — всегда `[]`. «4 из 6» на листе сведений — это длина этого списка
против числа участников. Читается одним запросом на весь список и только по готовым.

`video_url` — подписанная ссылка на готовый ролик, живёт `R2_DOWNLOAD_TTL_SECONDS` (15 минут, тот
же срок, что у галереи). У всего, что не `ready`, она `null` — это «ещё не готово», а не ошибка;
протухла — клиент запрашивает список заново. Ключ ролика наружу не отдаётся, только ссылка.

`poster_url` — то же самое для кадра-постера, который клиент показывает до запуска ролика:
подписывается из `poster_key` тем же способом и на тот же срок. `null` не только у неготового —
у ролика, смонтированного до того, как воркер научился резать кадр, постера нет и не появится, и
клиент рисует такой ролик без превью.

`stages` — куда дошла сборка: **пять этапов в порядке пайплайна**, у каждого своё состояние
(`pending` / `running` / `done` / `failed`). Из них карточка на ленте сама считает «3 из 5» и красит
шкалу из пяти полосок (`design/screens/MemoryFrames.html`), а упавший этап красит по-своему —
открывать журнал каждой карточки для этого не нужно.

```json
"stages":[{"stage":"prep","state":"done"},{"stage":"analysis","state":"running"},
          {"stage":"directing","state":"pending"},{"stage":"music","state":"pending"},
          {"stage":"assembly","state":"pending"}]
```

Этапов у ролика либо пять, либо ни одного: воркер заводит все пять разом, в `pending`, как только
взял ролик, — до первой записи и первого скачанного файла. `null` — когда этапов нет (ролик
`queued`, то есть заказан или поставлен повторить, или отказан воркером раньше, чем тот завёл
этапы), и у **готового**: шкала ему не нужна, и его этапы список не читает. Что за этапы и в каком
состоянии они у упавшего — «Этапы» в `docs/journal.md`. На весь список этапы читаются
**одним запросом**, и чтение списка никого не отмечает смотрящим — это делает только маршрут
журнала.

У упавшего в `error_text` лежит то, что сказал воркер, — рядом с ним клиент рисует «повторить».

Не заданы `R2_*` — `503 {"error":"storage not configured"}`, как и у галереи: подписать нечем.
Не участник, несуществующее воспоминание и кривой id — общий `404 {"error":"not found"}`.

## `POST /memories/:memoryId/montages/:montageId/retry`

Там же, и снова **только `organizer`**. Повторяет **упавшую** сборку: та же строка возвращается в
`queued`, `error_text` обнуляется, в `jobs` встаёт новая задача `montage`. Ответ — обновлённая
строка в той же форме, что в списке (с `ordered_by`, `template`, `size_bytes`, `photos` и `videos`),
только без `stages`, `queue` и `watched_by`: их досчитывает список. Той же
транзакцией стираются записи журнала и этапы прошлой попытки — повтор встаёт в очередь с чистым
листом, без этапов в списке и с пустым журналом; смотрящих это не трогает.

| Ответ | Тело                                                        | Когда                          |
|-------|-------------------------------------------------------------|--------------------------------|
| `200` | строка ролика                                                | был `failed`, теперь `queued`  |
| `403` | `{"error":"forbidden"}`                                      | участник, но не организатор    |
| `409` | `{"error":"montage has not failed","status":"queued"}`       | ролик не падал                 |
| `404` | `{"error":"not found"}`                                      | нет такого ролика, он из чужого воспоминания или `montageId` не uuid |

Проверка «был `failed`» стоит в самом `UPDATE`, а не только в условии перед ним: две нажатые
подряд кнопки двигают строку один раз, и вторая получает `409`. Иначе на одной строке оказались бы
две задачи.

## `PATCH /memories/:memoryId/montages/:montageId`

«Переименовать» (макет SheetFilmInfo). Только **`organizer`**, в **любом статусе** — имя воркеру
не нужно, и сборка его не трогает.

```
{"name": "Дача, лето"}
```

`name` обязательно, до 200 символов, обрезается по краям. Пустое — ролик снова без имени и
отдаётся с «Ролик на 1:00». Ответ — строка ролика в той же форме, что у повтора; новое имя сразу
видно в списке и в «Сведениях о кадре» (`docs/media.md`).

| Ответ | Тело                     | Когда                                              |
|-------|--------------------------|----------------------------------------------------|
| `200` | строка ролика            | переименован                                       |
| `400` | ошибка схемы             | нет `name`, не строка или длиннее 200 символов     |
| `403` | `{"error":"forbidden"}`  | участник, но не организатор                        |
| `404` | `{"error":"not found"}`  | нет такого ролика, он из чужого воспоминания или `montageId` не uuid |

## `DELETE /memories/:memoryId/montages/:montageId`

«Удалить ролик» — насовсем. Только **`organizer`**, в **любом статусе**. Ответ — `200 {"ok":true}`.

Одним запросом уходят строка ролика, задача в очереди, если до неё не дошли, и каскадом — журнал,
этапы, раскладка кадров (`montage_frames`), смотрящие сборку и отметки «посмотрел».
`memories.montage_count` уменьшается на один — это «N роликов» на карточке воспоминания;
`user_usage.montage_count` не трогается — он считает заказанное. После коммита из хранилища
удаляются видео и постер, тем же способом, что файлы удалённого кадра: без отката и best effort —
не удалилось — предупреждение в логе, а ролика уже нет. Собиравшийся в этот момент ролик воркер
дособирает, не находит строки и сам убирает залитое. Тот же запрос делает и удаление воспоминания
целиком (`DELETE /memories/:memoryId`).

| Ответ | Тело                     | Когда                                              |
|-------|--------------------------|----------------------------------------------------|
| `200` | `{"ok":true}`            | удалён                                             |
| `403` | `{"error":"forbidden"}`  | участник, но не организатор                        |
| `404` | `{"error":"not found"}`  | нет такого ролика (или уже удалён), он из чужого воспоминания или `montageId` не uuid |

## `POST /memories/:memoryId/montages/:montageId/watched`

«Посмотрел»: экран готового ролика стучится сюда, когда открылся. Ссылку на видео приложение
берёт из списка и играет прямо из хранилища — до API показ не доходит, поэтому отметку шлёт сам
экран. Любой участник, `viewer` в том числе. Тела нет.

Это факт «открывал хоть раз», а не история показов: строка на человека в `montage_watches`,
повторный стук ничего не меняет и снова отвечает `200 {"ok":true}`. Отмечается только **готовый**
ролик. Кто отмечен — `watched_by` в списке.

| Ответ | Тело                                                    | Когда                        |
|-------|---------------------------------------------------------|------------------------------|
| `200` | `{"ok":true}`                                           | отмечен (или уже был)        |
| `409` | `{"error":"montage is not ready","status":"queued"}`    | ролик не `ready`             |
| `404` | `{"error":"not found"}`                                 | нет такого ролика, он из чужого воспоминания или `montageId` не uuid |

Не путать со смотрящими журнала (`viewers` в `docs/journal.md`): там «кто смотрит сборку прямо
сейчас» с окном в секунды, здесь — кто видел готовый ролик.

## `POST /internal/montages/:montageId/ready`

**Не за `app.authenticate`** — за этим маршрутом нет человека и сессии. Стучится montage-воркер,
когда ролик выложен и строка уже переведена в `ready`; API делает то единственное, чего воркер не
может, — доносит новость до телефонов.

```bash
curl -X POST http://localhost:3000/internal/montages/<id>/ready \
  -H "Authorization: Bearer $INTERNAL_WORKER_TOKEN"
```

Авторизация — общий секрет `INTERNAL_WORKER_TOKEN` в заголовке `Authorization: Bearer`. Не совпал,
не пришёл вовсе или не задан в окружении — `401 {"error":"unauthorized"}`. Сверка идёт по хешам
через `timingSafeEqual`: обычное сравнение строк выдаёт префикс секрета тому, кто его меряет.

Ответ — `200 {"ok":true}`, **даже если пуш не дошёл ни до кого**: ролик готов независимо от
уведомления, а сказать воркеру «не вышло» значило бы отправить его повторять задачу, вся работа
которой сделана. Несуществующий, кривой `montageId` — и строка, которая ещё не `ready`, —
`404 {"error":"not found"}`: маршрут умеет сказать только «ролик готов», и над строкой в `queued`,
`processing` или `failed` ему нечего объявлять. Поэтому порядок обязателен — сперва записать
`ready`, потом стучаться, — и повторный стук по той же строке безопасен.

Тело у запроса не читается: `video_key`, `poster_key`, `duration_seconds` и `status` воркер уже
записал сам.
