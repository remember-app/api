# Тесты

Тесты (интеграционные, против той же локальной базы и того же локального хранилища; миграции
накатываются сами, шагом `pretest`, поэтому поднятые Postgres и MinIO обязательны):

```bash
npm test
```

⚠️ `npm test` накатывает миграции и пишет в ту базу, на которую смотрит `DATABASE_URL`. Не
запускайте его с `.env`, направленным куда-либо кроме локальной базы.

Тест миграций (`src/migrations.test.ts`) гоняет цепочку в собственной временной базе — создаёт и
сам удаляет её, поэтому пользователю из `DATABASE_URL` нужно право `CREATE DATABASE` (у локального
Postgres из `docker-compose.yml` оно есть). Общие таблицы он не трогает.

Почтовый ящик тестам не нужен: `src/auth/auth.test.ts` поднимает свой SMTP-сервер (`smtp-server`)
и шлёт письма входа туда — с STARTTLS и AUTH, как в бою. Настройки `SMTP_*` из `.env` он
перекрывает своими.

Хранилище в тестах — MinIO, драйвер `s3`. `src/media/r2.test.ts` ставит перед MinIO из `R2_*` свою
записывающую прокладку на свободном порту, проигрывает через неё жизнь файла и сверяет каждый
запрос с формой, которую принимает S3-совместимый API Google. Пишет под префиксом `r2-test/` и за
собой убирает.

Сквозной сценарий — `src/journey.test.ts`: настоящий сервер на порту, вход по письму (свой SMTP) и
через дверь рецензента (боевой режим, без почты), воспоминание, кадр из двух кусков с докачкой по
заново выданной ссылке, галерея, скачивание, удаление кадра и воспоминания, выход и отзыв сессий.
Запуск сервера как процесса (порядок проверок: хранилище, потом база; громкий выход) —
`src/server.test.ts`.

Боевой драйвер `google` проверяет `src/media/gcs.test.ts` — без сети и без Google: эмулятора его
multipart нет, поэтому `fetch` подменён, а ключ служебной учётки тест делает себе сам. Сверяются
подпись ссылок (канонический запрос выписан в тесте руками по справочнику Google, подпись
проверяется открытой половиной ключа), покупка и кеш токена, форма каждого запроса, ответы
`404`/`204`/`400`/`403`, повторы, префикс и отказ стартовать без настроек. Что именно сверяется —
`docs/media.md`, «Хранилище: Google Cloud Storage»; на настоящем бакете — `npm run storage:check`
(`docs/running.md`).

## Журнал монтажа — снимки и записанные ответы

Тест `src/montages/journal.golden.test.ts` ведёт через настоящие маршруты api не написанный руками
журнал, а **настоящий вывод воркера**: ролик грузится в базу из снимка, читается `GET …/journal`,
`GET …/montages`, повторяется и удаляется. Данные лежат в `src/montages/golden/`:

| Файл                                                  | Что это                                                                |
|-------------------------------------------------------|-------------------------------------------------------------------------|
| `journal_director.json`                               | снимок сборки, которую режиссировала нейросеть (записанным ответом): 13 файлов, ролик 15 с |
| `journal_algorithm.json`                              | снимок сборки без нейросети (подготовка и ритм): 12 файлов, ролик 10,07 с     |
| `responses_director.json`, `responses_algorithm.json` | ответы api по этим двум сборкам — для приложения (ниже)                  |

**Снимки — копии.** Их пишет воркер (`projects/montage/tests/fixtures/journal_*.json`; формат и
нормализация — в `docs/testing.md` montage, «Золотой снимок журнала»), а здесь лежат закоммиченные копии.
Между репозиториями ничто не следит, что копии свежие: воркер перезаписал свои снимки, а здесь их не
обновили — тест зелёный на старом выводе. Этот разъезд — условие связи, устранить его api не может.

> **Разъезд на этот раз — в другую сторону, и он не разъезд, а порядок.** Снимки здесь переписаны под
> пять новых этапов (`format: 2`, `prep` / `analysis` / `directing` / `music` / `assembly`, `details` в
> записях, новые ключи `outcome`) **раньше, чем воркер перейдёт на них** (TASK-464). Копии в
> `projects/montage/tests/fixtures/` пока старые, `format: 1`, — так и должно быть: контракт(api)
> зафиксирован первым, воркер подтягивается под него. Поэтому **не перезаписывайте снимки отсюда
> командой ниже**, пока TASK-464 не придёт: она вернёт старый формат и тест упадёт. Когда придёт —
> копии надо взять у воркера заново и убедиться, что он пишет `format: 2`.

Обновить копии (после того, как воркер перешёл на новый формат):

```sh
cp ../montage/tests/fixtures/journal_*.json src/montages/golden/
npx biome format --write src/montages/golden       # воркер пишет свой формат, biome его переписывает
npm test -- src/montages/journal.golden.test.ts    # упадёт на записанных ответах, если вывод изменился
```

**Записанные ответы** тест по умолчанию только **сверяет** с закоммиченными и падает с
построчной разницей по имени шага; молча не перезаписывает никогда. Перезапись — только явно:

```sh
JOURNAL_RECORD_RESPONSES=1 npm test -- src/montages/journal.golden.test.ts
npx biome format --write src/montages/golden
```

Затем посмотреть разницу в `src/montages/golden` — изменившиеся ответы читает приложение, поэтому
это повод сказать ему, а не только закоммитить.

### Формат записанных ответов

`responses_<сценарий>.json` — самодостаточный JSON, знать TypeScript для чтения не нужно:

```json
{ "format": 1, "scenario": "director", "source": "journal_director.json",
  "steps": [
    { "name": "live_poll_3",
      "request":  { "as": "organizer", "method": "GET",
                    "path": "/memories/00000000-0000-4000-8000-a00000000001/montages/00000000-0000-4000-8000-b00000000001/journal",
                    "query": { "after": 4, "limit": 4 } },
      "response": { "status": 200, "body": { "montage": {}, "stages": [], "entries": [], "has_more": true, "files": [], "viewers": [] } } } ] }
```

- `steps` — **по времени**: так они шли в одном прогоне; `live_*` — это одна сборка, опрос за
  опросом, проигрывать по порядку. `name` уникален в файле.
- `request.as` — кто спрашивает: `organizer`, `contributor`, `viewer`, `stranger` (не участник) или
  `null` (без токена). Токенов в записи нет. `method` — всегда `GET`, `path` — как есть, `query` —
  параметры строки запроса (`limit`, `after`, `media_id`).
- `response.status` — код ответа, `response.body` — тело **как его отдал api** (форма — `docs/journal.md`
  и «Список роликов» в `docs/montages.md`), с нормализацией ниже.

Нормализация — чтобы запись не менялась от прогона к прогону:

- **Все id — фиксированные uuid** вида `00000000-0000-4000-8000-<буква><11 цифр>`: воспоминание
  `a…01`; ролики `b…01` (ролик из снимка), `b…02` (старый готовый, собранный до журнала — журнал
  пуст), `b…03` (стоит в очереди); люди `c…01` организатор `anya`, `c…02` участник `marko`, `c…03`
  зритель `lena`, `c…04` посторонний `ivan`; файлы `f…NN`, где `NN` — `position` файла в снимке
  (`f1` → `f…01`). Файлы с нечётным `position` привёз организатор, с чётным — участник.
- **`entries[].id` — номер записи `n` из снимка** (1, 2, 3… в порядке записи), а не bigserial из
  базы. Курсоры в `query.after` и `query.before` — тоже эти номера; `0` — «с начала».
- **Ссылки** (`thumbnail_url`, `video_url`, `poster_url`) — без подписи и срока: `<хост>/<бакет>/<ключ>?signed`.
  Настоящие подписаны и живут 900 секунд; в записи они лишь показывают, что ссылка есть и куда ведёт.
- **`files` отсортированы по id**: порядок файлов в ответе api не обещает.
- **Времена не менялись**, они и так фиксированы: записи и этапы — метки снимка (секунды от
  `2026-01-01T00:00:00Z`), `captured_at` файла — `2025-12-31T18:00:00Z` плюс `captured_after_seconds`
  из снимка, `created_at` роликов задан тестом.
- **Что настоящее, что смоделировано.** Записи и итоговые строки этапов — вывод воркера, из
  снимка. Порядок, в котором они ложатся в базу, тест ведёт так, как воркер (`journal.py`,
  `montage.py`), — строка этапа не появляется, а только меняется:
  1. **`begin`** — до первого скачанного файла и первой записи все пять этапов сразу, в `pending`:
     `started_at` и `finished_at` пусты, `done_count` `0`, `total_count` пуст, `outcome` `{}`,
     `eta_seconds` — оценка воркера по числу файлов снимка и заказанной длине ролика (`prep`
     1,5 с на файл, `analysis` 0,8, `directing` 0,5, `music` 0,2 с на файл и 0,1 на секунду
     ролика, `assembly` 1,4 с на секунду ролика; округление как у Python). Эти числа — копия ручки
     воркера `journal.ESTIMATE` в тесте, а не часть снимка (закрытый этап стоит с нулём), так что
     с копиями снимков они ездят вместе: воркер подстроил ручку — обновить её и в тесте.
  2. **Этап начался** — `UPDATE` той же строки: `running`, `started_at`, `total_count`; оценка та же,
     что поставил `begin`.
  3. **По ходу** — двигают счётчик только два этапа. Подготовка — по файлу: после записи о файле
     `done_count` равен номеру файла в порядке съёмки (`position`), а `eta_seconds` пересчитан по
     факту (прошло ÷ сделано × осталось). Сборка — по готовому куску; опрос — на середине.
     «Анализ», «Режиссура» и «Музыка» ничего не двигают: пока этап идёт, `done_count` `0`, оценка —
     с `begin`, а записи ложатся порциями по пять. У сборки запись одна (мысль без файла), у музыки —
     по одной на часть истории, а **частей у снимка без режиссуры нет**, и в `journal_algorithm`
     записей у музыки нет вовсе.
  4. **Этап кончился** — `done`, `finished_at`, `eta_seconds` `0`, `done_count` равен `total_count`,
     `outcome` из снимка.

  Раскладка кадров (`montage_frames`) ложится между ритмом и склейкой. Времена — метки снимка;
  `begin` стоит в ту же секунду, с которой начинается первый этап, а середина склейки — на
  пропорциональной доле её отрезка. Тест **не умеет завести этап**: `start`, `progress`, `finish`
  только `UPDATE`-ят и падают, если строки нет, — поэтому «этап появился по ходу сборки» в записи
  попасть не может: в `live_first_open_empty` пять этапов в `pending`, и во всех опросах после — те
  же пять. Записи ложатся порциями по пять, опрос — `limit=4`, поэтому после порции видно
  `has_more: true`, а на следующем опросе — хвост. В первом опросе отсев
  стоит `running` с `done_count`, равным `total_count`: отсеянные файлы в снимках — последние по
  порядку съёмки, и счётчик доходит до конца раньше, чем воркер закрывает этап, — это не ошибка
  записи.

Шаги (в порядке записи):

| `name`                                                      | Что это                                                        |
|-------------------------------------------------------------|-----------------------------------------------------------------|
| `journal_of_old_ready_montage`, `journal_of_queued_montage` | ролик без журнала — `stages: []`, `entries: []`                  |
| `live_first_open_empty`                                     | экран открыли до первой записи, когда воркер уже завёл этапы: записей нет, курсор дальше — `0`, этапов пять и все `pending` с `eta_seconds` |
| `live_poll_1` … `live_poll_N`                               | опросы `after=<наибольший id прошлого ответа>`, `limit=4`; пока `has_more` — спрашивать сразу; в каждом ответе все пять этапов; ответ без записей — у этапа сменилось состояние или счётчик. Хвост после опроса, где `directing` стал `done`: музыка `running`, затем её записи (в снимке режиссёра — по одной на часть истории, в снимке без режиссёра их нет вовсе), музыка `done`, сборка `running` (`0` из N, оценка с `begin`), сборка на середине (`done_count` — половина, оценка пересчитана), сборка `done` |
| `montage_list_while_building`                               | список роликов, пока сборка идёт: у собирающегося пять этапов со своими `state`, у ждущего и старого готового — `stages: null`, `queue: null` |
| `live_viewer_opens_mid_build`                               | зритель открыл сборку посередине: первая загрузка без `after`, свежие сверху, `has_more: true`, в `viewers` рядом организатор |
| `journal_after_ready_nothing_new`                           | ролик собран, курсор тот же — записей нет, `viewers: []`         |
| `journal_of_ready_montage`                                  | готовый ролик — весь журнал за один запрос (`limit` по умолчанию 200) |
| `journal_of_one_file`                                       | тот же ролик, суженный до одного файла (`media_id`)              |
| `montage_list_after_ready`                                  | список роликов после сборки: у готового `stages: null`, `video_url` есть |
| `journal_of_stranger`                                       | посторонний: `404 {"error":"not found"}`                         |

Что тест проверяет за собой, а не только записывает: по курсору с малым `limit` ничего не потеряно,
не задвоено, порядок сохранён; этапов в каждом ответе живого сеанса ровно пять, а состояние каждого — то, что воркер оставил в базе на этот миг; после «готов» журнал совпадает со снимком запись в запись (по смыслу
полей, а не по id), этапы — с тем, что записал воркер; `files[].places` — раскладка снимка, у файла
вне раскладки пусто; у клипа, взятого несколькими отрезками (`f3` режиссёрского снимка), i-я его
запись «беру» приходится на i-е место в `places`, даже если раскладка легла в базу задом наперёд; читают организатор, участник и зритель, а посторонний, чужой ролик и чужое
воспоминание — `404`, без токена — `401`; упавший ролик (`failed` с упавшим этапом) повторяет только
организатор, после повтора журнал пуст, этапы в списке `null`, в очереди одна задача; удалён кадр —
записи о нём остались без сведений о файле, мест в раскладке у него нет; удалён ролик — журнала нет.

Ролик без журнала — собранный раньше, чем журнал появился, ещё стоящий в очереди или отказанный
раньше, чем воркер завёл этапы, — отвечает **пустым ответом, а не ошибкой**: `stages: []`,
`entries: []`, `files: []`. Взятый воркером отвечает пятью этапами в `pending` ещё до первой
записи. Журнал готового ролика читается так же, как идущий, сколько бы времени ни прошло; у
упавшего — то, что успело записаться.
