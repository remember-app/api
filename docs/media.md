# Медиа: загрузка, галерея, кадр и лейблы

## Загрузка медиа — как это устроено

Байты в API **не приходят**. Приложение говорит «хочу загрузить», получает подписанные ссылки и
льёт файл прямо в хранилище, а потом сообщает, что закончило:

1. `POST /memories/:memoryId/media` — проверяются права и лимиты, заводится запись `media_items`
   в статусе `pending_upload`, в ответ — подписанные ссылки на куски (multipart).
2. Приложение шлёт `PUT` на каждую ссылку своим куском файла и запоминает заголовок `ETag`
   каждого ответа.
3. `POST /memories/:memoryId/media/:mediaId/complete` со списком кусков и их `ETag` — API
   собирает объект в хранилище, переводит запись в `processing`, двигает счётчики и ставит
   воркеру задачу `media_preview`.

Ссылки живут час (`R2_UPLOAD_TTL_SECONDS`). Протухли — `GET /memories/:memoryId/media/:mediaId/upload`
выдаёт новые **для той же записи и той же multipart-загрузки**: уже отправленные куски
остаются в хранилище, догрузка продолжается с места обрыва, а не начинается заново.

## `POST /memories/:memoryId/media`

За `app.authenticate` + `app.requireMembership`. Порог — `contributor`: `viewer` получает
`403 {"error":"forbidden"}` (матрица даёт ему смотреть, но не приносить).

```
{"kind": "photo", "size_bytes": 4194304, "captured_at": "2026-09-02T19:30:00+03:00"}
```

| Поле               | Обязательно     | Что это                                                     |
|--------------------|-----------------|--------------------------------------------------------------|
| `kind`             | да              | `photo` или `video`                                          |
| `size_bytes`       | да              | размер файла целиком; по нему считается число кусков          |
| `captured_at`      | нет             | момент съёмки из галереи, RFC 3339 со смещением; `null` — файл без даты |
| `duration_seconds` | **для видео**   | длительность; без неё видео не принять — нечем проверить лимит |
| `file_name`        | нет             | как файл называется на телефоне, до 255 символов; показывается в «Сведениях о кадре» |

`file_name` необязателен и останется таким: приложение начнёт его слать отдельной задачей, а всё
загруженное до того живёт без него. Хранится как пришло — его никто не разбирает, только
показывают; вырезается лишь NUL (его не держит ни одна `text`-колонка), пробелы по краям
срезаются, и пустая строка после этого — то же самое, что «не прислали».

```
201 Created
{"id":"…","status":"pending_upload",
 "upload":{"key":"originals/…","upload_id":"…","part_size":8388608,
           "parts":[{"part_number":1,"url":"http://…&X-Amz-Signature=…"}],
           "expires_at":"2026-09-03T12:00:00.000Z"}}
```

Файл режется на куски по `part_size`, кусок номер N уходит на `parts[N-1].url` методом `PUT`.
Ключ оригинала — по id записи, и он приходит в ответе: собирать его на клиенте не нужно.

Отказы по лимитам — до того, как что-либо записано: **записи и ключа в хранилище не остаётся**.

| Ответ | Тело                                                        | Когда                          |
|-------|-------------------------------------------------------------|--------------------------------|
| `413` | `{"error":"file is too large","limit_bytes":1073741824}`     | файл больше потолка            |
| `413` | `{"error":"video is too long","limit_seconds":300}`          | видео длиннее потолка          |
| `409` | `{"error":"memory is full","limit_files":1000}`              | в воспоминании больше нельзя файлов |
| `409` | `{"error":"memory is out of space","limit_bytes":10737418240}` | не хватает объёма            |
| `400` | `{"error":"duration_seconds is required for a video"}`       | видео без длительности         |
| `503` | `{"error":"storage not configured"}`                         | не заданы `R2_*`               |

Счётчики воспоминания двигаются в момент завершения загрузки, а не выдачи ссылки, поэтому пачка
загрузок «в полёте» может перебрать потолок на то, что летит. Следующая заявка тогда откажет.

## `GET /memories/:memoryId/media/:mediaId/upload`

За `app.authenticate` + `app.requireMembership`. Та же запись, та же multipart-загрузка, свежие
подписи. Тело — как у `POST` выше.

Новой записи не заводится и уже загруженные куски не теряются — это и есть докачка.

Чужая запись, запись из другого воспоминания, несуществующая и кривой `mediaId` — общий
`404 {"error":"not found"}`. Доделать загрузку может только тот, кто её начал: это не про роль, а
про владение. Запись, которая уже не `pending_upload`, — `409
{"error":"upload is already finished","status":"processing"}`.

## `POST /memories/:memoryId/media/:mediaId/complete`

За `app.authenticate` + `app.requireMembership`, та же проверка владения. Куски — все, что были
отправлены, с их `ETag` из ответов хранилища.

```
{"parts": [{"part_number": 1, "etag": "\"254a7725306413d2a8e39ad05ffa018a\""}]}
```

```
200 OK
{"id":"…","status":"processing","first_upload":true}
```

Внутри одной транзакции: запись переходит в `processing`, у воспоминания растут `storage_bytes` и
`media_count`, у загрузившего — строка `user_usage`, в `jobs` встаёт задача `media_preview`, и —
если он стоял в `not_started` или в `nothing` — его `contribution_status` переходит в
`more_coming`.

`first_upload` — это «переход из `not_started` только что случился»: по нему приложение задаёт
вопрос «всё загрузили или ещё будете?» (doc-06) и шлёт ответ в
`POST /memories/:memoryId/contribution-status`. Приходит в каждом ответе, `false` во всех
остальных случаях — второй загрузкой, повторным колбэком и статусами `more_coming` и `done`.

Сказал «ждать нечего» и всё-таки что-то залил — статус чинится сам (`nothing` → `more_coming`),
но вопрос не задаётся: `first_upload` остаётся `false`. Своё слово человек уже сказал, а ростер
организатора после этого перестаёт врать.

**Повторный вызов безопасен** — телефон, не дождавшийся ответа, зовёт снова и получает то же
самое: счётчики не сдвигаются второй раз, вторая задача не ставится и `first_upload` приходит
`false`. В ответе — текущий статус записи, каким бы он к тому моменту ни стал (воркер мог уже
увести её в `ready`).

Записывается **тот размер, который хранилище реально держит**, а не заявленный в первом шаге:
заявленный проверяется лимитами, но занизить его в счётчиках нельзя. Если объекта в хранилище
нет — `409 {"error":"the upload is not in storage"}`, запись остаётся `pending_upload`, и загрузку
можно доделать.

## `GET /memories/:memoryId/media`

За `app.authenticate` + `app.requireMembership`. Галерея воспоминания — **весь** материал, чей бы
он ни был. Читает её любой участник, `viewer` в том числе: матрица даёт ему «смотреть галерею».

```
200 OK
[{"id":"…","kind":"photo","status":"processing","uploaded_by":"…",
  "size_bytes":"4096","captured_at":"2026-09-02T16:30:00.000Z",
  "width":null,"height":null,"duration_seconds":null,"created_at":"…",
  "label_ids":["…","…"],
  "thumbnail_url":"http://…&X-Amz-Signature=…","preview_url":null,
  "screening_rejected":true,"screening_reason":"blur"}]
```

Порядок — **по времени съёмки**, а для файла без даты по времени загрузки: то же правило, по
которому воркер расставляет кадры в ролике (`architecture.md`, «Montage-пайплайн»), чтобы галерея
читалась в том же порядке, в каком ролик играет.

Записи в статусе `pending_upload` в список **не попадают** — байтов за ними ещё нет. `failed`
попадают: клиент рисует плейсхолдер и предлагает повторить.

Ссылки — только на **деривативы** и только подписанные, живут `R2_DOWNLOAD_TTL_SECONDS` (15 минут).
Пока воркер не сделал превью, `thumbnail_url` и `preview_url` — `null`; это не ошибка, а «ещё не
готово». Оригинал отсюда не отдаётся: галерея показывает лёгкую версию, а оригинал уходит только
тогда, когда его попросили, — двумя маршрутами `/download` ниже. Протухли — клиент просто
запрашивает список заново.

**Лейблы кадра** — `label_ids`: в каких коробках он лежит (doc-13). Только в тех, что **видны
спрашивающему**: общие лейблы воспоминания и его собственные личные. Чужой личный лейбл не
оставляет здесь следа — ни id, ни лишней длины массива. Кадр, не лежащий нигде, приходит с пустым
массивом. Состав и порядок галереи от лейблов не зависят вовсе, и кадр не дублируется, сколько бы
лейблов на нём ни было: это подзапрос-массив, а не join. Порядок внутри массива — тот же, что у
`GET /memories/:memoryId/labels`: сперва общие, внутри по названию. Отбирать галерею по лейблу
сервер не умеет и не должен: она приходит без параметров и фильтруется на телефоне.

**Автоматический отсев брака** (doc-03) приходит теми же двумя полями: `screening_rejected` —
отбраковал ли анализ этот кадр, `screening_reason` — почему (`unreadable`, `blur`, `exposure` и
что воркер научится видеть дальше; у оставленного кадра — `null`). Пишет их воркер, ровно как
`thumbnail_key`/`preview_key`, а API только отдаёт. Пока анализ до кадра не дошёл, оба поля —
`null`, и это «ещё не посчитано», а не «кадр годный»: `false` означало бы, что анализ посмотрел и
оставил. Это **предложение**, а не решение — организатор правит его перед заказом ролика, и на то,
какие кадры войдут в ролик, поля сами по себе не влияют: воркер при заказе судит каждый файл заново
тем же анализом. Предел длины ролика по ним при этом считается — отсеянное в него не идёт (см.
«Длина — число секунд в пределе воспоминания» у заказа).

Словарь причин — воркера (`projects/montage/screening.py`), здесь он только перечислен. `duplicate`
в это поле не приходит **никогда**: дубль определяется сравнением кадра с соседями, а не по нему
одному, и решается это при заказе ролика, а не на самой записи.

Не заданы `R2_*` — `503 {"error":"storage not configured"}`: подписать нечем, и список из одних
`null` был бы неправдой. Не участник, несуществующее воспоминание и кривой id — общий
`404 {"error":"not found"}`.

## `GET /memories/:memoryId/media/:mediaId`

За `app.authenticate` + `app.requireMembership`. Лист «Сведения о кадре» (doc-02, макет
`design/screens/SheetFrameInfo.html`) — всё про один кадр, чего не видно по самой картинке. Читает
любой участник, `viewer` в том числе: матрица даёт ему «смотреть галерею», а это один её кадр
словами.

```
200 OK
{"id":"…","file_name":"IMG_4471.HEIC","size_bytes":"4404019",
 "captured_at":"2026-09-13T18:47:00.000Z","created_at":"2026-09-15T09:12:00.000Z",
 "width":4032,"height":3024,
 "camera_model":"iPhone 15 Pro","focal_length_mm":24,"aperture":1.8,
 "latitude":55.518,"longitude":37.53,
 "uploaded_by":{"id":"…","username":"mark","name":"Марк Ковалёв","media_count":96},
 "montages":[{"id":"…","duration_seconds":90,"start_seconds":72.5}]}
```

Ссылок здесь нет и хранилище не спрашивается: лист открывается поверх кадра, который приложение уже
показывает, — миниатюра пришла с галереей. Поэтому `503` у этого маршрута не бывает.

| Поле                        | Что это                                                        |
|-----------------------------|----------------------------------------------------------------|
| `file_name`                 | имя файла с телефона; **ключа нет**, если имени нет             |
| `size_bytes`                | размер в байтах, строкой (bigint без округления)               |
| `captured_at`               | время съёмки; `null` — файл без даты                            |
| `created_at`                | когда кадр принесли                                            |
| `width`, `height`           | размеры в пикселях; `null`, пока воркер не измерил              |
| `camera_model`              | модель камеры: `iPhone 15 Pro`                                  |
| `focal_length_mm`           | фокусное расстояние в мм                                        |
| `aperture`                  | диафрагменное число: `1.8` — это «f/1.8»                        |
| `latitude`, `longitude`     | координаты съёмки                                               |
| `uploaded_by`               | кто принёс: `id`, `username`, `name` — и `media_count`          |
| `montages`                  | в каких готовых роликах кадр стоит и на какой секунде           |

`file_name` приходит, только если он есть: у кадров, загруженных до того, как приложение начало
слать имя, ключа в ответе просто нет — строка на экране не рисуется, и клиенту не приходится
отличать «имени нет» от пустого.

`uploaded_by.media_count` — сколько кадров этот человек принёс **в это воспоминание** («всего 96
кадров» на макете), а не всего в продукте: считаются те же записи, что показывает галерея, то есть
`pending_upload` не в счёт.

«Место» — это координаты, и только они. Названия («Усадьба «Остафьево»» на макете) здесь нет:
превратить координаты в название может только внешний геокодер, а это платный сервис и регистрация
— нужно ли продукту название, решает chief.

`montages` — только **готовые** ролики этого же воспоминания, новые сверху, как и в списке роликов.
`duration_seconds` там — длина самого ролика, `start_seconds` — секунда, на которой в нём стоит
этот кадр. Имени у ролика пока нет: шаблоны заводит веха Montage order, а до неё клиент собирает
«Ролик на 1:00» из длительности.

Кадр из другого воспоминания, несуществующий, `mediaId`, который вовсе не uuid, и запись в
`pending_upload` (байтов за ней ещё нет, и в галерее её тоже нет) — общий
`404 {"error":"not found"}`.

## Сведения о кадре — что пишет воркер

Камеру, место и раскладку по роликам API не вычисляет: их пишет **montage-воркер**
(`projects/montage`) — ровно так же, как он пишет `width`, `height` и `thumbnail_key`. Контракт
между репозиториями — имена таблиц и колонок.

`media_items` — таблица API, воркер обновляет в ней колонки:

| Колонка           | Тип                | Что это                                    |
|-------------------|--------------------|--------------------------------------------|
| `camera_model`    | `text`             | модель камеры из метаданных: `iPhone 15 Pro` |
| `focal_length_mm` | `double precision` | фокусное расстояние в мм: `24`             |
| `aperture`        | `double precision` | диафрагменное число: `1.8`                 |
| `latitude`        | `double precision` | широта съёмки                              |
| `longitude`       | `double precision` | долгота съёмки                             |

Готовой строкой «iPhone 15 Pro · 24 мм · f/1.8» это не хранится: единицы в ней — слова, и ставит их
приложение на языке читателя (`users.language`). Ничего не нашлось в файле — колонка остаётся
`null`, и для читателя это то же самое, что «воркер ещё не смотрел».

`montage_frames` — таблица API, воркер вставляет в неё строки, когда собирает ролик:

| Колонка            | Тип                         | Что это                              |
|--------------------|-----------------------------|--------------------------------------|
| `montage_id`       | `uuid NOT NULL`             | ролик, `montages.id`, каскад при удалении |
| `media_id`         | `uuid NOT NULL`             | кадр, `media_items.id`, каскад при удалении |
| `start_seconds`    | `double precision NOT NULL` | на какой секунде ролика кадр стоит   |
| `duration_seconds` | `double precision NOT NULL` | сколько секунд он в нём держится     |
| `created_at`       | `timestamptz NOT NULL`      | по умолчанию `now()`                 |

Первичный ключ — `(montage_id, media_id, start_seconds)`: один кадр может законно стоять в ролике
дважды (клип, разрезанный надвое; фотография, вернувшаяся в конце). Индекс
`montage_frames_media_idx (media_id)` — под единственный вопрос, который задаёт ей API: «в каких
роликах этот кадр». Пересобрал ролик — удали его строки и вставь новые; удалять ролик или кадр
руками не нужно, обе внешние ссылки каскадные.

Таблица одна на все вехи: это раскладка ролика, и второй её копии в чужом журнале быть не должно.
API в неё только читает — маршрутом выше («в каких роликах этот кадр») и журналом монтажа
(`files[].places`, «где этот кадр лёг в этом ролике»), и больше нигде.

## `GET /memories/:memoryId/media/:mediaId/download`

За `app.authenticate` + `app.requireMembership`. Подписанная ссылка на **оригинал** одного файла —
то самое «скачать». Порога по роли здесь нет: матрица даёт скачивать оригиналы каждому участнику,
`viewer` в том числе, и стоять в воспоминании — это всё, что проверяется.

```
200 OK
{"url":"http://…&X-Amz-Signature=…"}
```

Ссылка живёт `R2_DOWNLOAD_TTL_SECONDS` (15 минут) — тот же срок и по той же причине, что у ссылок
галереи: она не должна пережить членство того, кому её выдали. Протухла — клиент просит новую.
Байты идут из хранилища напрямую, API на их пути нет — ровно как при загрузке.

Записи в `pending_upload` отсюда не отдаются: байтов за ними ещё нет, подписывать нечего, а для
вызывающего это ровно «нет такой записи». Она, запись из другого воспоминания, несуществующая и
`mediaId`, который вовсе не uuid, — общий `404 {"error":"not found"}`. Не заданы `R2_*` — `503
{"error":"storage not configured"}`.

## `GET /memories/:memoryId/media/download`

Там же и с тем же порогом. Ссылки на оригиналы **всей** галереи одним ответом: клиент сохраняет
файлы сам, и просить ссылку по одной значило бы отдельный запрос на каждый файл.

```
200 OK
[{"id":"…","kind":"photo","url":"http://…&X-Amz-Signature=…"}]
```

Отбор и порядок — те же, что у `GET /memories/:memoryId/media`: `pending_upload` не попадает,
`failed` попадает (оригинал у него есть, не хватает только превью), сортировка по времени съёмки, а
для файла без даты по времени загрузки. Так скачанное на телефон ложится в том же порядке, в каком
лежало на экране. Пустая галерея — пустой массив, а не `404`.

Все ссылки списка подписаны в один момент и протухают вместе, через те же 15 минут: скачивание
стоит начинать сразу, а не откладывать, — на протухшие клиент запрашивает список заново, как и в
галерее. Отказы — те же, что у маршрута на один файл: `503` без `R2_*`, общий `404` от проверки
прав.

Два маршрута различаются одним сегментом — `/media/download` и `/media/:mediaId/download`. Роутер
предпочитает буквальный сегмент параметру, поэтому «вся галерея» не читается как запись с id
`download`; порядок объявления на это не влияет.

## `DELETE /memories/:memoryId/media/:mediaId`

Там же. Удаляет **тот, кто загрузил** — это владение, а не роль, — и `organizer`, которому матрица
даёт любое медиа:

| Кто                        | Что                                    |
|----------------------------|----------------------------------------|
| загрузивший (любой роли)   | `200 {"ok":true}`                      |
| `organizer`                | `200 {"ok":true}` на любое медиа       |
| участник, но не тот и не он| `403 {"error":"forbidden"}`            |

Поэтому `viewer` может удалить своё (если оно у него есть), а `contributor` не может удалить
соседское. Нет такой записи, запись из другого воспоминания и `mediaId`, который вовсе не uuid, —
`404 {"error":"not found"}`, тем же телом, что и всё в этом семействе.

Если удаляемый кадр стоял обложкой воспоминания, обложка снимается сама: `memories.cover_media_id`
держит внешний ключ с `ON DELETE SET NULL`, поэтому правило живёт в базе, а не в маршруте — материал
уходит из воспоминания двумя путями (поштучно и вместе с ушедшим участником), и правило, записанное
в одном из них, второй однажды забудет. Само воспоминание при этом целое, только без обложки.

В одной транзакции: строка `media_items` пропадает, `storage_bytes` и `media_count` воспоминания
уменьшаются, `user_usage` загрузившего — тоже, задача `media_preview` снимается с очереди. Оригинал
и деривативы уходят из хранилища **после** коммита — про порядок и про то, что бывает, если
хранилище не ответило, см. «Материал уходит вместе с человеком» в `docs/memories.md`.

Запись, которая так и не догрузилась (`pending_upload`), счётчиков не двигала — значит и при
удалении они не двигаются. Иначе счётчики ушли бы ниже факта.

## Лейблы — как это устроено

Лейбл (doc-13) — коробка с названием и цветом внутри одного воспоминания: участник раскладывает по
ним кадры. Лейбл **общий** — его видят все участники — или **личный**, и тогда его не видит никто,
кроме хозяина: ни названия, ни состава, ни следа в галерее. Один кадр лежит в нескольких лейблах
сразу, в одном и том же — один раз; кадр при этом не копируется и из воспоминания никуда не
девается. Прав лейбл не даёт и не отнимает: положить в свою коробку чужой кадр можно, и это не
делает его твоим — удаление кадра живёт по своему правилу (`DELETE
/memories/:memoryId/media/:mediaId`).

Цвет — **номер ячейки палитры, 1–8**, а не краска: восемь цветов держит клиент
(`design/screens/SheetLabelNew.html`), и светлая тема перекрашивает их у себя, ничего не спрашивая
у базы. Уникальности названий нет: на воспоминание она выдавала бы чужие личные названия («занято»
— это ответ о том, чего спрашивающий видеть не должен), а тёзки ничему не мешают — лейбл
различается по id.

Две таблицы: `labels` (воспоминание, хозяин, название, цвет, общий ли) и `label_media` (связь
кадра с лейблом, с подписью — кто положил). У связи есть и `memory_id`, и он там не для красоты:
на нём висят два составных внешних ключа, и вдвоём они и есть «лейбл не выходит за своё
воспоминание» — не обещание маршрута, а то, чего база просто не даст записать. Тем же каскадом
удалённый кадр — поштучно или уходом участника — **сам** пропадает из всех лейблов, и в коде
удаления на это нет ни строки. Сам лейбл при этом остаётся.

Подпись «кто положил» (`added_by`) — записанный факт, и только: прав она не даёт, правило ниже её
не спрашивает. Уйдёт человек — связь остаётся, и кадр из чужой коробки не выпадает; не станет самой
учётной записи — забудется только подпись.

**Кадры кладут и убирают пачкой.** В режиме выбора человек отмечает несколько кадров и кладёт их
одним запросом; повторный тап по той же строке листа их оттуда убирает. Предел пачки — **файловый
предел воспоминания** (`MEMORY_MAX_FILES`, по умолчанию 1000): пачка длиннее, чем воспоминание
вмещает файлов, называет что-то дважды или является мусором. Уже лежащий кадр в пачке — не ошибка
и не дубль; кадр соседнего воспоминания, несуществующий и ещё не долетевший (`pending_upload`) —
отказ всей пачке, с именами, и ничего не кладётся наполовину.

### Кто что может (decision-12)

Решение человека: «права на лейбл общие — могу изменять все, личные только человек», и про
зрителя — «заводить не даём — у него только просмотр». Общий лейбл общий для всех участников,
личный — только хозяина. В коде правило **одной функцией** (`labelDenial` в
`src/media/labels.ts`), и спрашивают её все: и маршруты записи, и поля `can_edit`/`can_add_media`
в списке.

| Что делают                             | Общий лейбл                                   | Личный лейбл |
|----------------------------------------|-----------------------------------------------|--------------|
| завести                                | любой участник, кроме `viewer`                | любой участник, `viewer` тоже |
| положить кадры                         | любой участник, `viewer` тоже                 | хозяин       |
| убрать кадры                           | любой участник, `viewer` тоже, кто бы кадр ни положил | хозяин |
| переименовать, перекрасить, удалить    | любой участник, `viewer` тоже                 | хозяин       |

Ни создатель общего лейбла, ни организатор здесь ничем не выделены. Зритель (`viewer`) правит и
наполняет общие лейблы наравне со всеми и заводит себе личные, но завести общий не может — `403
{"error":"forbidden"}`, так решил человек. **Чужой личный лейбл на любую запись — `404
{"error":"not found"}`, как будто его нет, организатору тоже:** «нельзя» было бы ответом о том,
что он существует.

**Ушёл участник или его исключили:** личные лейблы этого воспоминания уходят вместе с ним — их всё
равно никто больше не видел, — а общие остаются стоять, и хозяином им становится организатор. Всё
это в той же транзакции, что и строка `memory_members`. Кадры живут по своему правилу: принесённые
ушедшим удаляются и пропадают из всех коробок каскадом, чужие кадры в его коробках остаются лежать
в галерее.

## `GET /memories/:memoryId/labels`

За `app.authenticate` + `app.requireMembership`. Лейблы воспоминания глазами спрашивающего: общие
и его собственные личные. Читает любой участник, `viewer` в том числе — свои коробки есть у
каждого, кто стоит в воспоминании.

```
200 OK
[{"id":"…","title":"Лучшее","color":1,"shared":true,"mine":true,
  "can_edit":true,"can_add_media":true,"media_count":23},
 {"id":"…","title":"Любимые","color":6,"shared":false,"mine":true,
  "can_edit":true,"can_add_media":true,"media_count":9}]
```

`shared` — общий или личный, `mine` — завёл ли его спрашивающий, `media_count` — сколько кадров в
коробке лежит. Число считается по связям, поэтому оно всегда равно тому, что в ней есть на самом
деле.

`can_edit` (переименовать, перекрасить, удалить) и `can_add_media` (положить кадры) — **что
спрашивающему можно с этим лейблом**, по тому же правилу прав, по которому отказывают маршруты
записи. Считает их та же функция, поэтому приложению не нужно повторять правило у себя: кнопки
правки рисуются там, где сервер сказал «можно». И это не то же самое, что `mine` — общий лейбл
правит и наполняет любой участник, а не только тот, кто его завёл.

**Чужих личных лейблов в ответе нет ни в каком виде** — ни строкой, ни в подсчётах: их не видно
и из соседнего ответа не вычислить, потому что запрос их попросту не читает. Это закреплено
автотестом снаружи, через HTTP (`src/media/labels.test.ts`).

Порядок — сперва общие, внутри по названию, тёзки по id: ровно так лист «В лейбл» и разложен на
две группы (`design/screens/SheetLabels.html`). Тот же порядок у `label_ids` в галерее, чтобы
клиенту не пришлось пересортировывать одно под другое.

Лейблов нет — пустой массив, а не `404`. Не участник, несуществующее воспоминание и кривой id —
общий `404 {"error":"not found"}`.

## `POST /memories/:memoryId/labels`

За `app.authenticate` + `app.requireMembership`. «Новый лейбл»
(`design/screens/SheetLabelNew.html`) — и сразу с отмеченными кадрами, если его заводят из режима
выбора: кнопка там так и называется, «Создать и положить 4 кадра».

```
POST /memories/:memoryId/labels
{"title":"Лучшее","color":1,"shared":true,"media_ids":["…","…"]}

201 Created
{"id":"…","title":"Лучшее","color":1,"shared":true,"mine":true,
 "can_edit":true,"can_add_media":true,"media_count":2}
```

Отвечает строкой списка — той же, что придёт в `GET …/labels`: лист, с которого лейбл завели,
вставляет её себе, ничего не переспрашивая.

`title` — обязательное, непустое (одни пробелы не название), до 100 символов, края обрезаются.
`color` — номер ячейки палитры, целое от 1 до 8. `shared` — обязательное: общий лейбл или личный,
и **после создания это не меняется**. `media_ids` — необязательная пачка; лейбл и его кадры
появляются вместе или не появляются вовсе (одна транзакция).

| Код   | Тело                                                          | Когда |
|-------|---------------------------------------------------------------|-------|
| `400` | стандартная ошибка валидации Fastify                           | пустое название, длиннее предела, цвет вне 1–8, не сказан `shared`, пачка пустая или с повторами |
| `400` | `{"error":"no such media in this memory","media_ids":["…"]}`   | в пачке кадр соседнего воспоминания, несуществующий или ещё не долетевший |
| `403` | `{"error":"forbidden"}`                                        | `viewer` заводит общий лейбл |

## `PATCH /memories/:memoryId/labels/:labelId`

Переименовать и перекрасить. Присылается то, что человек тронул; чего нет в теле, то остаётся как
было. Отвечает той же строкой списка.

```
PATCH /memories/:memoryId/labels/:labelId
{"title":"Смешное","color":4}

200 OK
{"id":"…","title":"Смешное","color":4,"shared":true,"mine":true,
 "can_edit":true,"can_add_media":true,"media_count":2}
```

Пустое тело — `400`: это не правка, и `200` сказал бы, что она была. `shared` у этого маршрута
нет вовсе — присланный, он молча отбрасывается (ajv у Fastify работает с `removeAdditional`), и
лейбл остаётся каким был: общий ↔ личный после создания не переключается, макет этого не рисует, а
перевод общего в личный спрятал бы от всех чужие кадры, которые в нём лежат.

## `DELETE /memories/:memoryId/labels/:labelId`

Удалить коробку — `200 {"ok":true}`. Связи уходят с ней каскадом, **кадры не трогаются**: они
лежат в воспоминании и в галерее ровно там же, где лежали, и галерея от этого не меняется ничем,
кроме опустевшего `label_ids`.

## `POST /memories/:memoryId/labels/:labelId/media`

Положить пачку в коробку. Отвечает строкой списка с новым `media_count`.

```
POST /memories/:memoryId/labels/:labelId/media
{"media_ids":["…","…"]}

200 OK
{"id":"…","title":"Лучшее","color":1,"shared":true,"mine":false,
 "can_edit":true,"can_add_media":true,"media_count":5}
```

Уже лежащий кадр — не ошибка и не дубль. Чужой кадр положить можно: он не становится твоим и прав
на него не меняет. Кадр соседнего воспоминания, несуществующий и ещё не долетевший — `400
{"error":"no such media in this memory","media_ids":["…"]}` на всю пачку, и ничего не кладётся
наполовину.

## `DELETE /memories/:memoryId/labels/:labelId/media`

Убрать пачку из коробки — тело то же, `{"media_ids":[…]}`, ответ тот же. Убирают **из лейбла, а не
из воспоминания**: кадры остаются в галерее на своих местах. Кадра, которого в коробке и не было,
это не касается — убирать нечего, и это не ошибка.

Кто что может — таблица выше. Право одно на весь лейбл, а не на каждый кадр: кому можно убирать из
этого лейбла, тот убирает любой кадр в нём, кто бы его ни положил.
