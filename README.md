# remember-api

Бэкенд-API продукта **Remember** — единственная точка входа для мобильного приложения.
TypeScript + [Fastify](https://fastify.dev/) + Postgres.

Сейчас здесь скелет (m-7 Foundation) и аккаунт целиком (m-3 Accounts): health-эндпоинт,
подключение к базе, миграции, аутентификация запроса, ник и управление сессиями. Остальные
сущности приходят со своими фичами.

Продуктовая плоскость и архитектурные решения — в корневом репозитории (`backlog/`,
`architecture.md`).

## Требования

- Node.js **≥ 22.18** (TypeScript выполняется движком напрямую, шага сборки нет).
- Docker — для локального Postgres.

## Запуск с чистой машины

```bash
npm install

# 1. Поднять локальный Postgres 16 на localhost:5432
docker compose up -d --wait

# 2. Задать окружение
cp .env.example .env

# 3. Накатить миграции
npm run migrate

# 4. Запустить сервер
npm run dev

# 5. Проверить
curl -i http://localhost:3000/health
# HTTP/1.1 200 OK
# content-type: application/json; charset=utf-8
# {"status":"ok"}
```

Тесты (интеграционные, против той же локальной базы; миграции накатываются сами, шагом
`pretest`, поэтому поднятый Postgres обязателен):

```bash
npm test
```

⚠️ `npm test` накатывает миграции и пишет в ту базу, на которую смотрит `DATABASE_URL`. Не
запускайте его с `.env`, направленным куда-либо кроме локальной базы.

## Локальный Postgres

`docker-compose.yml` в этом репозитории — **канонная локальная база всего продукта**: на неё
смотрят и `api`, и `montage`. Не поднимайте себе вторую.

```bash
docker compose up -d --wait   # поднять и дождаться готовности
docker compose down           # остановить (данные остаются в volume)
docker compose down -v        # остановить и стереть данные
```

Postgres 16, `localhost:5432`, база / пользователь / пароль — `remember` / `remember` / `remember`,
то есть:

```
DATABASE_URL=postgres://remember:remember@localhost:5432/remember
```

## Окружение

Одна обязательная переменная. Сервер и мигратор падают сразу, если её нет. Всё остальное имеет
значение по умолчанию — для загрузки не нужно ничего, кроме `DATABASE_URL`.

| Переменная                         | Обязательна | По умолчанию | Что это                                   |
|------------------------------------|-------------|--------------|-------------------------------------------|
| `DATABASE_URL`                     | да          | —            | строка подключения к Postgres             |
| `PORT`                             | нет         | `3000`       | порт HTTP-сервера                         |
| `SESSION_TTL_DAYS`                 | нет         | `30`         | срок жизни сессии                         |
| `EMAIL_LOGIN_TTL_MINUTES`          | нет         | `15`         | срок жизни ссылки входа                   |
| `EMAIL_LOGIN_RATE_MAX`             | нет         | `5`          | заявок на вход за окно — на один ящик     |
| `EMAIL_LOGIN_RATE_MAX_PER_IP`      | нет         | `50`         | то же на один IP — грубый заслон          |
| `EMAIL_LOGIN_RATE_WINDOW_MINUTES`  | нет         | `15`         | длина этого окна                          |
| `APPLE_CLIENT_ID`                  | нет         | —            | наш client id у Apple — `aud` id-токена   |
| `GOOGLE_CLIENT_ID`                 | нет         | —            | то же у Google                            |

У `APPLE_CLIENT_ID` и `GOOGLE_CLIENT_ID` значения по умолчанию нет и быть не может: не задан
(или пустой — это та же опечатка) — значит провайдер выключен, и его эндпоинт отвечает `501`.
Пустая строка в роли `aud` сняла бы проверку аудитории вовсе, то есть приняла бы токен, выписанный
для чужого приложения.

Числовые значения проверяются: не число, ноль или отрицательное — это опечатка, а не намерение,
поэтому берётся значение по умолчанию. Иначе `EMAIL_LOGIN_RATE_WINDOW_MINUTES=-15` молча снял бы
ограничение частоты с единственного неавторизованного эндпоинта.

Скрипты читают `.env` через встроенный `--env-file-if-exists` — никакого `dotenv`.
Значения из окружения перекрывают файл. `.env` в git не попадает.

## Миграции

Инструмент — [postgrator](https://github.com/rickbergfalk/postgrator): обычные `.sql`-файлы,
никакого DSL, состояние в таблице `schema_migrations`.

```bash
npm run migrate
```

Файлы лежат в `migrations/` и называются `<версия>.<do|undo>.<имя>.sql`:

```
migrations/001.do.init.sql     # применить
migrations/001.undo.init.sql   # откатить
```

Новая миграция — следующий номер и пара `do`/`undo`. Postgrator считает md5 применённых файлов,
поэтому **применённую миграцию не редактируют** — добавляют следующую.

Файл целиком уходит в Postgres одним запросом, то есть выполняется как одна неявная транзакция:
упавшая на середине миграция не оставит половину схемы. Отметка о версии пишется отдельным
запросом следом — если процесс убить ровно между ними, миграция окажется накатанной, но не
записанной, и следующий прогон её повторит. Поэтому миграции пишем идемпотентными
(`IF NOT EXISTS`).

## API

### `GET /health`

Без авторизации. Контракт зафиксирован между репозиториями — мобильное приложение проверяет
ровно это, поэтому форма ответа не меняется:

```
200 OK
content-type: application/json; charset=utf-8

{"status":"ok"}
```

Тело — ровно `{"status":"ok"}`. Content-type Fastify всегда отдаёт с `; charset=utf-8` и убрать
его без onSend-хука нельзя, поэтому клиент сверяет заголовок **по префиксу**, а не на равенство.

Это liveness-проба: она отвечает `ok`, пока жив процесс, и ничего не говорит о базе. Связь с
Postgres проверяется один раз на старте — сервер не поднимется, если база недоступна.

### `POST /auth/email/start`

Без авторизации. Тело — `{"email": "..."}`. Заводит пользователя, если такого адреса ещё не
видели, и выпускает одноразовую ссылку входа.

```
200 OK
{"ok":true}
```

Ответ **одинаков** и для нового адреса, и для известного: иначе эндпоинт отвечал бы на вопрос
«этот человек у вас зарегистрирован?». Придушен по частоте за окно
`EMAIL_LOGIN_RATE_WINDOW_MINUTES`: отдельно на ящик (`EMAIL_LOGIN_RATE_MAX`, `+tag` не считается
за новый адрес) и отдельно, куда мягче, на IP (`EMAIL_LOGIN_RATE_MAX_PER_IP` — за одним адресом
сидит целый офис). Сверх лимита — `429 {"error":"too many requests"}`. Кривой адрес — `400`
в стандартной форме Fastify (`FST_ERR_VALIDATION`).

### `POST /auth/email/verify`

Без авторизации. Тело — `{"token": "..."}` (токен из ссылки). Гасит токен и открывает сессию.

```
200 OK
{"token":"<токен сессии>","user":{"id":"…","username":null,"name":null,"email":"…"}}
```

Токен ссылки одноразовый: он исчезает в тот же момент, а не просто протухает потом. Повтор с
тем же токеном — `401 {"error":"invalid or expired token"}`, как и для чужого или просроченного.

### `POST /auth/apple`, `POST /auth/google`

Без авторизации. Тело — `{"idToken": "<id-токен от провайдера>"}`: приложение уже получило его
нативным SDK, сервер сам с провайдером не общается. Проверяются подпись по JWKS провайдера, `iss`,
`aud` (`APPLE_CLIENT_ID` / `GOOGLE_CLIENT_ID`) и `exp` — это `jose`. Ответ — ровно как у
`/auth/email/verify`:

```
200 OK
{"token":"<токен сессии>","user":{"id":"…","username":null,"name":"…","email":"…"}}
```

Пользователь заводится при первой встрече пары (провайдер, `sub`); `name` и `email` берутся из
токена, если он их несёт, иначе `null` — Apple имени не присылает, а адрес может быть скрытым
релеем. Токен не прошёл проверку любым способом (подпись, `aud`, `iss`, `exp`, не JWT) —
`401 {"error":"invalid token"}`, одинаково для всех причин: разница в ответе подсказывала бы, что
подделать. Провайдер без client id выключен — `501 {"error":"provider not configured"}`.

### `GET /me`

За `app.authenticate`. Отдаёт текущего пользователя — то же, что лежит в `request.user`:

```
200 OK
{"id":"…","username":null,"name":null,"email":"…"}
```

### `POST /me/username`

За `app.authenticate`. Тело — `{"username": "..."}`. Занимает ник, если его ещё нет, и меняет,
если есть, — это один и тот же запрос: прежний ник нигде не хранится и освобождается сразу.
Отвечает обновлённым пользователем, **ровно в форме `GET /me`**:

```
200 OK
{"id":"…","username":"kubik","name":null,"email":"…"}
```

Правила ника:

| Что                | Как                                                             |
|--------------------|-----------------------------------------------------------------|
| Набор знаков       | латинские буквы, цифры и разделители `_` `.` `-`                |
| Длина              | 3–30                                                            |
| Края               | разделитель не может стоять первым или последним знаком         |
| Регистр            | хранится как введён, но уникальность — регистронезависимая      |

Латиница намеренно: ник — это то, чем один человек указывает на другого при приглашении, а
кириллическая `а` неотличима от латинской `a`. `citext` сводит регистр, но не алфавиты, поэтому
Unicode-ник был бы готовым инструментом выдать себя за кого угодно.

Ник занят кем-то другим (в любом регистре) — `409 {"error":"username taken"}`. Сменить регистр
**своего** ника (`foo` → `Foo`) можно: это та же строка в базе. Не подходит под правила выше —
`400` в стандартной форме Fastify.

### `GET /users?username=<ник>`

За `app.authenticate`. Поиск человека по нику, чтобы пригласить его в воспоминание. Совпадение
**точное** и регистронезависимое; префиксного и нечёткого поиска нет и в MVP не будет — иначе это
превращается в справочник всех пользователей.

```
200 OK
{"id":"…","username":"kubik","name":null}
```

Три поля и ни одного больше: ник можно подобрать, поэтому он не должен быть способом вытащить
чужой email. Никто такой ник не держит — `404 {"error":"not found"}`.

Запрос сначала проверяется тем же правилом, каким проверяется занятие ника, и всё, что под него
не подходит, — сразу `404`. Это не придирка: `citext` сводит регистр через `lower()` базы, а тот
отображает `İ` на `i` и `U+212A KELVIN SIGN` на `k`, так что незачищенный запрос `KUBİK` достал
бы настоящую строку `kubik`. Занять ник с такими знаками нельзя (только латиница), значит и найти
по ним нельзя — иначе «точное совпадение» было бы неправдой. Заодно это не пускает в базу
нулевой байт, который она сравнивать не умеет и отвечала на него `500`.

`400` здесь означает ровно одно — параметр `username` не передан вовсе.

### `GET /auth/sessions`

За `app.authenticate`. Живые сессии текущего пользователя — не отозванные и не протухшие,
свежая первой. `current` помечает ту, которой сделан этот самый запрос:

```
200 OK
[{"id":"…","created_at":"2026-09-02T…","expires_at":"2026-10-02T…","current":true}]
```

Список — голый массив: это перечень и ничего кроме. Чужие сессии в него не попадают.

`current` помечает **не больше одной** строки (`token_hash` уникален), но клиенту стоит держать
в уме и ноль: если ровно в этот момент текущую сессию погасили с другого устройства, она выпадет
из выборки живых. Это самолечится — следующий запрос этим токеном получит `401`.

### `POST /auth/sessions/:id/revoke`

За `app.authenticate`. Гасит одну **свою** сессию по id — «выйти на том телефоне».

```
200 OK
{"ok":true}
```

Чужой или несуществующий id — `404 {"error":"not found"}`, одинаково: иначе эндпоинт отвечал бы
на вопрос «существует ли такая сессия?». Повторный отзыв — тоже `200`, результат тот же. `id` не
uuid — `400`; форма `urn:uuid:…` тоже `400`, хотя ajv её за uuid считает, — Postgres не считает.

⚠️ Оба эндпоинта отзыва тела **не принимают**. Не ставьте на них `Content-Type: application/json`
с пустым телом: Fastify отвечает на это `400 FST_ERR_CTP_EMPTY_JSON_BODY` до всякой логики.
Либо не шлите заголовок, либо шлите телом `{}`.

### `POST /auth/logout`

За `app.authenticate`. Гасит ту сессию, чьим токеном сделан запрос. Остальные сессии
пользователя живы.

```
200 OK
{"ok":true}
```

После этого тот же токен получает `401` на любом маршруте — в том числе на повторном
`/auth/logout`. Тела не принимает — про пустой `Content-Type: application/json` см. выше.

## Аутентификация

Своя, по модели данных из `architecture.md`. Сессия — непрозрачный случайный токен (32 байта из
`node:crypto`), в базе только его SHA-256. Транспорт — заголовок `Authorization: Bearer <токен>`:
клиент нативный, куки и CSRF не нужны. Провайдеров в MVP три — ссылка на email, Apple и Google, —
и все три кончаются одним и тем же: строкой в `auth_identities` и сессией из `src/auth/session.ts`.

Аккаунты **не** сращиваются по совпадению email: первая встреча пары (провайдер, id у провайдера)
заводит нового пользователя. У Apple адрес бывает скрытым релеем — он меняется и может быть выдан
другому человеку, так что склейка по нему рано или поздно пустила бы одного в аккаунт другого.

Apple и Google проверяются через `jose` (`src/auth/providers.ts`): `createRemoteJWKSet` держит
ключи провайдера с их ротацией, `jwtVerify` сверяет подпись, `iss`, `aud` и `exp`. Руками из
токена берётся только `sub` — им и связывают, — плюс `name` и `email`, если они там есть.

### Как повесить проверку сессии

`app.authenticate` — готовый `preHandler`. Он сидит на корневом инстансе, поэтому доступен в любом
маршруте и импортировать нечего:

```ts
app.get("/memories", { preHandler: app.authenticate }, async (request) => {
  return listMemoriesOf(request.user.id);
});
```

Что он делает: читает `Authorization: Bearer <токен>` (схема регистронезависима), считает SHA-256,
ищет сессию без `revoked_at` и с непрошедшим `expires_at`. Нашёл — кладёт пользователя в
`request.user` и пускает дальше. Не нашёл — заголовка нет, схема другая, токен чужой, протухший
или отозванный — **сам** отвечает `401 {"error":"unauthorized"}`, и хендлер не вызывается.

`request.user` — ровно четыре поля и ничего больше:

| Поле       | Тип              | Что это                                        |
|------------|------------------|------------------------------------------------|
| `id`       | `string` (uuid)  | стабильная ссылка на человека — ссылайтесь на неё |
| `username` | `string \| null` | ник; `null`, пока человек его не занял         |
| `name`     | `string \| null` | имя                                            |
| `email`    | `string \| null` | адрес, с которым вошли                         |

Тип объявлен на `FastifyRequest` как всегда присутствующий — так удобнее в защищённом хендлере,
но заполняется он **только** за `app.authenticate`. На маршруте без этого `preHandler` там
`undefined`, и TypeScript об этом не предупредит.

### Как добыть токен в разработке

Почтового сервиса в MVP нет — ссылка печатается в лог API:

```bash
curl -X POST http://localhost:3000/auth/email/start \
  -H 'content-type: application/json' -d '{"email":"you@example.com"}'
```

В логе появляется строка `magic link issued`:

```
{"level":30,…,"email":"you@example.com","link":"remember://auth/email?token=GuYNXVEl…","msg":"magic link issued"}
```

Дальше либо открыть ссылку на симуляторе (схема `remember://` в приложении уже настроена):

```bash
xcrun simctl openurl booted "remember://auth/email?token=GuYNXVEl…"
```

либо обменять токен на сессию руками:

```bash
curl -X POST http://localhost:3000/auth/email/verify \
  -H 'content-type: application/json' -d '{"token":"GuYNXVEl…"}'
# {"token":"42HDiF7t…","user":{…}}

curl http://localhost:3000/me -H "Authorization: Bearer 42HDiF7t…"
```

### Ошибки

Свои отказы эндпоинты отдают как `{"error": "…"}`. Отказы, которые формирует сам Fastify
(валидация тела, неизвестный маршрут), приходят в его стандартной форме — `statusCode`, `code`,
`error`, `message`.

Всё, что упало на сервере, наружу уходит как `500 {"error":"internal"}`, а настоящая ошибка
пишется в лог: иначе отвалившаяся база отвечала бы постороннему своим SQLSTATE и текстом запроса.

### Отзыв сессий

`src/auth/session.ts`: `revoke(sessionId)` гасит одну сессию по id, `revokeByToken(token)` — ту,
которой сейчас пользуются (это и есть выход из аккаунта). Отзыв проставляет `revoked_at`, строка
остаётся; `app.authenticate` перестаёт её принимать сразу.

Наружу это выведено как `GET /auth/sessions`, `POST /auth/sessions/:id/revoke` и
`POST /auth/logout`. `revoke(sessionId)` про владельца ничего не знает — принадлежность сессии
проверяет маршрут, до вызова.

Свой токен можно достать из заголовка тем же способом, каким его читает проверка сессии:
`bearerToken(request.headers.authorization)` из того же модуля. Разбор заголовка живёт в одном
месте, чтобы «какая из этих сессий — текущая» и `app.authenticate` не разошлись.

## Устройство

```
src/app.ts            Fastify-приложение и маршруты (без сети — тестируется через inject)
src/server.ts         точка входа: проверить базу, слушать порт
src/db.ts             клиент Postgres из DATABASE_URL
src/auth/session.ts   выпуск, проверка и отзыв сессий
src/auth/email.ts     вход по ссылке на email
src/auth/providers.ts проверка id-токенов Apple и Google (jose, JWKS)
src/auth/social.ts    маршруты входа через Apple и Google
src/auth/plugin.ts    декоратор app.authenticate и маршруты входа
src/auth/identity.ts  ник, поиск по нику, список и отзыв сессий
src/auth/config.ts    сроки и лимиты из окружения, с проверкой значений
src/auth/testing.ts   общая оснастка тестов (приложение с логом, вход, уборка)
scripts/migrate.ts    запуск postgrator
migrations/           .sql-миграции
```

`authPlugin` вызывается из `buildApp` напрямую, а не через `app.register`: Fastify инкапсулирует
плагины, и `authenticate`, объявленный внутри зарегистрированного, снаружи был бы не виден.

Шага сборки нет: Node исполняет `.ts` напрямую, срезая типы. Значит, `enum`, `namespace` и
параметры-свойства конструктора не работают — `tsconfig.json` включает `erasableSyntaxOnly`,
так что `npm run typecheck` поймает это раньше рантайма.

Сервер слушает `0.0.0.0`, чтобы телефон или симулятор в той же сети мог до него достучаться.
