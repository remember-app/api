# remember-api

Бэкенд-API продукта **Remember** — единственная точка входа для мобильного приложения.
TypeScript + [Fastify](https://fastify.dev/) + Postgres.

Сейчас здесь скелет (m-7 Foundation), аккаунт целиком (m-3 Accounts), воспоминания с участниками
и медиа целиком: health-эндпоинт, подключение к базе, миграции, аутентификация запроса,
ник и управление сессиями, права на воспоминание, подписанные ссылки на загрузку в хранилище,
галерея воспоминания, скачивание оригиналов — одного файла и всей галереи — и удаление медиа,
поштучно и каскадом при уходе участника. Остальные сущности приходят со своими фичами.

Продуктовая плоскость и архитектурные решения — в корневом репозитории (`backlog/`,
`architecture.md`).

## Требования

- Node.js **≥ 22.18** (TypeScript выполняется движком напрямую, шага сборки нет).
- Docker — для локального Postgres и локального хранилища (MinIO).

## Запуск с чистой машины

```bash
npm install

# 1. Поднять локальный Postgres 16 (localhost:5432) и MinIO (localhost:9000)
docker compose up -d --wait

# 2. Задать окружение
cp .env.example .env

# 3. Накатить миграции
npm run migrate

# 4. Запустить сервер
npm run dev

# 5. Проверить
curl -i http://localhost:3000/health
# HTTP/1.1 200 OK
# content-type: application/json; charset=utf-8
# {"status":"ok"}
```

Тесты (интеграционные, против той же локальной базы и того же локального хранилища; миграции
накатываются сами, шагом `pretest`, поэтому поднятые Postgres и MinIO обязательны):

```bash
npm test
```

⚠️ `npm test` накатывает миграции и пишет в ту базу, на которую смотрит `DATABASE_URL`. Не
запускайте его с `.env`, направленным куда-либо кроме локальной базы.

## Локальный Postgres

`docker-compose.yml` в этом репозитории — **канонная локальная база всего продукта**: на неё
смотрят и `api`, и `montage`. Не поднимайте себе вторую.

```bash
docker compose up -d --wait   # поднять и дождаться готовности
docker compose down           # остановить (данные остаются в volume)
docker compose down -v        # остановить и стереть данные
```

Postgres 16, `localhost:5432`, база / пользователь / пароль — `remember` / `remember` / `remember`,
то есть:

```
DATABASE_URL=postgres://remember:remember@localhost:5432/remember
```

## Локальное хранилище

Тот же `docker-compose.yml` поднимает **MinIO** — это локальная замена Cloudflare R2. Протокол
один и тот же (S3), поэтому код в `src/media/r2.ts` не знает, с кем говорит: меняются только
значения `R2_*` в окружении.

- API хранилища — `http://localhost:9000`, бакет `remember` (заводится сам при первом старте
  контейнера), ключ / секрет — `remember` / `remember-secret`.
- Веб-консоль — `http://localhost:9001`, вход теми же ключами. Через неё видно, что реально
  долетело в бакет.
- Данные лежат в volume `miniodata`; `docker compose down -v` стирает их вместе с базой.

Подписанные ссылки собираются из `R2_ENDPOINT` как есть, и телефон идёт по ним сам. С реального
устройства `localhost` — это оно само, поэтому там нужен IP машины в сети:
`R2_ENDPOINT=http://192.168.1.10:9000`. На симуляторе и эмуляторе `localhost` работает.

Боевой R2 — тот же набор переменных с другими значениями (`R2_ENDPOINT` вида
`https://<account>.r2.cloudflarestorage.com`, `R2_REGION=auto`). Бакет и ключи заводит человек,
в коде их нет.

## Окружение

Одна обязательная переменная. Сервер и мигратор падают сразу, если её нет. Всё остальное имеет
значение по умолчанию — для загрузки не нужно ничего, кроме `DATABASE_URL`.

| Переменная                         | Обязательна | По умолчанию | Что это                                   |
|------------------------------------|-------------|--------------|-------------------------------------------|
| `DATABASE_URL`                     | да          | —            | строка подключения к Postgres             |
| `PORT`                             | нет         | `3000`       | порт HTTP-сервера                         |
| `SESSION_TTL_DAYS`                 | нет         | `30`         | срок жизни сессии                         |
| `EMAIL_LOGIN_TTL_MINUTES`          | нет         | `15`         | срок жизни ссылки входа                   |
| `EMAIL_LOGIN_RATE_MAX`             | нет         | `5`          | заявок на вход за окно — на один ящик     |
| `EMAIL_LOGIN_RATE_MAX_PER_IP`      | нет         | `50`         | то же на один IP — грубый заслон          |
| `EMAIL_LOGIN_RATE_WINDOW_MINUTES`  | нет         | `15`         | длина этого окна                          |
| `RESEND_API_KEY`                   | для входа по email | —     | ключ API Resend, которым уходит письмо со ссылкой |
| `MAIL_FROM`                        | для входа по email | —     | адрес отправителя, вида `Remember <no-reply@…>` |
| `RESEND_API_URL`                   | нет         | `https://api.resend.com/emails` | куда уходит письмо; переопределяется для тестов |
| `APPLE_CLIENT_ID`                  | нет         | —            | наш client id у Apple — `aud` id-токена   |
| `GOOGLE_CLIENT_ID`                 | нет         | —            | то же у Google                            |
| `EXPO_PUSH_URL`                    | нет         | `https://exp.host/--/api/v2/push/send` | куда уходят пуши; пустая строка — пуши выключены |
| `R2_ENDPOINT`                      | для загрузки | —           | адрес S3-совместимого хранилища           |
| `R2_BUCKET`                        | для загрузки | —           | бакет, куда кладутся оригиналы            |
| `R2_ACCESS_KEY_ID`                 | для загрузки | —           | ключ доступа                              |
| `R2_SECRET_ACCESS_KEY`             | для загрузки | —           | секрет                                    |
| `R2_REGION`                        | нет         | `auto`       | у R2 — всегда `auto`, у MinIO своя        |
| `R2_UPLOAD_TTL_SECONDS`            | нет         | `3600`       | сколько живёт подписанная ссылка на загрузку |
| `R2_DOWNLOAD_TTL_SECONDS`          | нет         | `900`        | то же для ссылки на просмотр и скачивание |
| `MEDIA_UPLOAD_PART_BYTES`          | нет         | `8388608`    | размер куска multipart-загрузки (8 МиБ)   |
| `MEDIA_MAX_FILE_BYTES`             | нет         | `1073741824` | потолок на один файл (1 ГиБ)              |
| `MEDIA_MAX_VIDEO_SECONDS`          | нет         | `300`        | потолок на длительность видео (5 мин)     |
| `MEMORY_MAX_STORAGE_BYTES`         | нет         | `10737418240`| потолок объёма на воспоминание (10 ГиБ)   |
| `MEMORY_MAX_FILES`                 | нет         | `1000`       | потолок числа файлов на воспоминание      |
| `MONTAGE_TARGET_SECONDS`           | нет         | `60`         | длина ролика, если заказчик её не назвал  |
| `MONTAGE_TARGET_SECONDS_MIN`       | нет         | `15`         | короче этого ролик не заказать            |
| `MONTAGE_TARGET_SECONDS_MAX`       | нет         | `300`        | длиннее — тоже                            |
| `INTERNAL_WORKER_TOKEN`            | для пуша «ролик готов» | —  | общий секрет, которым montage-воркер стучится в `/internal/*` |
| `MONTAGE_SCHEMA_SQL`               | нет         | `../montage/schema.sql` | откуда берётся таблица `jobs` — см. «Миграции» |

Четыре `R2_*` без значения по умолчанию работают как пара client id: не заданы (или пустые) —
хранилища нет, и эндпоинты загрузки честно отвечают `503 {"error":"storage not configured"}`
вместо того, чтобы делать вид, что виноват клиент. Всё остальное работает и без них.

`RESEND_API_KEY` и `MAIL_FROM` — то же правило для почты: нет обоих (или пустые) — письмо слать
нечем, и `POST /auth/email/start` отвечает `503 {"error":"mail not configured"}`. Сервис при этом
поднимается как обычно: вход по Apple и Google, сессии и всё остальное почты не касаются. Ключ
заводит человек в [Resend](https://resend.com), в коде его нет; отправитель должен быть на домене,
подтверждённом в Resend, иначе провайдер откажет.

Лимиты — предложенные числа из `architecture.md` («Лимиты»). Они в окружении, а не в коде,
потому что их будут двигать, когда придёт настоящий материал, и админки для этого нет. Границы
длины ролика читаются один раз, при сборке приложения: ajv компилирует схему тела запроса заранее,
так что переменную нужно задать до старта, а не менять на живом процессе.

`INTERNAL_WORKER_TOKEN` — единственный ключ от `/internal/*`, куда стучится montage-воркер. Не
задан (или пустой) — маршрут закрыт для всех, и любой стук получает `401`: незаданный секрет это
«вход заперт», а не «вход свободен». Значение кладут в окружение обоих сервисов, и оно должно
совпадать до символа. Придумывать его руками не нужно и не стоит: маршрут висит на том же открытом
наружу порту, что и все остальные, и частота стуков ничем не ограничена — значит секрет должен быть
случайным: `openssl rand -base64 32`.

У `APPLE_CLIENT_ID` и `GOOGLE_CLIENT_ID` значения по умолчанию нет и быть не может: не задан
(или пустой — это та же опечатка) — значит провайдер выключен, и его эндпоинт отвечает `501`.
Пустая строка в роли `aud` сняла бы проверку аудитории вовсе, то есть приняла бы токен, выписанный
для чужого приложения.

Числовые значения проверяются: не число, ноль или отрицательное — это опечатка, а не намерение,
поэтому берётся значение по умолчанию. Иначе `EMAIL_LOGIN_RATE_WINDOW_MINUTES=-15` молча снял бы
ограничение частоты с единственного неавторизованного эндпоинта.

Скрипты читают `.env` через встроенный `--env-file-if-exists` — никакого `dotenv`.
Значения из окружения перекрывают файл. `.env` в git не попадает.

## Миграции

Инструмент — [postgrator](https://github.com/rickbergfalk/postgrator): обычные `.sql`-файлы,
никакого DSL, состояние в таблице `schema_migrations`.

```bash
npm run migrate
```

Файлы лежат в `migrations/` и называются `<версия>.<do|undo>.<имя>.sql`:

```
migrations/001.do.init.sql     # применить
migrations/001.undo.init.sql   # откатить
```

Новая миграция — следующий номер и пара `do`/`undo`. Postgrator считает md5 применённых файлов,
поэтому **применённую миграцию не редактируют** — добавляют следующую.

Файл целиком уходит в Postgres одним запросом, то есть выполняется как одна неявная транзакция:
упавшая на середине миграция не оставит половину схемы. Отметка о версии пишется отдельным
запросом следом — если процесс убить ровно между ними, миграция окажется накатанной, но не
записанной, и следующий прогон её повторит. Поэтому миграции пишем идемпотентными
(`IF NOT EXISTS`).

### Таблица `jobs` — не наша

Очередь `jobs` принадлежит **montage** (`schema.sql`, `python worker.py init`); схему её API не
меняет. Своих строк у API три вида: `insert` задачи `media_preview` при завершении загрузки,
`delete` этой же задачи, когда удаляемое медиа перестало существовать (гнать воркера за тем, чего
уже нет, незачем), и `insert` задачи `montage` — при заказе ролика и при повторе упавшего.
Миграции на неё здесь нет и быть не должно — вместо этого `npm run migrate` в конце
**применяет файл соседа** (`../montage/schema.sql`, путь переопределяется `MONTAGE_SCHEMA_SQL`).
Так у схемы очереди остаётся один источник, а локальная база и `npm test` таблицу всё же имеют.
Файл идемпотентен, повторный прогон ничего не меняет.

Если соседа рядом нет (репозиторий API склонирован сам по себе), `npm run migrate` печатает об
этом строку и идёт дальше — таблицу тогда заводит montage сам, своей командой.

## API

### `GET /health`

Без авторизации. Контракт зафиксирован между репозиториями — мобильное приложение проверяет
ровно это, поэтому форма ответа не меняется:

```
200 OK
content-type: application/json; charset=utf-8

{"status":"ok"}
```

Тело — ровно `{"status":"ok"}`. Content-type Fastify всегда отдаёт с `; charset=utf-8` и убрать
его без onSend-хука нельзя, поэтому клиент сверяет заголовок **по префиксу**, а не на равенство.

Это liveness-проба: она отвечает `ok`, пока жив процесс, и ничего не говорит о базе. Связь с
Postgres проверяется один раз на старте — сервер не поднимется, если база недоступна.

### `POST /auth/email/start`

Без авторизации. Тело — `{"email": "..."}`. Заводит пользователя, если такого адреса ещё не
видели, выпускает одноразовую ссылку входа и **отправляет её письмом** через Resend.

```
200 OK
{"ok":true}
```

Ответ **одинаков** и для нового адреса, и для известного: иначе эндпоинт отвечал бы на вопрос
«этот человек у вас зарегистрирован?». Придушен по частоте за окно
`EMAIL_LOGIN_RATE_WINDOW_MINUTES`: отдельно на ящик (`EMAIL_LOGIN_RATE_MAX`, `+tag` не считается
за новый адрес) и отдельно, куда мягче, на IP (`EMAIL_LOGIN_RATE_MAX_PER_IP` — за одним адресом
сидит целый офис). Сверх лимита — `429 {"error":"too many requests"}`. Кривой адрес — `400`
в стандартной форме Fastify (`FST_ERR_VALIDATION`).

Почта не настроена (нет `RESEND_API_KEY` или `MAIL_FROM`) — `503 {"error":"mail not configured"}`,
и это проверяется первым: пользователь не заводится, ссылка не выпускается, лимит не тратится.
Провайдер не принял письмо (сеть, ключ, отказ API) — `502 {"error":"mail delivery failed"}`:
это не про адрес и не про клиента, поэтому не 4xx, и не про нас, поэтому не 500. Настоящая
причина уходит в лог строкой `magic link not sent` и в ответе не появляется. Токен при этом уже
выпущен и просто протухает — повтор выпускает новый.

Самой ссылки и токена в логе больше нет: ссылка — это ключ от аккаунта, а строка лога живёт
дольше и видна большему числу людей, чем письмо. В логе остаётся `magic link sent` с адресом.

### `POST /auth/email/verify`

Без авторизации. Тело — `{"token": "..."}` (токен из ссылки). Гасит токен и открывает сессию.

```
200 OK
{"token":"<токен сессии>","user":{"id":"…","username":null,"name":null,"email":"…"}}
```

Токен ссылки одноразовый: он исчезает в тот же момент, а не просто протухает потом. Повтор с
тем же токеном — `401 {"error":"invalid or expired token"}`, как и для чужого или просроченного.

### `POST /auth/apple`, `POST /auth/google`

Без авторизации. Тело — `{"idToken": "<id-токен от провайдера>"}`: приложение уже получило его
нативным SDK, сервер сам с провайдером не общается. Проверяются подпись по JWKS провайдера, `iss`,
`aud` (`APPLE_CLIENT_ID` / `GOOGLE_CLIENT_ID`) и `exp` — это `jose`. Ответ — ровно как у
`/auth/email/verify`:

```
200 OK
{"token":"<токен сессии>","user":{"id":"…","username":null,"name":"…","email":"…"}}
```

Пользователь заводится при первой встрече пары (провайдер, `sub`); `name` и `email` берутся из
токена, если он их несёт, иначе `null` — Apple имени не присылает, а адрес может быть скрытым
релеем. Токен не прошёл проверку любым способом (подпись, `aud`, `iss`, `exp`, не JWT) —
`401 {"error":"invalid token"}`, одинаково для всех причин: разница в ответе подсказывала бы, что
подделать. Провайдер без client id выключен — `501 {"error":"provider not configured"}`.

### `GET /me`

За `app.authenticate`. Отдаёт текущего пользователя — то же, что лежит в `request.user`:

```
200 OK
{"id":"…","username":null,"name":null,"email":"…"}
```

### `POST /me/username`

За `app.authenticate`. Тело — `{"username": "..."}`. Занимает ник, если его ещё нет, и меняет,
если есть, — это один и тот же запрос: прежний ник нигде не хранится и освобождается сразу.
Отвечает обновлённым пользователем, **ровно в форме `GET /me`**:

```
200 OK
{"id":"…","username":"kubik","name":null,"email":"…"}
```

Правила ника:

| Что                | Как                                                             |
|--------------------|-----------------------------------------------------------------|
| Набор знаков       | латинские буквы, цифры и разделители `_` `.` `-`                |
| Длина              | 3–30                                                            |
| Края               | разделитель не может стоять первым или последним знаком         |
| Регистр            | хранится как введён, но уникальность — регистронезависимая      |

Латиница намеренно: ник — это то, чем один человек указывает на другого при приглашении, а
кириллическая `а` неотличима от латинской `a`. `citext` сводит регистр, но не алфавиты, поэтому
Unicode-ник был бы готовым инструментом выдать себя за кого угодно.

Ник занят кем-то другим (в любом регистре) — `409 {"error":"username taken"}`. Сменить регистр
**своего** ника (`foo` → `Foo`) можно: это та же строка в базе. Не подходит под правила выше —
`400` в стандартной форме Fastify.

### `GET /me/username/available?username=<ник>`

За `app.authenticate`. Тот же вопрос, что и `POST /me/username`, но без попытки занять: поле ника
говорит «свободен» ещё до отправки формы.

```
200 OK
{"available":true}
```

Свой текущий ник — тоже `true`: отправить его обратно без изменений или сменить в нём регистр
`POST` разрешает, значит и здесь это не «занято». Ник не по правилам — `400` в стандартной форме
Fastify, тем же правилом и на том же месте, что и при занятии: тихое «свободен» на строке, которую
`POST` потом отвергнет, — обман поля.

### `GET /users?username=<ник>`

За `app.authenticate`. Поиск человека по нику, чтобы пригласить его в воспоминание. Совпадение
**точное** и регистронезависимое; префиксного и нечёткого поиска нет и в MVP не будет — иначе это
превращается в справочник всех пользователей.

```
200 OK
{"id":"…","username":"kubik","name":null}
```

Три поля и ни одного больше: ник можно подобрать, поэтому он не должен быть способом вытащить
чужой email. Никто такой ник не держит — `404 {"error":"not found"}`.

Запрос сначала проверяется тем же правилом, каким проверяется занятие ника, и всё, что под него
не подходит, — сразу `404`. Это не придирка: `citext` сводит регистр через `lower()` базы, а тот
отображает `İ` на `i` и `U+212A KELVIN SIGN` на `k`, так что незачищенный запрос `KUBİK` достал
бы настоящую строку `kubik`. Занять ник с такими знаками нельзя (только латиница), значит и найти
по ним нельзя — иначе «точное совпадение» было бы неправдой. Заодно это не пускает в базу
нулевой байт, который она сравнивать не умеет и отвечала на него `500`.

`400` здесь означает ровно одно — параметр `username` не передан вовсе.

### `GET /auth/sessions`

За `app.authenticate`. Живые сессии текущего пользователя — не отозванные и не протухшие,
свежая первой. `current` помечает ту, которой сделан этот самый запрос:

```
200 OK
[{"id":"…","created_at":"2026-09-02T…","expires_at":"2026-10-02T…","current":true}]
```

Список — голый массив: это перечень и ничего кроме. Чужие сессии в него не попадают.

`current` помечает **не больше одной** строки (`token_hash` уникален), но клиенту стоит держать
в уме и ноль: если ровно в этот момент текущую сессию погасили с другого устройства, она выпадет
из выборки живых. Это самолечится — следующий запрос этим токеном получит `401`.

### `POST /auth/sessions/:id/revoke`

За `app.authenticate`. Гасит одну **свою** сессию по id — «выйти на том телефоне».

```
200 OK
{"ok":true}
```

Чужой или несуществующий id — `404 {"error":"not found"}`, одинаково: иначе эндпоинт отвечал бы
на вопрос «существует ли такая сессия?». Повторный отзыв — тоже `200`, результат тот же. `id` не
uuid — `400`; форма `urn:uuid:…` тоже `400`, хотя ajv её за uuid считает, — Postgres не считает.

⚠️ Оба эндпоинта отзыва тела **не принимают**. Не ставьте на них `Content-Type: application/json`
с пустым телом: Fastify отвечает на это `400 FST_ERR_CTP_EMPTY_JSON_BODY` до всякой логики.
Либо не шлите заголовок, либо шлите телом `{}`.

### `POST /auth/logout`

За `app.authenticate`. Гасит ту сессию, чьим токеном сделан запрос. Остальные сессии
пользователя живы.

```
200 OK
{"ok":true}
```

После этого тот же токен получает `401` на любом маршруте — в том числе на повторном
`/auth/logout`. Тела не принимает — про пустой `Content-Type: application/json` см. выше.

### `POST /memories`

За `app.authenticate`. Заводит воспоминание и сразу — членство создателя в нём с ролью
`organizer`, одним запросом, то есть атомарно.

```
{"title": "Свадьба Ани", "event_start": "2026-09-02T18:00:00+03:00", "event_end": null}
```

| Поле          | Обязательно | Что это                                                      |
|---------------|-------------|--------------------------------------------------------------|
| `title`       | да          | непустое (одни пробелы не считаются), до 200 символов; хранится обрезанным по краям |
| `event_start` | да          | момент начала мероприятия, RFC 3339 **со смещением**          |
| `event_end`   | нет         | момент конца; можно не слать или прислать `null`              |

Даты — `timestamptz`, и клиент шлёт именно момент, а не голую дату: по этому окну m-1 отбирает
медиа из галереи участника по времени съёмки. Голая дата (`2026-09-02`) отвергается с `400` —
иначе её пришлось бы растянуть в окно по часовому поясу сервера, а он не тот, в котором люди
были на мероприятии.

```
201 Created
{"id":"…","organizer_id":"…","title":"Свадьба Ани",
 "event_start":"2026-09-02T15:00:00.000Z","event_end":null,
 "storage_bytes":"0","media_count":0,"montage_count":0,
 "created_at":"…","role":"organizer","recent_thumbnail_urls":[]}
```

Отказы: пустой или отсутствующий `title`, отсутствующий или не-RFC-3339 `event_start` — `400`
в стандартной форме Fastify. `event_end` раньше `event_start` — `400
{"error":"event_end is before event_start"}` (моменты сравниваются как моменты: текстом
`…T01:00+03:00` идёт *после* `…T00:00Z`, а на деле на два часа раньше).

**`storage_bytes` — строка, а не число.** Колонка `bigint`, и postgres.js отдаёт такие строкой,
чтобы не округлить за пределами 2^53. Складывать её на клиенте как число нельзя.

### `GET /memories`

За `app.authenticate`. Главный экран: воспоминания, в которых вызывающий состоит — и как
организатор, и как приглашённый. Организатор держит обычную строку в `memory_members`, поэтому
особого случая тут нет.

```
200 OK
[{…то же тело, что у POST, включая "role"…}]
```

Порядок — сначала самые свежие по `event_start`, при равенстве по `created_at`. Чужие
воспоминания не видны; ответ — в точности массив тех же объектов, что отдаёт `POST /memories`,
так что созданное кладётся в начало списка как есть.

`recent_thumbnail_urls` — до **четырёх** последних кадров воспоминания: карточка на главном экране
рисует ими хвост из настоящих фотографий. Ссылки подписанные и живут те же
`R2_DOWNLOAD_TTL_SECONDS`, что и в галерее; ведут они на превью (`thumbnail_key`), а не на
оригиналы. Порядок — самое свежее первым, по времени съёмки, а для файла без даты по времени
загрузки: тот же порядок, что и в галерее, только с конца.

Всё считается **одним запросом** на весь список — по кадрам на воспоминание не ходят отдельно.
Записи, которым воркер ещё не сделал превью, в хвост не попадают, так что у свежего воспоминания
он пустой. Пустой он и когда не заданы `R2_*`: подписать нечем, но главный экран должен
нарисоваться — в отличие от галереи, где ссылки и есть весь ответ и потому там `503`.

### `POST /memories/:memoryId/members`

За `app.authenticate` + `app.requireMembership`. Зовёт человека по нику. Вызывающий должен быть
`contributor` или `organizer` — `viewer` получает `403 {"error":"forbidden"}`.

```
{"username": "anya", "role": "contributor"}
```

`role` — только `viewer` или `contributor`; `organizer` не выдаётся никогда и никому (у
воспоминания он один, его создатель), поэтому такое значение — `400`. Ник ищется точным
совпадением тем же кодом, что и `GET /users` (`findByUsername` в `src/auth/identity.ts`) — ника нет
или он в принципе не мог быть занят → `404 {"error":"not found"}`.

```
200 OK
{"id":"…","username":"anya","name":"Аня","role":"contributor"}
```

Повторный вызов на уже добавленного — тоже `200`, и **ничего не меняет**: в ответе приходит та
роль, которую человек держит, а не та, которую попросили. Так «пригласить» организатора не
понижает его до `viewer`. `invited_by` записывается на того, кто позвал, а не на организатора.

Успешное **добавление** (не повторное) шлёт приглашённому пуш — см. «Пуши» ниже.

### `GET /memories/:memoryId/members`

За `app.authenticate` + `app.requireMembership`. Кто состоит в воспоминании — **все участники,
включая организатора** (у него обычная строка в `memory_members`).

```
200 OK
[{"id":"…","username":"anya","name":"Аня","role":"organizer","contribution_status":"more_coming"},
 {"id":"…","username":"bob","name":null,"role":"contributor","contribution_status":"not_started"}]
```

**Читать может любой участник, `viewer` в том числе** — порога `contributor` здесь нарочно нет:
матрица даёт `viewer` «смотреть», и увидеть, кто ещё был на мероприятии, — это оно и есть.

Поля — ровно те же три, что отдаёт `GET /users`, плюс `role` и `contribution_status`: у клиента
одна форма пользователя на всё приложение. **Почты здесь нет и не будет** — список открыт каждому,
кто пришёл по ссылке, и адресной книгой он стать не должен. `invited_by` не отдаётся: клиенту с
этим uuid делать нечего.

`contribution_status` — прогресс участника по материалу, тот самый экран «кто уже скинул» (doc-06);
что означает каждое значение — в «Статусе вклада» ниже. Поле названо длинно нарочно: рядом на
клиенте лежит медиа со своим `status`, и это совсем про другое.

Порядок — по времени вступления, поэтому организатор идёт первым. Не участник, несуществующее
воспоминание и кривой id — общий `404 {"error":"not found"}` от самой проверки.

### Статус вклада

У каждого участника внутри воспоминания есть статус того, что он принёс, — колонка
`memory_members.status`. Он **на участии, а не на человеке**: один и тот же человек может всё
скинуть в одно воспоминание и ничего в другое.

| Значение      | Что это                                                      | Кто ставит                     |
|---------------|--------------------------------------------------------------|--------------------------------|
| `not_started` | позвали, ничего не загружено и ничего не сказано              | само, при добавлении в память  |
| `more_coming` | что-то принёс и ещё будет                                     | API, на первой загрузке и поверх `nothing` |
| `done`        | «это всё, больше не буду»                                     | сам участник                   |
| `nothing`     | «материала от меня не будет»                                  | сам участник                   |

`done` и `nothing` оба — слово самого участника, и API их не переписывает, с одним исключением:
`nothing` — это утверждение о будущем, и загрузка его опровергает, поэтому пришедший файл переводит
участника из `nothing` в `more_coming`. Иначе у организатора в ростере навсегда оставалось бы
«ждать нечего» над человеком, чьи фотографии лежат в галерее, и починить это в приложении было бы
нечем. `done` при этом не трогается: он от новых файлов устаревает, но не становится ложью, а
переспрашивать уже отвеченное незачем. Промежуточного «напомнили» нет: автонапоминания вне MVP
(decision-03).

**Статус не режет права.** Ни загрузка, ни просмотр, ни приглашения на него не смотрят — это
табличка для организатора, а не ещё один уровень доступа (doc-06).

### `POST /memories/:memoryId/contribution-status`

За `app.authenticate` + `app.requireMembership`. Участник ставит статус **себе** — либо отвечая на
вопрос приложения после первой загрузки, либо сам по себе, ничего не загрузив.

```
{"status": "nothing"}
```

```
200 OK
{"status":"nothing"}
```

Принимаются только `done` и `nothing`: остальные два значения API пишет сам, и просить их незачем.
Любое другое — `400` в стандартной форме Fastify.

**Порога по роли нет вовсе, `viewer` тоже может.** Статус ничего не даёт и ничего не отнимает, а
не дать человеку сказать «у меня ничего нет» значило бы оставить организатора ждать. Чужой статус
не ставится никак — в маршруте нет `:userId`, и ставится он всегда вызывающему.

Повторный вызов просто перезаписывает — участник вправе передумать. Не участник, несуществующее
воспоминание и кривой id — общий `404 {"error":"not found"}`, без сессии — `401`.

### `GET /memories/:memoryId/invite`

За `app.authenticate` + `app.requireMembership`, тот же порог `contributor`. Отдаёт действующую
ссылку-приглашение и **заводит её, если её ещё нет** — клиенту нечего делать с ответом «ссылки
пока нет», он спрашивает ровно в момент тапа по «поделиться».

```
200 OK
{"token":"XfxBlXErAGL8Gbteai_kfTAa6Zo0IoG5EoFOx8Pwt3Y","role":"contributor"}
```

Живая ссылка у воспоминания ровно одна — это держит частичный уникальный индекс
`invites_one_active_idx`, а не код. Второй вызов вернёт ту же самую. Заведённая на первом запросе
даёт `contributor`: людей зовут, чтобы они принесли материал.

`token` — непрозрачные 32 случайных байта; сам deep link из него собирает приложение.

### `POST /memories/:memoryId/invite`

Там же и с тем же порогом. Отзыв и есть выпуск новой: старый `token` помечается `revoked_at` и
сразу же заводится новый. Другого «отозвать» нет — у воспоминания всегда есть ссылка.

```
{"role": "viewer"}     // необязательно; без тела или без поля — "contributor"
```

```
200 OK
{"token":"…новый…","role":"viewer"}
```

Этим же меняется уровень, который ссылка выдаёт: старая ссылка после этого не пускает никого.
Тело можно не слать вовсе — `POST` без тела означает «просто дай новую».

### `POST /invites/accept`

**Только** за `app.authenticate`, без `app.requireMembership`: вызывающий как раз ещё не участник.
Веб-страницы приглашения нет и не будет (decision-01) — ссылка открывает приложение, а у того, кто
по ней пришёл, уже есть аккаунт.

```
{"token": "XfxBlXErAGL8Gbteai_kfTAa6Zo0IoG5EoFOx8Pwt3Y"}
```

```
200 OK
{…ровно то же тело, что у POST /memories, с "role" из приглашения…}
```

Отдаётся всё воспоминание целиком, чтобы приложение открыло экран загрузки сразу, без второго
запроса. Уже участник — тоже `200`, роль остаётся прежней: ссылка это вход, а не способ сменить
уровень. Отозванный и несуществующий токен — один и тот же `404 {"error":"not found"}`: по
старой ссылке нельзя узнать даже того, что она когда-то работала.

Пуш здесь **не** шлётся: человек пришёл сам и знает, куда попал.

### `DELETE /memories/:memoryId/members/:userId`

За `app.authenticate` + `app.requireMembership`. Исключение и выход — это одно действие над одной
строкой, и разница только в том, себя удаляют или другого:

| Кто           | Кого                | Что                                              |
|---------------|---------------------|--------------------------------------------------|
| `organizer`   | любого другого      | `200 {"ok":true}`                                 |
| любой участник| себя (выход)        | `200 {"ok":true}`                                 |
| не `organizer`| другого             | `403 {"error":"forbidden"}`                       |
| `organizer`   | себя                | `409 {"error":"organizer cannot leave the memory"}`|

Организатор выйти не может: не осталось бы никого, кто может исключать, удалять чужое медиа и
заказывать ролик, а передача роли — вне MVP (doc-01). Кого в воспоминании нет — и `userId`, который
вовсе не uuid, — это `404 {"error":"not found"}`, тем же телом, что и всё остальное в этом
семействе маршрутов.

**Материал уходит вместе с человеком.** В той же транзакции, что и строка `memory_members`,
пропадает всё, что он загрузил в это воспоминание: записи `media_items`, счётчики воспоминания и
его `user_usage` — вниз, задачи `media_preview` — из очереди. Оригиналы и деривативы удаляются из
хранилища **после** коммита (`architecture.md`, «Выход / исключение участника»).

Уже смонтированные ролики не трогаются, даже если там его кадры (m-2). Материал остальных
участников остаётся на месте — уходит ровно то, что принёс уходящий.

Порядок «сначала база, потом хранилище» не случаен: у R2 нет отката, поэтому объект, удалённый до
коммита, при откате оставил бы записи, указывающие в пустоту. Наоборот — остаются байты, на которые
никто не ссылается, и это стоит только места. Если хранилище не ответило, записей уже нет, а строка
об осиротевших ключах уходит в лог: выход из воспоминания не может упереться в недоступный R2.

### Загрузка медиа — как это устроено

Байты в API **не приходят**. Приложение говорит «хочу загрузить», получает подписанные ссылки и
льёт файл прямо в хранилище, а потом сообщает, что закончило:

1. `POST /memories/:memoryId/media` — проверяются права и лимиты, заводится запись `media_items`
   в статусе `pending_upload`, в ответ — подписанные ссылки на куски (multipart).
2. Приложение шлёт `PUT` на каждую ссылку своим куском файла и запоминает заголовок `ETag`
   каждого ответа.
3. `POST /memories/:memoryId/media/:mediaId/complete` со списком кусков и их `ETag` — API
   собирает объект в хранилище, переводит запись в `processing`, двигает счётчики и ставит
   воркеру задачу `media_preview`.

Ссылки живут час (`R2_UPLOAD_TTL_SECONDS`). Протухли — `GET /memories/:memoryId/media/:mediaId/upload`
выдаёт новые **для той же записи и той же multipart-загрузки**: уже отправленные куски
остаются в хранилище, догрузка продолжается с места обрыва, а не начинается заново.

### `POST /memories/:memoryId/media`

За `app.authenticate` + `app.requireMembership`. Порог — `contributor`: `viewer` получает
`403 {"error":"forbidden"}` (матрица даёт ему смотреть, но не приносить).

```
{"kind": "photo", "size_bytes": 4194304, "captured_at": "2026-09-02T19:30:00+03:00"}
```

| Поле               | Обязательно     | Что это                                                     |
|--------------------|-----------------|--------------------------------------------------------------|
| `kind`             | да              | `photo` или `video`                                          |
| `size_bytes`       | да              | размер файла целиком; по нему считается число кусков          |
| `captured_at`      | нет             | момент съёмки из галереи, RFC 3339 со смещением; `null` — файл без даты |
| `duration_seconds` | **для видео**   | длительность; без неё видео не принять — нечем проверить лимит |

```
201 Created
{"id":"…","status":"pending_upload",
 "upload":{"key":"originals/…","upload_id":"…","part_size":8388608,
           "parts":[{"part_number":1,"url":"http://…&X-Amz-Signature=…"}],
           "expires_at":"2026-09-03T12:00:00.000Z"}}
```

Файл режется на куски по `part_size`, кусок номер N уходит на `parts[N-1].url` методом `PUT`.
Ключ оригинала — по id записи, и он приходит в ответе: собирать его на клиенте не нужно.

Отказы по лимитам — до того, как что-либо записано: **записи и ключа в хранилище не остаётся**.

| Ответ | Тело                                                        | Когда                          |
|-------|-------------------------------------------------------------|--------------------------------|
| `413` | `{"error":"file is too large","limit_bytes":1073741824}`     | файл больше потолка            |
| `413` | `{"error":"video is too long","limit_seconds":300}`          | видео длиннее потолка          |
| `409` | `{"error":"memory is full","limit_files":1000}`              | в воспоминании больше нельзя файлов |
| `409` | `{"error":"memory is out of space","limit_bytes":10737418240}` | не хватает объёма            |
| `400` | `{"error":"duration_seconds is required for a video"}`       | видео без длительности         |
| `503` | `{"error":"storage not configured"}`                         | не заданы `R2_*`               |

Счётчики воспоминания двигаются в момент завершения загрузки, а не выдачи ссылки, поэтому пачка
загрузок «в полёте» может перебрать потолок на то, что летит. Следующая заявка тогда откажет.

### `GET /memories/:memoryId/media/:mediaId/upload`

За `app.authenticate` + `app.requireMembership`. Та же запись, та же multipart-загрузка, свежие
подписи. Тело — как у `POST` выше.

Новой записи не заводится и уже загруженные куски не теряются — это и есть докачка.

Чужая запись, запись из другого воспоминания, несуществующая и кривой `mediaId` — общий
`404 {"error":"not found"}`. Доделать загрузку может только тот, кто её начал: это не про роль, а
про владение. Запись, которая уже не `pending_upload`, — `409
{"error":"upload is already finished","status":"processing"}`.

### `POST /memories/:memoryId/media/:mediaId/complete`

За `app.authenticate` + `app.requireMembership`, та же проверка владения. Куски — все, что были
отправлены, с их `ETag` из ответов хранилища.

```
{"parts": [{"part_number": 1, "etag": "\"254a7725306413d2a8e39ad05ffa018a\""}]}
```

```
200 OK
{"id":"…","status":"processing","first_upload":true}
```

Внутри одной транзакции: запись переходит в `processing`, у воспоминания растут `storage_bytes` и
`media_count`, у загрузившего — строка `user_usage`, в `jobs` встаёт задача `media_preview`, и —
если он стоял в `not_started` или в `nothing` — его `contribution_status` переходит в
`more_coming`.

`first_upload` — это «переход из `not_started` только что случился»: по нему приложение задаёт
вопрос «всё загрузили или ещё будете?» (doc-06) и шлёт ответ в
`POST /memories/:memoryId/contribution-status`. Приходит в каждом ответе, `false` во всех
остальных случаях — второй загрузкой, повторным колбэком и статусами `more_coming` и `done`.

Сказал «ждать нечего» и всё-таки что-то залил — статус чинится сам (`nothing` → `more_coming`),
но вопрос не задаётся: `first_upload` остаётся `false`. Своё слово человек уже сказал, а ростер
организатора после этого перестаёт врать.

**Повторный вызов безопасен** — телефон, не дождавшийся ответа, зовёт снова и получает то же
самое: счётчики не сдвигаются второй раз, вторая задача не ставится и `first_upload` приходит
`false`. В ответе — текущий статус записи, каким бы он к тому моменту ни стал (воркер мог уже
увести её в `ready`).

Записывается **тот размер, который хранилище реально держит**, а не заявленный в первом шаге:
заявленный проверяется лимитами, но занизить его в счётчиках нельзя. Если объекта в хранилище
нет — `409 {"error":"the upload is not in storage"}`, запись остаётся `pending_upload`, и загрузку
можно доделать.

### `GET /memories/:memoryId/media`

За `app.authenticate` + `app.requireMembership`. Галерея воспоминания — **весь** материал, чей бы
он ни был. Читает её любой участник, `viewer` в том числе: матрица даёт ему «смотреть галерею».

```
200 OK
[{"id":"…","kind":"photo","status":"processing","uploaded_by":"…",
  "size_bytes":"4096","captured_at":"2026-09-02T16:30:00.000Z",
  "width":null,"height":null,"duration_seconds":null,"created_at":"…",
  "thumbnail_url":"http://…&X-Amz-Signature=…","preview_url":null}]
```

Порядок — **по времени съёмки**, а для файла без даты по времени загрузки: то же правило, по
которому воркер расставляет кадры в ролике (`architecture.md`, «Montage-пайплайн»), чтобы галерея
читалась в том же порядке, в каком ролик играет.

Записи в статусе `pending_upload` в список **не попадают** — байтов за ними ещё нет. `failed`
попадают: клиент рисует плейсхолдер и предлагает повторить.

Ссылки — только на **деривативы** и только подписанные, живут `R2_DOWNLOAD_TTL_SECONDS` (15 минут).
Пока воркер не сделал превью, `thumbnail_url` и `preview_url` — `null`; это не ошибка, а «ещё не
готово». Оригинал отсюда не отдаётся: галерея показывает лёгкую версию, а оригинал уходит только
тогда, когда его попросили, — двумя маршрутами `/download` ниже. Протухли — клиент просто
запрашивает список заново.

Не заданы `R2_*` — `503 {"error":"storage not configured"}`: подписать нечем, и список из одних
`null` был бы неправдой. Не участник, несуществующее воспоминание и кривой id — общий
`404 {"error":"not found"}`.

### `GET /memories/:memoryId/media/:mediaId/download`

За `app.authenticate` + `app.requireMembership`. Подписанная ссылка на **оригинал** одного файла —
то самое «скачать». Порога по роли здесь нет: матрица даёт скачивать оригиналы каждому участнику,
`viewer` в том числе, и стоять в воспоминании — это всё, что проверяется.

```
200 OK
{"url":"http://…&X-Amz-Signature=…"}
```

Ссылка живёт `R2_DOWNLOAD_TTL_SECONDS` (15 минут) — тот же срок и по той же причине, что у ссылок
галереи: она не должна пережить членство того, кому её выдали. Протухла — клиент просит новую.
Байты идут из хранилища напрямую, API на их пути нет — ровно как при загрузке.

Записи в `pending_upload` отсюда не отдаются: байтов за ними ещё нет, подписывать нечего, а для
вызывающего это ровно «нет такой записи». Она, запись из другого воспоминания, несуществующая и
`mediaId`, который вовсе не uuid, — общий `404 {"error":"not found"}`. Не заданы `R2_*` — `503
{"error":"storage not configured"}`.

### `GET /memories/:memoryId/media/download`

Там же и с тем же порогом. Ссылки на оригиналы **всей** галереи одним ответом: клиент сохраняет
файлы сам, и просить ссылку по одной значило бы отдельный запрос на каждый файл.

```
200 OK
[{"id":"…","kind":"photo","url":"http://…&X-Amz-Signature=…"}]
```

Отбор и порядок — те же, что у `GET /memories/:memoryId/media`: `pending_upload` не попадает,
`failed` попадает (оригинал у него есть, не хватает только превью), сортировка по времени съёмки, а
для файла без даты по времени загрузки. Так скачанное на телефон ложится в том же порядке, в каком
лежало на экране. Пустая галерея — пустой массив, а не `404`.

Все ссылки списка подписаны в один момент и протухают вместе, через те же 15 минут: скачивание
стоит начинать сразу, а не откладывать, — на протухшие клиент запрашивает список заново, как и в
галерее. Отказы — те же, что у маршрута на один файл: `503` без `R2_*`, общий `404` от проверки
прав.

Два маршрута различаются одним сегментом — `/media/download` и `/media/:mediaId/download`. Роутер
предпочитает буквальный сегмент параметру, поэтому «вся галерея» не читается как запись с id
`download`; порядок объявления на это не влияет.

### `DELETE /memories/:memoryId/media/:mediaId`

Там же. Удаляет **тот, кто загрузил** — это владение, а не роль, — и `organizer`, которому матрица
даёт любое медиа:

| Кто                        | Что                                    |
|----------------------------|----------------------------------------|
| загрузивший (любой роли)   | `200 {"ok":true}`                      |
| `organizer`                | `200 {"ok":true}` на любое медиа       |
| участник, но не тот и не он| `403 {"error":"forbidden"}`            |

Поэтому `viewer` может удалить своё (если оно у него есть), а `contributor` не может удалить
соседское. Нет такой записи, запись из другого воспоминания и `mediaId`, который вовсе не uuid, —
`404 {"error":"not found"}`, тем же телом, что и всё в этом семействе.

В одной транзакции: строка `media_items` пропадает, `storage_bytes` и `media_count` воспоминания
уменьшаются, `user_usage` загрузившего — тоже, задача `media_preview` снимается с очереди. Оригинал
и деривативы уходят из хранилища **после** коммита — про порядок и про то, что бывает, если
хранилище не ответило, см. «Материал уходит вместе с человеком» выше.

Запись, которая так и не догрузилась (`pending_upload`), счётчиков не двигала — значит и при
удалении они не двигаются. Иначе счётчики ушли бы ниже факта.

### Ролики — как это устроено

Ролик монтирует не API, а сосед — **montage-воркер** (`projects/montage`). API владеет таблицей
`montages` и делает ровно три вещи: заводит строку по заказу организатора, показывает список
участникам и рассылает пуш, когда воркер сказал «готово».

1. `POST /memories/:memoryId/montages` — проверяются права и материал, в `montages` появляется
   строка в статусе `queued`, в `jobs` — задача `montage` со ссылкой на её `id`.
2. Воркер берёт задачу, ведёт строку `queued` → `processing` → `ready` (или `failed`), сам пишет в
   неё `video_key`, `duration_seconds`, `error_text`.
3. Готово — воркер стучится в `POST /internal/montages/:montageId/ready`, и API шлёт пуш «ролик
   готов» **всем** участникам воспоминания.
4. Упало — у организатора кнопка «повторить»: та же строка возвращается в `queued`, и в очередь
   встаёт новая задача.

Статусы ролика — те же четыре слова, что у медиа, но своя цепочка: `queued` (заказан, ждёт
воркера), `processing` (монтируется), `ready` (можно смотреть), `failed` (упал, можно повторить).
Ролики живут **отдельно от галереи** и в неё не подмешиваются (doc-03).

#### Контракт с воркером

Единственное, что связывает два репозитория, — это оно, и меняется только вместе с ними обоими:

| Что                | Чьё            | Как именно                                                      |
|--------------------|----------------|-----------------------------------------------------------------|
| таблица `montages` | заводит API (миграция) | воркер читает и пишет строку по `id`, как `media.py` уже делает с `media_items` |
| задача в `jobs`    | таблица montage | тип — ровно `montage`, `ref` — `montages.id` строкой            |
| `status`           | пишут оба      | API ставит только `queued`; всё дальше — воркера                 |
| `video_key`, `duration_seconds`, `error_text` | воркер | API их только читает и подписывает ссылку     |
| `params`           | пишет API      | `{"target_seconds": 60}` плюс `music_track_id`, если его назвали  |
| `/internal/montages/:id/ready` | API | воркер дёргает его после того, как записал `ready`               |

Каталог треков (`warm`, `bright`, `calm`) общий на оба сервиса: здесь по нему только проверяется
вход, сами файлы вшиты в воркер.

### `POST /memories/:memoryId/montages`

За `app.authenticate` + `app.requireMembership`. Заказать ролик может **только `organizer`**:
`contributor` и `viewer` получают `403 {"error":"forbidden"}`. Материал приносят все, а что из него
собрать — решает организатор (`architecture.md`, «Проверка прав»).

```
{"target_seconds": 90, "music_track_id": "calm"}
```

| Поле              | Обязательно | Что это                                                        |
|-------------------|-------------|-----------------------------------------------------------------|
| `target_seconds`  | нет         | желаемая длина, целое; границы — `MONTAGE_TARGET_SECONDS_MIN`/`MAX` |
| `music_track_id`  | нет         | `warm`, `bright` или `calm` — трек из набора воркера             |

Тело целиком необязательно: `{}`, `null` и запрос вовсе без тела — это один и тот же «без
пожеланий». Одна оговорка про третий вариант: «без тела» значит и без заголовка
`Content-Type: application/json`. Заголовок при пустом теле — это `400`
`FST_ERR_CTP_EMPTY_JSON_BODY` от самого Fastify, ещё до нашей схемы; клиенту, который ставит этот
заголовок всегда, надёжнее слать `{}`.

Незаданная длина записывается в строку значением по умолчанию (`MONTAGE_TARGET_SECONDS`, 60 с),
незаданный трек не записывается вовсе — его выберет воркер. Неизвестные поля отбрасываются, в
`params` попадает только то, что здесь описано.

```
201 Created
{"id":"…","memory_id":"…","ordered_by":"…","status":"queued","duration_seconds":null,
 "params":{"target_seconds":90,"music_track_id":"calm"},"error_text":null,
 "created_at":"…","updated_at":"…","video_url":null}
```

| Ответ | Тело                                                        | Когда                          |
|-------|-------------------------------------------------------------|--------------------------------|
| `403` | `{"error":"forbidden"}`                                      | участник, но не организатор    |
| `409` | `{"error":"not enough material for a montage","ready_items":2,"need":3}` | в воспоминании меньше трёх `ready`-медиа |
| `400` | ошибка схемы                                                 | длина вне границ, трек не из набора |

Меньше трёх готовых файлов — отказ **до** записи: ни строки, ни задачи не остаётся. Считаются
только `media_items` в статусе `ready`: то, что ещё грузится или обрабатывается, воркеру нечем
монтировать (`architecture.md`, «Montage-пайплайн»). Клиент показывает это своими словами —
«недостаточно материала для ролика»; тело ответа, как и везде здесь, английское и с числами.

Строка, задача в очереди, `memories.montage_count` и `user_usage.montage_count` двигаются **одной
транзакцией**: счётчик считает заказанное, а не смонтированное, и разойтись со строками не может.
Числа роликов на воспоминание не ограничиваем (doc-03).

### `GET /memories/:memoryId/montages`

За `app.authenticate` + `app.requireMembership`. Список роликов воспоминания, **новые сверху**.
Читает любой участник, `viewer` в том числе: матрица даёт ему «смотреть галерею и ролики».

```
200 OK
[{"id":"…","memory_id":"…","ordered_by":"…","status":"ready","duration_seconds":58.5,
  "params":{"target_seconds":60},"error_text":null,"created_at":"…","updated_at":"…",
  "video_url":"http://…&X-Amz-Signature=…"}]
```

`video_url` — подписанная ссылка на готовый ролик, живёт `R2_DOWNLOAD_TTL_SECONDS` (15 минут, тот
же срок, что у галереи). У всего, что не `ready`, она `null` — это «ещё не готово», а не ошибка;
протухла — клиент запрашивает список заново. Ключ ролика наружу не отдаётся, только ссылка.

У упавшего в `error_text` лежит то, что сказал воркер, — рядом с ним клиент рисует «повторить».

Не заданы `R2_*` — `503 {"error":"storage not configured"}`, как и у галереи: подписать нечем.
Не участник, несуществующее воспоминание и кривой id — общий `404 {"error":"not found"}`.

### `POST /memories/:memoryId/montages/:montageId/retry`

Там же, и снова **только `organizer`**. Повторяет **упавшую** сборку: та же строка возвращается в
`queued`, `error_text` обнуляется, в `jobs` встаёт новая задача `montage`. Ответ — обновлённая
строка в той же форме, что в списке.

| Ответ | Тело                                                        | Когда                          |
|-------|-------------------------------------------------------------|--------------------------------|
| `200` | строка ролика                                                | был `failed`, теперь `queued`  |
| `403` | `{"error":"forbidden"}`                                      | участник, но не организатор    |
| `409` | `{"error":"montage has not failed","status":"queued"}`       | ролик не падал                 |
| `404` | `{"error":"not found"}`                                      | нет такого ролика, он из чужого воспоминания или `montageId` не uuid |

Проверка «был `failed`» стоит в самом `UPDATE`, а не только в условии перед ним: две нажатые
подряд кнопки двигают строку один раз, и вторая получает `409`. Иначе на одной строке оказались бы
две задачи.

### `POST /internal/montages/:montageId/ready`

**Не за `app.authenticate`** — за этим маршрутом нет человека и сессии. Стучится montage-воркер,
когда ролик выложен и строка уже переведена в `ready`; API делает то единственное, чего воркер не
может, — доносит новость до телефонов.

```bash
curl -X POST http://localhost:3000/internal/montages/<id>/ready \
  -H "Authorization: Bearer $INTERNAL_WORKER_TOKEN"
```

Авторизация — общий секрет `INTERNAL_WORKER_TOKEN` в заголовке `Authorization: Bearer`. Не совпал,
не пришёл вовсе или не задан в окружении — `401 {"error":"unauthorized"}`. Сверка идёт по хешам
через `timingSafeEqual`: обычное сравнение строк выдаёт префикс секрета тому, кто его меряет.

Ответ — `200 {"ok":true}`, **даже если пуш не дошёл ни до кого**: ролик готов независимо от
уведомления, а сказать воркеру «не вышло» значило бы отправить его повторять задачу, вся работа
которой сделана. Несуществующий, кривой `montageId` — и строка, которая ещё не `ready`, —
`404 {"error":"not found"}`: маршрут умеет сказать только «ролик готов», и над строкой в `queued`,
`processing` или `failed` ему нечего объявлять. Поэтому порядок обязателен — сперва записать
`ready`, потом стучаться, — и повторный стук по той же строке безопасен.

Тело у запроса не читается: `video_key`, `duration_seconds` и `status` воркер уже записал сам.

### `POST /me/push-tokens`

За `app.authenticate`. Приложение отдаёт сюда свой Expo push token.

```
{"token": "ExponentPushToken[xxxxxxxxxxxxxxxxxxxxxx]", "platform": "ios"}
```

`platform` необязателен и принимает только `ios` или `android` — он для чтения таблицы глазами,
ветвлений по нему нет. Ответ — `200 {"ok":true}`.

Ключ таблицы — сам токен, поэтому повторная регистрация того же устройства идемпотентна, а
устройство, сменившее владельца, **переезжает** к новому: иначе телефон продолжал бы получать
уведомления о чужих воспоминаниях.

### Пуши

Типов в MVP два, и оба уходят одним и тем же путём — `fetch` прямо в Expo
(`src/memories/push.ts`), одним запросом на все устройства получателей (Expo берёт не больше 100
сообщений за раз и на 101-е отвечает `400` целой пачке, поэтому длинные рассылки режутся на сотни —
у приглашения адресат один, а у «ролик готов» это все участники):

- **«вас позвали в воспоминание»** (decision-06) — приглашённому, только при добавлении **по нику**
  и только когда человек действительно добавился;
- **«ролик готов»** (doc-03) — всем участникам воспоминания разом, по стуку воркера в
  `/internal/montages/:montageId/ready`. Не только заказавшему: ролик и есть награда за то, что
  люди скинули медиа.

```
«<кто позвал> приглашает вас в «<название>» — загрузите свои фото и видео»
                                                        + data: {"memoryId": "…"}
«Ролик из «<название>» готов — посмотрите и поделитесь»
                                       + data: {"memoryId": "…", "montageId": "…"}
```

**Формулировка без рода.** «добавил вас в» врало бы половине зовущих (в самом decision-06 пример —
«Аня добавила»), а «добавил(а)» читается как бланк. Настоящее время ни с кем не согласуется, поэтому
одна строка верна для любого организатора; менять её на прошедшее нельзя. Призыв загрузить медиа —
часть уведомления, а не украшение: ради него оно и шлётся (decision-06).

Зовущий подписывается своим `name`, а если его нет — ником; нет и его — «Кто-то».
`data.memoryId` — это и есть deep link: приложение по нему открывает нужное воспоминание на экране
загрузки.

**Пуш не может уронить то, о чём сообщает.** Членство коммитится первым и отдельно, отправка идёт
после и целиком снаружи транзакции; у ролика то же самое — воркер стучится, уже записав `ready`.
Отправка глотает всё — нет токенов, нет сети, Expo ответил не 200, пуши выключены — и пишет строку
в лог. Человек оказывается участником, а ролик готовым, независимо от того, дошло уведомление или
нет.

Без `EXPO_PUSH_URL` (или без единого зарегистрированного устройства) в лог уходит `invite push not
sent` / `montage push not sent` с телом, которое **должно было** уйти, — на машине без пушей
разработчик видит ровно это. Первое слово в строке лога — это и есть тип уведомления.

⚠️ **Вживую не проверено.** Ни устройства, ни доступов к Expo в этом окружении нет: путь отправки
покрыт тестами (в том числе на мёртвый хост), но что уведомление реально долетает до телефона,
никто не видел. Первый прогон с реальным dev-билдом — за мобильным клиентом.

`ponytail:` повторов нет. Потерянный пуш потерян насовсем — членство при этом на месте, ролик тоже,
так что цена ровно одна: человек найдёт их сам при следующем заходе. Начнут теряться заметно — путь
переезжает на очередь `jobs`, у которой ретраи с backoff уже есть.

## Аутентификация

Своя, по модели данных из `architecture.md`. Сессия — непрозрачный случайный токен (32 байта из
`node:crypto`), в базе только его SHA-256. Транспорт — заголовок `Authorization: Bearer <токен>`:
клиент нативный, куки и CSRF не нужны. Провайдеров в MVP три — ссылка на email, Apple и Google, —
и все три кончаются одним и тем же: строкой в `auth_identities` и сессией из `src/auth/session.ts`.

Аккаунты **не** сращиваются по совпадению email: первая встреча пары (провайдер, id у провайдера)
заводит нового пользователя. У Apple адрес бывает скрытым релеем — он меняется и может быть выдан
другому человеку, так что склейка по нему рано или поздно пустила бы одного в аккаунт другого.

Apple и Google проверяются через `jose` (`src/auth/providers.ts`): `createRemoteJWKSet` держит
ключи провайдера с их ротацией, `jwtVerify` сверяет подпись, `iss`, `aud` и `exp`. Руками из
токена берётся только `sub` — им и связывают, — плюс `name` и `email`, если они там есть.

### Как повесить проверку сессии

`app.authenticate` — готовый `preHandler`. Он сидит на корневом инстансе, поэтому доступен в любом
маршруте и импортировать нечего:

```ts
app.get("/memories", { preHandler: app.authenticate }, async (request) => {
  return listMemoriesOf(request.user.id);
});
```

Что он делает: читает `Authorization: Bearer <токен>` (схема регистронезависима), считает SHA-256,
ищет сессию без `revoked_at` и с непрошедшим `expires_at`. Нашёл — кладёт пользователя в
`request.user` и пускает дальше. Не нашёл — заголовка нет, схема другая, токен чужой, протухший
или отозванный — **сам** отвечает `401 {"error":"unauthorized"}`, и хендлер не вызывается.

`request.user` — ровно четыре поля и ничего больше:

| Поле       | Тип              | Что это                                        |
|------------|------------------|------------------------------------------------|
| `id`       | `string` (uuid)  | стабильная ссылка на человека — ссылайтесь на неё |
| `username` | `string \| null` | ник; `null`, пока человек его не занял         |
| `name`     | `string \| null` | имя                                            |
| `email`    | `string \| null` | адрес, с которым вошли                         |

Тип объявлен на `FastifyRequest` как всегда присутствующий — так удобнее в защищённом хендлере,
но заполняется он **только** за `app.authenticate`. На маршруте без этого `preHandler` там
`undefined`, и TypeScript об этом не предупредит.

### Как повесить проверку прав на воспоминание

Это раздел для m-1, m-2, m-5 и m-6: всё, что живёт под конкретным воспоминанием, вешает готовую
проверку `app.requireMembership` и ничего своего не пишет.

`app.requireMembership` — второй `preHandler`, тоже на корневом инстансе (`src/memories/plugin.ts`).
Он идёт **после** `app.authenticate` и без него не работает: ему нужен `request.user`.

```ts
app.post(
  "/memories/:memoryId/media",
  { preHandler: [app.authenticate, app.requireMembership] },
  async (request, reply) => {
    if (request.membership.role === "viewer") {
      return reply.code(403).send({ error: "forbidden" });
    }
    return upload(request.membership.memory, request.user.id);
  },
);
```

Параметр маршрута называется **`:memoryId`** — ровно так, проверка читает его по имени.

Что он делает: берёт `:memoryId`, ищет строку `memory_members` этого воспоминания на вызывающего.
Нашёл — кладёт в `request.membership` и пускает дальше:

| Поле                       | Тип                                          | Что это                        |
|----------------------------|----------------------------------------------|--------------------------------|
| `request.membership.role`  | `"organizer" \| "contributor" \| "viewer"`   | роль вызывающего в этом воспоминании |
| `request.membership.memory`| строка `memories` целиком                    | `id`, `organizer_id`, `title`, `event_start`, `event_end`, счётчики, `created_at` |
| `request.membership.status`| `"not_started" \| "more_coming" \| "done" \| "nothing"` | статус вклада вызывающего — см. «Статус вклада» |

Воспоминание уже загружено — второй раз его доставать не нужно. `status` — тот, что был **до**
этого запроса: он читается в начале, и именно поэтому по нему видно, что текущая загрузка у
человека первая.

#### Матрица прав

Из `architecture.md` («Проверка прав»), это источник истины; здесь копия, чтобы не ходить:

| Роль          | Может                                                                |
|---------------|----------------------------------------------------------------------|
| не участник   | ничего                                                               |
| `viewer`      | смотреть галерею и ролики, **скачивать** оригиналы                   |
| `contributor` | + загружать медиа, звать людей (поиском и ссылкой)                   |
| `organizer`   | + удалять любое медиа, исключать участников, **заказывать ролик**     |

Своё загруженное медиа может удалить каждый — это не роль, а владение: проверяется по тому, кто
загрузил, а не по `role`.

Проверка выдаёт роль и на этом останавливается: различать по ней — дело маршрута, у каждого своя
строка матрицы. Хелпера «не ниже роли X» нарочно нет — пока ни один маршрут его не просит,
а роль в `if` читается и так.

#### Домашнее правило: `404` один на всех

**Не участник, несуществующее воспоминание и кривой id получают побайтово одинаковый ответ:**

```
404 Not Found
{"error":"not found"}
```

Это правило наследуется, а не переизобретается: всякая фича, которая вешает эту проверку,
сохраняет такое поведение и **не** заводит своё «403, вы не участник» и своё «404, нет такого».
Разница между этими двумя ответами — это ответ на вопрос «а такое воспоминание вообще есть?»,
и по нему чужие воспоминания перебираются по id.

По той же причине сама проверка не отвечает `403`: `403` на маршруте — это уже про роль
(участник есть, но `viewer` не может загружать), и он законен только за пройденной проверкой.

Кривой id (не uuid) отсекается там же и тем же ответом: без этого он доехал бы до Postgres
ошибкой приведения типа и вернулся `500`.

### Как добыть токен в разработке

С ключом Resend в `.env` — обычным письмом, как у настоящего человека:

```bash
curl -X POST http://localhost:3000/auth/email/start \
  -H 'content-type: application/json' -d '{"email":"you@example.com"}'
```

Без ключа (`503 {"error":"mail not configured"}`) токен выписывается той же функцией, какой его
выписывает эндпоинт, — почта тут ни при чём:

```bash
node --env-file=.env --input-type=module \
  -e "const { startEmailLogin } = await import('./src/auth/email.ts');
      console.log(await startEmailLogin('you@example.com')); process.exit(0)"
# 2yuV9wBJQIQoFqSm…
```

Ссылка — это `remember://auth/email?token=<токен>`. Дальше либо открыть её на симуляторе:

```bash
# dev-билд приложения — схема remember:// принадлежит ему
xcrun simctl openurl booted "remember://auth/email?token=GuYNXVEl…"

# Expo Go — схема remember:// ему не принадлежит, тот же экран открывается через схему Expo
xcrun simctl openurl booted "exp://127.0.0.1:8081/--/auth/email?token=GuYNXVEl…"
```

В Expo Go первая команда падает с `LSApplicationWorkspaceErrorDomain 115`: `remember://`
требует dev-билда.

либо обменять токен на сессию руками:

```bash
curl -X POST http://localhost:3000/auth/email/verify \
  -H 'content-type: application/json' -d '{"token":"GuYNXVEl…"}'
# {"token":"42HDiF7t…","user":{…}}

curl http://localhost:3000/me -H "Authorization: Bearer 42HDiF7t…"
```

### Ошибки

Свои отказы эндпоинты отдают как `{"error": "…"}`. Отказы, которые формирует сам Fastify
(валидация тела, неизвестный маршрут), приходят в его стандартной форме — `statusCode`, `code`,
`error`, `message`.

Всё, что упало на сервере, наружу уходит как `500 {"error":"internal"}`, а настоящая ошибка
пишется в лог: иначе отвалившаяся база отвечала бы постороннему своим SQLSTATE и текстом запроса.

### Отзыв сессий

`src/auth/session.ts`: `revoke(sessionId)` гасит одну сессию по id, `revokeByToken(token)` — ту,
которой сейчас пользуются (это и есть выход из аккаунта). Отзыв проставляет `revoked_at`, строка
остаётся; `app.authenticate` перестаёт её принимать сразу.

Наружу это выведено как `GET /auth/sessions`, `POST /auth/sessions/:id/revoke` и
`POST /auth/logout`. `revoke(sessionId)` про владельца ничего не знает — принадлежность сессии
проверяет маршрут, до вызова.

Свой токен можно достать из заголовка тем же способом, каким его читает проверка сессии:
`bearerToken(request.headers.authorization)` из того же модуля. Разбор заголовка живёт в одном
месте, чтобы «какая из этих сессий — текущая» и `app.authenticate` не разошлись.

## Устройство

```
src/app.ts            Fastify-приложение и маршруты (без сети — тестируется через inject)
src/server.ts         точка входа: проверить базу, слушать порт
src/db.ts             клиент Postgres из DATABASE_URL
src/auth/session.ts   выпуск, проверка и отзыв сессий
src/auth/email.ts     вход по ссылке на email
src/auth/mail.ts      отправка письма со ссылкой (Resend, обычный HTTP)
src/auth/providers.ts проверка id-токенов Apple и Google (jose, JWKS)
src/auth/social.ts    маршруты входа через Apple и Google
src/auth/plugin.ts    декоратор app.authenticate и маршруты входа
src/auth/identity.ts  ник, поиск по нику, список и отзыв сессий
src/auth/config.ts    сроки и лимиты из окружения, с проверкой значений
src/auth/testing.ts   общая оснастка тестов (приложение с логом, вход, уборка)
src/memories/plugin.ts декоратор app.requireMembership и маршруты воспоминаний
src/media/upload.ts   приём загрузки: заявка, повторная ссылка, колбэк «загружено»
src/media/gallery.ts  галерея, удаление медиа и общий каскад (счётчики, jobs, ключи R2)
src/media/r2.ts       S3-совместимое хранилище: multipart и подписанные ссылки
src/media/config.ts   лимиты и сроки ссылок из окружения
src/montages/montages.ts заказ ролика, список, повтор и внутренний маршрут для воркера
scripts/migrate.ts    запуск postgrator и таблица jobs из montage
migrations/           .sql-миграции
```

`authPlugin` и `memoriesPlugin` вызываются из `buildApp` напрямую, а не через `app.register`:
Fastify инкапсулирует плагины, и `authenticate` или `requireMembership`, объявленный внутри
зарегистрированного, снаружи был бы не виден — а оба существуют ровно затем, чтобы их вешали
отовсюду.

Шага сборки нет: Node исполняет `.ts` напрямую, срезая типы. Значит, `enum`, `namespace` и
параметры-свойства конструктора не работают — `tsconfig.json` включает `erasableSyntaxOnly`,
так что `npm run typecheck` поймает это раньше рантайма.

Сервер слушает `0.0.0.0`, чтобы телефон или симулятор в той же сети мог до него достучаться.
