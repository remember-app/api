# remember-api

Бэкенд-API продукта **Remember** — единственная точка входа для мобильного приложения.
TypeScript + [Fastify](https://fastify.dev/) + Postgres.

Сейчас здесь скелет (m-7 Foundation), аккаунт целиком (m-3 Accounts), воспоминания с участниками
и медиа целиком: health-эндпоинт, подключение к базе, миграции, аутентификация запроса,
ник и управление сессиями, права на воспоминание, подписанные ссылки на загрузку в хранилище,
галерея воспоминания, скачивание оригиналов — одного файла и всей галереи — и удаление медиа,
поштучно и каскадом при уходе участника. Остальные сущности приходят со своими фичами.

Продуктовая плоскость и архитектурные решения — в корневом репозитории (`backlog/`,
`architecture.md`).

## Требования

- Node.js **≥ 22.18** (TypeScript выполняется движком напрямую, шага сборки нет).
- Docker — для локального Postgres и локального хранилища (MinIO).

## Запуск с чистой машины

```bash
npm install

# 1. Поднять локальный Postgres 16 (localhost:5432) и MinIO (localhost:9000)
docker compose up -d --wait

# 2. Задать окружение
cp .env.example .env

# 3. Накатить миграции
npm run migrate

# 4. Запустить сервер
npm run dev

# 5. Проверить
curl -i http://localhost:3000/health
# HTTP/1.1 200 OK
# content-type: application/json; charset=utf-8
# {"status":"ok"}
```

Тесты (интеграционные, против той же локальной базы и того же локального хранилища; миграции
накатываются сами, шагом `pretest`, поэтому поднятые Postgres и MinIO обязательны):

```bash
npm test
```

⚠️ `npm test` накатывает миграции и пишет в ту базу, на которую смотрит `DATABASE_URL`. Не
запускайте его с `.env`, направленным куда-либо кроме локальной базы.

Тест миграций (`src/migrations.test.ts`) гоняет цепочку в собственной временной базе — создаёт и
сам удаляет её, поэтому пользователю из `DATABASE_URL` нужно право `CREATE DATABASE` (у локального
Postgres из `docker-compose.yml` оно есть). Общие таблицы он не трогает.

## Локальный Postgres

`docker-compose.yml` в этом репозитории — **канонная локальная база всего продукта**: на неё
смотрят и `api`, и `montage`. Не поднимайте себе вторую.

```bash
docker compose up -d --wait   # поднять и дождаться готовности
docker compose down           # остановить (данные остаются в volume)
docker compose down -v        # остановить и стереть данные
```

Postgres 16, `localhost:5432`, база / пользователь / пароль — `remember` / `remember` / `remember`,
то есть:

```
DATABASE_URL=postgres://remember:remember@localhost:5432/remember
```

## Локальное хранилище

Тот же `docker-compose.yml` поднимает **MinIO** — это локальная замена Cloudflare R2. Протокол
один и тот же (S3), поэтому код в `src/media/r2.ts` не знает, с кем говорит: меняются только
значения `R2_*` в окружении.

- API хранилища — `http://localhost:9000`, бакет `remember` (заводится сам при первом старте
  контейнера), ключ / секрет — `remember` / `remember-secret`.
- Веб-консоль — `http://localhost:9001`, вход теми же ключами. Через неё видно, что реально
  долетело в бакет.
- Данные лежат в volume `miniodata`; `docker compose down -v` стирает их вместе с базой.

Подписанные ссылки собираются из `R2_ENDPOINT` как есть, и телефон идёт по ним сам. С реального
устройства `localhost` — это оно само, поэтому там нужен IP машины в сети:
`R2_ENDPOINT=http://192.168.1.10:9000`. На симуляторе и эмуляторе `localhost` работает.

Боевой R2 — тот же набор переменных с другими значениями (`R2_ENDPOINT` вида
`https://<account>.r2.cloudflarestorage.com`, `R2_REGION=auto`). Бакет и ключи заводит человек,
в коде их нет.

## Окружение

Одна обязательная переменная. Сервер и мигратор падают сразу, если её нет. Всё остальное имеет
значение по умолчанию — для загрузки не нужно ничего, кроме `DATABASE_URL`.

|------------------------------------|-------------|--------------|-------------------------------------------|

| `PORT`                             | нет         | `3000`       | порт HTTP-сервера                         |
| `NODE_ENV`                         | в бою — да  | —            | `production` запрещает обход почты на `/auth/email/start` при любых других настройках |
| `EMAIL_LOGIN_DEV_BYPASS`           | нет         | —            | `1`/`true` — обход почты для адресов на `test.test`; в бою не задавать |
| `SESSION_TTL_DAYS`                 | нет         | `30`         | срок жизни сессии                         |
| `EMAIL_LOGIN_TTL_MINUTES`          | нет         | `15`         | срок жизни кода входа                     |
| `EMAIL_LOGIN_MAX_ATTEMPTS`         | нет         | `5`          | попыток ввести код, прежде чем он умрёт   |
| `EMAIL_LOGIN_RATE_MAX`             | нет         | `5`          | заявок на вход за окно — на один ящик     |

Четыре `R2_*` без значения по умолчанию работают как пара client id: не заданы (или пустые) —
хранилища нет, и эндпоинты загрузки честно отвечают `503 {"error":"storage not configured"}`
вместо того, чтобы делать вид, что виноват клиент. Всё остальное работает и без них.

`EMAIL_LOGIN_MAX_ATTEMPTS` и `EMAIL_LOGIN_RATE_MAX` двигают только вместе: код из шести цифр — это
миллион вариантов, и перебор ограничивает их произведение. Пять попыток на код и пять кодов за
окно — двадцать пять догадок из миллиона за пятнадцать минут; поднять любую из двух вдвое значит
вдвое облегчить подбор. Попытки считаются на код, а не на адрес: кончились — код мёртв целиком,
даже для верных цифр, и нужен новый запрос.

`RESEND_API_KEY` и `MAIL_FROM` — то же правило для почты: нет обоих (или пустые) — письмо слать
нечем, и `POST /auth/email/start` отвечает `503 {"error":"mail not configured"}`. Сервис при этом
поднимается как обычно: вход по Apple и Google, сессии и всё остальное почты не касаются. Ключ
заводит человек в [Resend](https://resend.com), в коде его нет; отправитель должен быть на домене,
подтверждённом в Resend, иначе провайдер откажет.

`EMAIL_LOGIN_DEV_BYPASS` — единственная дверь мимо письма, и она узкая: обход срабатывает, только
если переменная задана (`1` или `true`, регистр не важен), адрес на домене `test.test` и режим не
боевой. Нет хотя бы одного из трёх — запрос идёт обычным путём: письмо, а без ключей почты `503`
(см. «Как войти в разработке»). Домен выбран не случайно: `.test` — зона, которую RFC 2606
резервирует навсегда, её нельзя зарегистрировать, и почтового сервера там не будет ни у кого.
Ключи почты на обход не влияют — письму на `test.test` всё равно некуда прийти. Значение, которого
переменная не понимает (`0`, `no`, пустое), значит «выключено»: это единственная переменная,
которая открывает, а не запирает, поэтому непонятое значение оставляет дверь закрытой.

Раньше эту дверь держал открытой один лишь незаданный `NODE_ENV` — то есть забытая на чужой машине
переменная превращала вход по email в раздачу кодов на любой адрес. Теперь незаданное значит
«закрыто» по всем трём условиям. `NODE_ENV=production` остаётся жёстким запретом сверху: в боевом
режиме обход невозможен, что бы ни стояло в `EMAIL_LOGIN_DEV_BYPASS`, поэтому в боевом окружении
`NODE_ENV` обязан быть задан. Значение сверяется без учёта регистра и лишних пробелов и по началу
слова — `Production`, `production ` и `prod` тоже считаются боевым режимом.

Лимиты — предложенные числа из `architecture.md` («Лимиты»). Они в окружении, а не в коде,
потому что их будут двигать, когда придёт настоящий материал, и админки для этого нет. Границы
длины ролика читаются один раз, при сборке приложения: ajv компилирует схему тела запроса заранее,
так что переменную нужно задать до старта, а не менять на живом процессе.

`INTERNAL_WORKER_TOKEN` — единственный ключ от `/internal/*`, куда стучится montage-воркер. Не
задан (или пустой) — маршрут закрыт для всех, и любой стук получает `401`: незаданный секрет это
«вход заперт», а не «вход свободен». Значение кладут в окружение обоих сервисов, и оно должно
совпадать до символа. Придумывать его руками не нужно и не стоит: маршрут висит на том же открытом
наружу порту, что и все остальные, и частота стуков ничем не ограничена — значит секрет должен быть
случайным: `openssl rand -base64 32`.

У `APPLE_CLIENT_ID` и `GOOGLE_CLIENT_ID` значения по умолчанию нет и быть не может: не задан
(или пустой — это та же опечатка) — значит провайдер выключен, и его эндпоинт отвечает `501`.
Пустая строка в роли `aud` сняла бы проверку аудитории вовсе, то есть приняла бы токен, выписанный
для чужого приложения.

Числовые значения проверяются: не число, ноль, отрицательное или дробное — это опечатка, а не
намерение, поэтому берётся значение по умолчанию. Иначе `EMAIL_LOGIN_RATE_WINDOW_MINUTES=-15` молча
снял бы ограничение частоты с единственного неавторизованного эндпоинта — а `=0.5` сделало бы ровно
то же самое, только выглядя осмысленно: все эти значения целые, и дробь округляется вниз до нуля.

Скрипты читают `.env` через встроенный `--env-file-if-exists` — никакого `dotenv`.
Значения из окружения перекрывают файл. `.env` в git не попадает.

## Миграции

Инструмент — [postgrator](https://github.com/rickbergfalk/postgrator): обычные `.sql`-файлы,
никакого DSL, состояние в таблице `schema_migrations`.

```bash
npm run migrate
```

Файлы лежат в `migrations/` и называются `<версия>.<do|undo>.<имя>.sql`:

```
migrations/001.do.init.sql     # применить
migrations/001.undo.init.sql   # откатить
```

Новая миграция — следующий номер и пара `do`/`undo`. Postgrator считает md5 применённых файлов,
поэтому **применённую миграцию не редактируют** — добавляют следующую.

Файл целиком уходит в Postgres одним запросом, то есть выполняется как одна неявная транзакция:
упавшая на середине миграция не оставит половину схемы. Отметка о версии пишется отдельным
запросом следом — если процесс убить ровно между ними, миграция окажется накатанной, но не
записанной, и следующий прогон её повторит. Поэтому миграции пишем идемпотентными
(`IF NOT EXISTS`).

### Таблица `jobs` — не наша

Очередь `jobs` принадлежит **montage** (`schema.sql`, `python -m montage init`); схему её API не
меняет. Своих строк у API три вида: `insert` задачи `media_preview` при завершении загрузки,
`delete` этой же задачи, когда удаляемое медиа перестало существовать (гнать воркера за тем, чего
уже нет, незачем), и `insert` задачи `montage` — при заказе ролика и при повторе упавшего.
Миграции на неё здесь нет и быть не должно — вместо этого `npm run migrate` в конце
**применяет файл соседа** (`../montage/schema.sql`, путь переопределяется `MONTAGE_SCHEMA_SQL`).
Так у схемы очереди остаётся один источник, а локальная база и `npm test` таблицу всё же имеют.
Файл идемпотентен, повторный прогон ничего не меняет.

Если соседа рядом нет (репозиторий API склонирован сам по себе), `npm run migrate` печатает об
этом строку и идёт дальше — таблицу тогда заводит montage сам, своей командой.

## API

### `GET /health`

Без авторизации. Контракт зафиксирован между репозиториями — мобильное приложение проверяет
ровно это, поэтому форма ответа не меняется:

```
200 OK
content-type: application/json; charset=utf-8

{"status":"ok"}
```

Тело — ровно `{"status":"ok"}`. Content-type Fastify всегда отдаёт с `; charset=utf-8` и убрать
его без onSend-хука нельзя, поэтому клиент сверяет заголовок **по префиксу**, а не на равенство.

Это liveness-проба: она отвечает `ok`, пока жив процесс, и ничего не говорит о базе. Связь с
Postgres проверяется один раз на старте — сервер не поднимется, если база недоступна.

### `POST /auth/email/start`

Без авторизации. Тело — `{"email": "...", "language": "ru"}`, где `language` необязателен. Заводит
пользователя, если такого адреса ещё не видели, выпускает одноразовый шестизначный код входа
и **отправляет его письмом** через Resend.

```
200 OK
{"ok":true}
```

Письмо уходит на языке, указанном в запросе, — и только в нём. Здесь ещё нет сессии, а для впервые
увиденного адреса нет и строки пользователя, так что читать `users.language` (см. `POST
/me/language`) неоткуда: язык кладёт в запрос само приложение, которое свой язык знает. Поля нет —
письмо русское, как и было до появления поля. Значение вне `ru`/`en` — `400` в стандартной форме
Fastify: это ошибка клиента, а не повод молча отправить не то письмо. Ни на ответ, ни на лимиты
язык не влияет — считаются ящик и IP, а не то, на каком языке попросили.

Ответ **одинаков** и для нового адреса, и для известного: иначе эндпоинт отвечал бы на вопрос
«этот человек у вас зарегистрирован?». Придушен по частоте за окно
`EMAIL_LOGIN_RATE_WINDOW_MINUTES`: отдельно на ящик (`EMAIL_LOGIN_RATE_MAX`, `+tag` не считается
за новый адрес) и отдельно, куда мягче, на IP (`EMAIL_LOGIN_RATE_MAX_PER_IP` — за одним адресом
сидит целый офис). Сверх лимита — `429 {"error":"too many requests"}`. Кривой адрес — `400`
в стандартной форме Fastify (`FST_ERR_VALIDATION`).

Живой код у человека ровно один: новая заявка заменяет предыдущий код, а не добавляет второй —
иначе пять заявок означали бы пять кодов, по которым можно угадывать одновременно.

Почта не настроена (нет `RESEND_API_KEY` или `MAIL_FROM`) — `503 {"error":"mail not configured"}`,
и это проверяется первым: пользователь не заводится, код не выпускается, лимит не тратится.
Единственное исключение — дверь для разработки: `EMAIL_LOGIN_DEV_BYPASS=1`, адрес на домене
`test.test` и не боевой режим. Тогда письма нет, а код приходит прямо в ответе —
`{"ok":true,"code":"043117"}` (см. «Как войти в разработке»). Любой другой адрес при
включённой переменной идёт обычным путём, а в боевом режиме обход не работает вовсе.
Провайдер не принял письмо (сеть, ключ, отказ API) — `502 {"error":"mail delivery failed"}`:
это не про адрес и не про клиента, поэтому не 4xx, и не про нас, поэтому не 500. Настоящая
причина уходит в лог строкой `login code not sent` и в ответе не появляется. Код при этом уже
выпущен и просто протухает — повтор выпускает новый.

Самого кода в логе нет: код — это ключ от аккаунта, а строка лога живёт дольше и видна большему
числу людей, чем письмо. В логе остаётся `login code sent` с адресом.

### `POST /auth/email/verify`

Без авторизации. Тело — `{"email": "...", "code": "043117"}`: код — секрет **адреса**, поэтому
проверяется пара. Гасит код и открывает сессию.

```
200 OK
{"token":"<токен сессии>","user":{"id":"…","username":null,"name":null,"email":"…","language":"ru"}}
```

Код одноразовый: он исчезает в тот же момент, а не просто протухает потом. Любой отказ — неверные
цифры, просроченный код, уже потраченный, незнакомый адрес, кончившиеся попытки — это одно и то же
`401 {"error":"invalid or expired code"}`: разница в ответе подсказывала бы, над какой половиной
пары работать дальше. Тело не из шести цифр — `400` в стандартной форме Fastify, до всякой проверки.

Шесть цифр — это миллион вариантов, то есть величина, которую перебирают, в отличие от 32-байтного
токена. Держат перебор две вещи. Во-первых, срок жизни: `EMAIL_LOGIN_TTL_MINUTES` (15 минут).
Во-вторых, счётчик попыток: `EMAIL_LOGIN_MAX_ATTEMPTS` (5) списывается на каждой попытке, и на нуле
код мёртв целиком — верные цифры после этого тоже получают `401`, нужен новый
`POST /auth/email/start`. Сам маршрут по частоте не придушен, и не нуждается: догадка вообще
доходит до проверки, только пока жив код, каждая тратит одну из его попыток, а выпуск кодов и
считает лимитер на `/auth/email/start`.

В базе лежит не код, а его scrypt-хеш с солью на строку. Сессионному токену хватает голого SHA-256
(угадывать в 32 случайных байтах нечего), а миллион вариантов по быстрому хешу перебирается за
секунды — украденный дамп не должен быть украденным входом.

### `POST /auth/apple`, `POST /auth/google`

Без авторизации. Тело — `{"idToken": "<id-токен от провайдера>"}`: приложение уже получило его
нативным SDK, сервер сам с провайдером не общается. Проверяются подпись по JWKS провайдера, `iss`,
`aud` (`APPLE_CLIENT_ID` / `GOOGLE_CLIENT_ID`) и `exp` — это `jose`. Ответ — ровно как у
`/auth/email/verify`:

```
200 OK
{"token":"<токен сессии>","user":{"id":"…","username":null,"name":"…","email":"…","language":"ru"}}
```

Пользователь заводится при первой встрече пары (провайдер, `sub`); `name` и `email` берутся из
токена, если он их несёт, иначе `null` — Apple имени не присылает, а адрес может быть скрытым
релеем. Токен не прошёл проверку любым способом (подпись, `aud`, `iss`, `exp`, не JWT) —
`401 {"error":"invalid token"}`, одинаково для всех причин: разница в ответе подсказывала бы, что
подделать. Провайдер без client id выключен — `501 {"error":"provider not configured"}`.

### `GET /me`

За `app.authenticate`. Отдаёт текущего пользователя — то же, что лежит в `request.user`:

```
200 OK
{"id":"…","username":null,"name":null,"email":"…","language":"ru"}
```

### `POST /me/consent`

За `app.authenticate`. Тела нет. Отмечает, что человек принял пользовательское соглашение — то
самое, где отдельной строкой названо распознавание лиц и животных на загруженных фото и видео
(doc-04, decision-9). Отвечает моментом принятия:

```
200 OK
{"accepted_at":"2026-09-18T12:00:00.000Z"}
```

**Это и есть регистрация:** без принятия нельзя получить ник (`POST /me/username` ниже), а ник —
то, что делает вошедшего зарегистрированным. Принять повторно не ошибка: ответ тот же и момент
тот же — сохраняется **первое** принятие, потому что именно тогда человек согласился. Повтор
случается по-настоящему: приложение переотправляет запрос, ответ на который потерялся, а тот, кто
вошёл снова, не успев выбрать ник, увидит экран соглашения второй раз.

Текст соглашения сервер не отдаёт — его несёт приложение. Версия соглашения не хранится: на пилоте
она одна, а вторая — это отдельная миграция вместе с решением, надо ли переспрашивать.

### `POST /me/username`

За `app.authenticate`. Тело — `{"username": "..."}`. Занимает ник, если его ещё нет, и меняет,
если есть, — это один и тот же запрос: прежний ник нигде не хранится и освобождается сразу.
Отвечает обновлённым пользователем, **ровно в форме `GET /me`**:

```
200 OK
{"id":"…","username":"kubik","name":null,"email":"…","language":"ru"}
```

Правила ника:

| Что                | Как                                                             |
|--------------------|-----------------------------------------------------------------|
| Набор знаков       | латинские буквы, цифры и разделители `_` `.` `-`                |
| Длина              | 3–30                                                            |
| Края               | разделитель не может стоять первым или последним знаком         |
| Регистр            | хранится как введён, но уникальность — регистронезависимая      |

Латиница намеренно: ник — это то, чем один человек указывает на другого при приглашении, а
кириллическая `а` неотличима от латинской `a`. `citext` сводит регистр, но не алфавиты, поэтому
Unicode-ник был бы готовым инструментом выдать себя за кого угодно.

Ник занят кем-то другим (в любом регистре) — `409 {"error":"username taken"}`. Сменить регистр
**своего** ника (`foo` → `Foo`) можно: это та же строка в базе. Не подходит под правила выше —
`400` в стандартной форме Fastify.

Ника ещё нет, а соглашение не принято — `403 {"error":"consent required"}`: первое занятие ника и
есть регистрация (`POST /me/consent` выше). **Смена** уже занятого ника соглашения не спрашивает —
человек уже зарегистрирован. Оба условия стоят в одном `UPDATE`, а не в отдельной проверке перед
ним: проверка в своём запросе может быть верна, когда выполняется, и неверна, когда доходит до
записи, а весь смысл этой двери — чтобы ник не достался непринявшему.

### `GET /me/username/available?username=<ник>`

За `app.authenticate`. Тот же вопрос, что и `POST /me/username`, но без попытки занять: поле ника
говорит «свободен» ещё до отправки формы.

```
200 OK
{"available":true}
```

Свой текущий ник — тоже `true`: отправить его обратно без изменений или сменить в нём регистр
`POST` разрешает, значит и здесь это не «занято». Ник не по правилам — `400` в стандартной форме
Fastify, тем же правилом и на том же месте, что и при занятии: тихое «свободен» на строке, которую
`POST` потом отвергнет, — обман поля.

### `POST /me/language`

За `app.authenticate`. Тело — `{"language": "ru"}` или `{"language": "en"}`; языка ровно два
(doc-8), третий — продуктовое решение и миграция, а не то, чем клиент может распорядиться сам.
Отвечает обновлённым пользователем, **ровно в форме `GET /me`**:

```
200 OK
{"id":"…","username":"kubik","name":null,"email":"…","language":"en"}
```

Язык выбирает приложение — сперва по языку телефона, дальше переключателем в профиле — и держит
эту строку в актуальном состоянии. Хранится на человеке, а не на устройстве, потому что тексты,
которые сервер пишет **для** человека, пишутся без его запроса: пуш о воспоминании уходит сразу
всем участникам, каждому на своём языке. Поле `NOT NULL`, у нового аккаунта `ru` — получателя без
языка не бывает. Что угодно кроме двух значений — `400` в стандартной форме Fastify.

### `GET /users?username=<ник>`

За `app.authenticate`. Поиск человека по нику, чтобы пригласить его в воспоминание. Совпадение
**точное** и регистронезависимое; префиксного и нечёткого поиска нет и в MVP не будет — иначе это
превращается в справочник всех пользователей.

```
200 OK
{"id":"…","username":"kubik","name":null}
```

Три поля и ни одного больше: ник можно подобрать, поэтому он не должен быть способом вытащить
чужой email. Никто такой ник не держит — `404 {"error":"not found"}`.

Запрос сначала проверяется тем же правилом, каким проверяется занятие ника, и всё, что под него
не подходит, — сразу `404`. Это не придирка: `citext` сводит регистр через `lower()` базы, а тот
отображает `İ` на `i` и `U+212A KELVIN SIGN` на `k`, так что незачищенный запрос `KUBİK` достал
бы настоящую строку `kubik`. Занять ник с такими знаками нельзя (только латиница), значит и найти
по ним нельзя — иначе «точное совпадение» было бы неправдой. Заодно это не пускает в базу
нулевой байт, который она сравнивать не умеет и отвечала на него `500`.

`400` здесь означает ровно одно — параметр `username` не передан вовсе.

### Контакты — как это устроено

Список контактов (doc-10) — это ники, которые человек сложил к себе, чтобы в следующий раз звать
этих людей в воспоминание, не набирая ник заново. **Это не друзья:** связь односторонняя. Согласия
не спрашивают, второй стороне ничего не сообщают, и попадание в чужой список не даёт ей ни
доступа к чему-либо, ни видимости. Взаимность — это просто две независимые строки.

Список плоский, только люди, и виден **исключительно хозяину**: все три маршрута ниже привязаны к
`request.user.id` и больше ни к чему — ни роль, ни участие в воспоминании до чужого списка не
дотягиваются. Поиска по списку на сервере нет: список у одного человека небольшой, приложение
фильтрует его у себя.

### `POST /me/contacts`

За `app.authenticate`. Кладёт человека в свой список по нику.

```
{"username": "anya"}
```

Ник ищется тем же `findByUsername`, что и `GET /users`, значит и ответы те же: ника нет или он в
принципе не мог быть занят → `404 {"error":"not found"}`. Совпадение точное и регистронезависимое.

```
200 OK
{"id":"…","username":"anya","name":"Аня"}
```

Те же три поля, что у `GET /users`, — у клиента одна форма пользователя, и почты в ней нет.
Повторное сохранение того же человека — тоже `200` и **не ошибка**: строка одна и та же, а
приложение предлагает «сохранить» рядом с каждым, кого не узнало. Сам себя — `400
{"error":"cannot add yourself"}`: список существует, чтобы звать других.

### `GET /me/contacts`

За `app.authenticate`. Свой список — голый массив, отсортированный по нику:

```
200 OK
[{"id":"…","username":"anya","name":"Аня"},{"id":"…","username":"bob","name":null}]
```

По нику, а не по времени сохранения, нарочно: список читают глазами и ищут по нему на клиенте, а
порядок, который меняется от захода к заходу, возвращает ровно ту «лень искать», ради которой
список и заведён. Чужие контакты сюда не попадают никогда.

### `DELETE /me/contacts/:userId`

За `app.authenticate`. Убирает человека из **своего** списка по его id пользователя.

```
200 OK
{"ok":true}
```

Тот, кого не сохраняли, уже удалённый и чужой контакт — один и тот же `404 {"error":"not found"}`:
иначе эндпоинт отвечал бы на вопрос «а есть ли этот человек в чьём-то списке?». `userId` не uuid —
тоже `404`, как и в `DELETE /memories/:memoryId/members/:userId`: домашнее правило для «убрать
человека из списка» — `404`, а не `400`.

### `GET /auth/sessions`

За `app.authenticate`. Живые сессии текущего пользователя — не отозванные и не протухшие,
свежая первой. `current` помечает ту, которой сделан этот самый запрос:

```
200 OK
[{"id":"…","created_at":"2026-09-02T…","expires_at":"2026-10-02T…","current":true}]
```

Список — голый массив: это перечень и ничего кроме. Чужие сессии в него не попадают.

`current` помечает **не больше одной** строки (`token_hash` уникален), но клиенту стоит держать
в уме и ноль: если ровно в этот момент текущую сессию погасили с другого устройства, она выпадет
из выборки живых. Это самолечится — следующий запрос этим токеном получит `401`.

### `POST /auth/sessions/:id/revoke`

За `app.authenticate`. Гасит одну **свою** сессию по id — «выйти на том телефоне».

```
200 OK
{"ok":true}
```

Чужой или несуществующий id — `404 {"error":"not found"}`, одинаково: иначе эндпоинт отвечал бы
на вопрос «существует ли такая сессия?». Повторный отзыв — тоже `200`, результат тот же. `id` не
uuid — `400`; форма `urn:uuid:…` тоже `400`, хотя ajv её за uuid считает, — Postgres не считает.

⚠️ Оба эндпоинта отзыва тела **не принимают**. Не ставьте на них `Content-Type: application/json`
с пустым телом: Fastify отвечает на это `400 FST_ERR_CTP_EMPTY_JSON_BODY` до всякой логики.
Либо не шлите заголовок, либо шлите телом `{}`.

### `POST /auth/logout`

За `app.authenticate`. Гасит ту сессию, чьим токеном сделан запрос. Остальные сессии
пользователя живы.

```
200 OK
{"ok":true}
```

После этого тот же токен получает `401` на любом маршруте — в том числе на повторном
`/auth/logout`. Тела не принимает — про пустой `Content-Type: application/json` см. выше.

### `POST /memories`

За `app.authenticate`. Заводит воспоминание и сразу — членство создателя в нём с ролью
`organizer`, одним запросом, то есть атомарно.

```
{"title": "Свадьба Ани", "event_start": "2026-09-02T18:00:00+03:00", "event_end": null}
```

| Поле          | Обязательно | Что это                                                      |
|---------------|-------------|--------------------------------------------------------------|
| `title`       | да          | непустое (одни пробелы не считаются), до 200 символов; хранится обрезанным по краям |
| `event_start` | да          | момент начала мероприятия, RFC 3339 **со смещением**          |
| `event_end`   | нет         | момент конца; можно не слать или прислать `null`              |

Даты — `timestamptz`, и клиент шлёт именно момент, а не голую дату: по этому окну m-1 отбирает
медиа из галереи участника по времени съёмки. Голая дата (`2026-09-02`) отвергается с `400` —
иначе её пришлось бы растянуть в окно по часовому поясу сервера, а он не тот, в котором люди
были на мероприятии.

```
201 Created
{"id":"…","organizer_id":"…","title":"Свадьба Ани",
 "event_start":"2026-09-02T15:00:00.000Z","event_end":null,
 "storage_bytes":"0","media_count":0,"montage_count":0,
 "created_at":"…","role":"organizer","cover_media_id":null,
 "cover_thumbnail_url":null,"recent_thumbnail_urls":[],
 "member_count":1,"contributed_member_count":0}
```

Отказы: пустой или отсутствующий `title`, отсутствующий или не-RFC-3339 `event_start` — `400`
в стандартной форме Fastify. `event_end` раньше `event_start` — `400
{"error":"event_end is before event_start"}` (моменты сравниваются как моменты: текстом
`…T01:00+03:00` идёт *после* `…T00:00Z`, а на деле на два часа раньше).

**`storage_bytes` — строка, а не число.** Колонка `bigint`, и postgres.js отдаёт такие строкой,
чтобы не округлить за пределами 2^53. Складывать её на клиенте как число нельзя.

### `GET /memories`

За `app.authenticate`. Главный экран: воспоминания, в которых вызывающий состоит — и как
организатор, и как приглашённый. Организатор держит обычную строку в `memory_members`, поэтому
особого случая тут нет.

```
200 OK
[{…то же тело, что у POST, включая "role"…}]
```

Порядок — сначала самые свежие по `event_start`, при равенстве по `created_at`. Чужие
воспоминания не видны; ответ — в точности массив тех же объектов, что отдаёт `POST /memories`,
так что созданное кладётся в начало списка как есть.

`recent_thumbnail_urls` — до **четырёх** последних кадров воспоминания: карточка на главном экране
рисует ими хвост из настоящих фотографий. Ссылки подписанные и живут те же
`R2_DOWNLOAD_TTL_SECONDS`, что и в галерее; ведут они на превью (`thumbnail_key`), а не на
оригиналы. Порядок — самое свежее первым, по времени съёмки, а для файла без даты по времени
загрузки: тот же порядок, что и в галерее, только с конца.

`contributed_member_count` и `member_count` — сводка по участникам: сколько уже принесли материал и
сколько их всего, включая организатора. Это строка на карточке главного экрана — «7 из 9 уже скинули
свои кадры» — и живёт она тут, а не в ростере, чтобы экран не делал по запросу на карточку.
**Принёс — это `done` или `nothing`**: оба ответа означают, что этого участника больше не ждут.
`more_coming` не считается — материал ещё в пути, `not_started` не считается — на него не отвечали
(doc-06, значения — в «Статусе вклада» ниже). **Зрители (`viewer`) не входят ни в одно из двух
чисел**: их не звали приносить материал, и в знаменателе они держали бы полосу недозаполненной
навсегда. У свежего воспоминания это `0` из `1`: в нём один организатор, и он ещё ничего не
загрузил. Числа — числа, а не строки: `count()` в Postgres `bigint`, и он приведён к `int`
специально.

`cover_media_id` и `cover_thumbnail_url` — обложка: кадр, который организатор выбрал лицом
воспоминания (`PATCH /memories/:memoryId` ниже). Ссылка ведёт на превью и подписана так же, как
ссылки хвоста. Обложка не выбрана — оба поля `null`, и карточка рисуется ровно так, как рисовалась
до того, как обложка появилась. Хвост от обложки не зависит: это разные поля, и что из них рисовать,
решает клиент.

Всё считается **одним запросом** на весь список — по кадрам на воспоминание не ходят отдельно.
Записи, которым воркер ещё не сделал превью, в хвост не попадают, так что у свежего воспоминания
он пустой. Пустой он и когда не заданы `R2_*`: подписать нечем, но главный экран должен
нарисоваться — в отличие от галереи, где ссылки и есть весь ответ и потому там `503`.

### `PATCH /memories/:memoryId`

За `app.authenticate` + `app.requireMembership`. Кнопка «Изменить название, даты и обложку» на
экране настроек воспоминания — одна кнопка, один маршрут. **Только организатор**: участник любой
другой роли получает `403 {"error":"forbidden"}`, не участник — `404 {"error":"not found"}`, как
везде в этом семействе.

```
{"title": "Свадьба Ани", "event_start": "2026-09-02T18:00:00+03:00",
 "event_end": null, "cover_media_id": "…"}
```

| Поле             | Что это                                                                  |
|------------------|--------------------------------------------------------------------------|
| `title`          | те же проверки, что при создании: непустое, до 200 символов, хранится обрезанным |
| `event_start`    | момент, RFC 3339 со смещением — голая дата отвергается так же, как при создании |
| `event_end`      | момент конца; `null` — снять конец, сделав окно одним днём                |
| `cover_media_id` | id кадра этого воспоминания; `null` — снять обложку                       |

Обязательных полей нет — уходит то, что тронули, — но пустое тело (`{}`) это `400`: ничего не
менять и получить `200` значит соврать, что что-то поменялось. Поля, которых в списке нет, ajv
молча выбрасывает (так настроен Fastify по всему сервису) — поэтому тело из одних таких полей
(опечатка в имени: `coverMediaId`) — тот же `400`: после выбрасывания оно пустое.

Окно проверяется **по строке, какой она станет**, а не по тому, что прислали: сдвинуть один только
`event_start` за уже записанный `event_end` — тот же `400 {"error":"event_end is before
event_start"}`, что и при создании.

Обложка — **готовый кадр этого же воспоминания**: `status = 'ready'` и превью уже снято. Кадр
соседнего воспоминания, кадр, который воркер ещё не доделал, и id, за которым ничего нет, — один и
тот же `404 {"error":"not found"}`: выбрать их нельзя, и чем именно они не подошли, ответ не
разбирает (то же правило, что у `/media/:mediaId/download`). Значение, которое вовсе не uuid, — это
`400` от схемы.

```
200 OK
{…ровно то же тело, что у POST /memories и GET /memories…}
```

Отвечает карточкой целиком — со счётчиками, хвостом кадров и обложкой, — чтобы экран заменил то,
что держит, и не ходил за списком второй раз.

### `DELETE /memories/:memoryId`

За `app.authenticate` + `app.requireMembership`. **Только организатор**: участник любой другой роли
получает `403 {"error":"forbidden"}`, не участник — `404 {"error":"not found"}`, как и `memoryId`,
который вовсе не uuid. Организатор из своего воспоминания не выходит (`409` выше) — удалить его
целиком и есть его единственный выход (doc-01).

```
200 OK
{"ok": true}
```

**Уходит всё, что на воспоминании висело.** В одной транзакции:

| Что                                                          | Чем уносится                              |
|--------------------------------------------------------------|-------------------------------------------|
| кадры, счётчики `user_usage` загрузивших, задачи очереди о них | `removeMedia` — тот же, что у удаления кадра и ухода участника |
| ролики, их журналы, этапы, зрители и раскладка кадров         | строка `montages` + каскады миграции 130   |
| незапущенные задачи `montage` этих роликов                    | снимаются с очереди тем же запросом        |
| треки организатора (`music_uploads`)                          | своим запросом — их ключи нужны хранилищу  |
| участники, приглашения, лейблы и их содержимое                | каскадом от `memories`                     |
| описания и расшифровки воркера (`media_understandings`, `media_speech`) | `removeMedia`: внешних ключей у этих таблиц нет и каскад их не заберёт |

Объекты из хранилища — оригиналы, деривативы, ролик, его обложка и трек — удаляются **после**
коммита, недоделанные multipart-загрузки обрываются; порядок и его причина те же, что у «Материал
уходит вместе с человеком» ниже.

Журнал запросов к нейросети (`ai_requests`) **остаётся**: doc-03 требует хранить все запросы к
модели для разбора, и это журнал сервиса, а не материал воспоминания.

Сборка, которая уже идёт у воркера, не отменяется — отменять её некому. Она дописывает ролик, не
находит строки `montages` и сама убирает из хранилища то, что успела залить (montage,
`video/montage.py`: «went away mid-assembly»); задача, до которой очередь ещё не дошла, снимается
здесь.

### `POST /memories/:memoryId/members`

За `app.authenticate` + `app.requireMembership`. Зовёт человека по нику. Вызывающий должен быть
`contributor` или `organizer` — `viewer` получает `403 {"error":"forbidden"}`.

```
{"username": "anya", "role": "contributor"}
```

`role` — только `viewer` или `contributor`; `organizer` не выдаётся никогда и никому (у
воспоминания он один, его создатель), поэтому такое значение — `400`. Ник ищется точным
совпадением тем же кодом, что и `GET /users` (`findByUsername` в `src/auth/identity.ts`) — ника нет
или он в принципе не мог быть занят → `404 {"error":"not found"}`.

```
200 OK
{"id":"…","username":"anya","name":"Аня","role":"contributor"}
```

Повторный вызов на уже добавленного — тоже `200`, и **ничего не меняет**: в ответе приходит та
роль, которую человек держит, а не та, которую попросили. Так «пригласить» организатора не
понижает его до `viewer`. `invited_by` записывается на того, кто позвал, а не на организатора.

Успешное **добавление** (не повторное) шлёт приглашённому пуш — см. «Пуши» ниже.

### `GET /memories/:memoryId/members`

За `app.authenticate` + `app.requireMembership`. Кто состоит в воспоминании — **все участники,
включая организатора** (у него обычная строка в `memory_members`).

```
200 OK
[{"id":"…","username":"anya","name":"Аня","role":"organizer","contribution_status":"more_coming","media_count":128},
 {"id":"…","username":"bob","name":null,"role":"contributor","contribution_status":"not_started","media_count":0},
 {"id":"…","username":"kk","name":"Костя","role":"viewer","contribution_status":null,"media_count":0}]
```

**Читать может любой участник, `viewer` в том числе** — порога `contributor` здесь нарочно нет:
матрица даёт `viewer` «смотреть», и увидеть, кто ещё был на мероприятии, — это оно и есть.

Поля — ровно те же три, что отдаёт `GET /users`, плюс `role`, `contribution_status` и
`media_count`: у клиента одна форма пользователя на всё приложение. **Почты здесь нет и не будет**
— список открыт каждому, кто пришёл по ссылке, и адресной книгой он стать не должен. `invited_by`
не отдаётся: клиенту с этим uuid делать нечего.

`contribution_status` — прогресс участника по материалу, тот самый экран «кто уже скинул» (doc-06);
что означает каждое значение — в «Статусе вклада» ниже. Поле названо длинно нарочно: рядом на
клиенте лежит медиа со своим `status`, и это совсем про другое. **У `viewer` тут всегда `null`** —
не значение из его строки: его не звали приносить материал, и «ничего не загрузил» над ним было бы
упрёком за работу, которой ему не давали. Экран рисует зрителей отдельной группой без статуса
(`design/screens/MemorySettings.html`), и то же правило держит их вне «N из M» в `GET /memories`.
`null`, а не отсутствующий ключ: форма строки одна на всех.

`media_count` — сколько кадров этот человек принёс **в это воспоминание** (не всего по продукту:
счёт на участии, как и статус). Это число рядом со статусом на экране настроек. Считаются те же
записи, что отдаёт галерея, — всё, кроме `pending_upload`, за которым ещё нет байтов, — поэтому
число сходится с тем, что видно в самой галерее. Раньше клиент считал его сам, вычитывая всю
галерею; теперь не надо.

Порядок — по времени вступления, поэтому организатор идёт первым. Не участник, несуществующее
воспоминание и кривой id — общий `404 {"error":"not found"}` от самой проверки.

### Статус вклада

У каждого участника внутри воспоминания есть статус того, что он принёс, — колонка
`memory_members.status`. Он **на участии, а не на человеке**: один и тот же человек может всё
скинуть в одно воспоминание и ничего в другое.

| Значение      | Что это                                                      | Кто ставит                     |
|---------------|--------------------------------------------------------------|--------------------------------|
| `not_started` | позвали, ничего не загружено и ничего не сказано              | само, при добавлении в память  |
| `more_coming` | что-то принёс и ещё будет                                     | сам участник; API — на первой загрузке и поверх `nothing` |
| `done`        | «это всё, больше не буду»                                     | сам участник                   |
| `nothing`     | «материала от меня не будет»                                  | сам участник                   |

**Статус есть только у тех, кого звали приносить материал** — у организатора и у `contributor`. У
`viewer` его нет: в ростере на его месте `null`, поставить его он не может (`403`), и ни в одно из
чисел «N из M» он не входит. Строка в базе у него, как у всех, лежит в `not_started` — это просто
значение по умолчанию колонки, наружу оно не отдаётся.

**Ни один из трёх не запирает дверь.** Участник в любой момент меняет свой статус на любой из них,
в том числе из `done` и `nothing` обратно в `more_coming` (на экране `not_started` и `more_coming`
читаются одной строкой — «Планирует загрузить»). Сказал «это всё», а потом вспомнил про второй
телефон — сказал «ещё будет», и организатор перестаёт считать его закончившим.

`done` и `nothing` оба — слово самого участника, и API их не переписывает, с одним исключением:
`nothing` — это утверждение о будущем, и загрузка его опровергает, поэтому пришедший файл переводит
участника из `nothing` в `more_coming`. Иначе у организатора в ростере навсегда оставалось бы
«ждать нечего» над человеком, чьи фотографии лежат в галерее, и починить это в приложении было бы
нечем. `done` при этом не трогается: он от новых файлов устаревает, но не становится ложью, а
переспрашивать уже отвеченное незачем. Промежуточного «напомнили» нет: автонапоминания вне MVP
(decision-03).

**Статус не режет права.** Ни загрузка, ни просмотр, ни приглашения на него не смотрят — это
табличка для организатора, а не ещё один уровень доступа (doc-06).

### `POST /memories/:memoryId/contribution-status`

За `app.authenticate` + `app.requireMembership`. Участник ставит статус **себе** — либо отвечая на
вопрос приложения после первой загрузки, либо сам по себе, ничего не загрузив.

```
{"status": "nothing"}
```

```
200 OK
{"status":"nothing"}
```

Принимаются три значения: `more_coming`, `done` и `nothing` — ровно те, что предлагает экран
настроек, и **в любом порядке, сколько угодно раз**: вернуться из «всё загрузил» в «ещё будет»
можно всегда. `not_started` не принимается: это то, что оставляет после себя приглашение, и просить
его обратно незачем — рядом со статусом стоит число уже принесённых кадров, которое такому ответу
противоречит. Любое другое значение — `400` в стандартной форме Fastify.

**`viewer` получает `403 {"error":"forbidden"}`** — единственный порог по роли, какой у статуса
есть. Его не звали приносить материал, организатор его не ждёт, и статус на его строке затащил бы
его в сводку, в которой его не считают. Остальным статус по-прежнему ничего не даёт и не отнимает.
Чужой статус не ставится никак — в маршруте нет `:userId`, и ставится он всегда вызывающему.

Не участник, несуществующее воспоминание и кривой id — общий `404 {"error":"not found"}`, без
сессии — `401`.

### `GET /memories/:memoryId/invite`

За `app.authenticate` + `app.requireMembership`, тот же порог `contributor`. Отдаёт действующую
ссылку-приглашение и **заводит её, если её ещё нет** — клиенту нечего делать с ответом «ссылки
пока нет», он спрашивает ровно в момент тапа по «поделиться».

```
200 OK
{"token":"XfxBlXErAGL8Gbteai_kfTAa6Zo0IoG5EoFOx8Pwt3Y","role":"contributor"}
```

Живая ссылка у воспоминания ровно одна — это держит частичный уникальный индекс
`invites_one_active_idx`, а не код. Второй вызов вернёт ту же самую. Заведённая на первом запросе
даёт `contributor`: людей зовут, чтобы они принесли материал.

`token` — непрозрачные 32 случайных байта; сам deep link из него собирает приложение.

### `POST /memories/:memoryId/invite`

Там же и с тем же порогом. Отзыв и есть выпуск новой: старый `token` помечается `revoked_at` и
сразу же заводится новый. Другого «отозвать» нет — у воспоминания всегда есть ссылка.

```
{"role": "viewer"}     // необязательно; без тела или без поля — "contributor"
```

```
200 OK
{"token":"…новый…","role":"viewer"}
```

Этим же меняется уровень, который ссылка выдаёт: старая ссылка после этого не пускает никого.
Тело можно не слать вовсе — `POST` без тела означает «просто дай новую».

### `POST /invites/accept`

**Только** за `app.authenticate`, без `app.requireMembership`: вызывающий как раз ещё не участник.
Веб-страницы приглашения нет и не будет (decision-01) — ссылка открывает приложение, а у того, кто
по ней пришёл, уже есть аккаунт.

```
{"token": "XfxBlXErAGL8Gbteai_kfTAa6Zo0IoG5EoFOx8Pwt3Y"}
```

```
200 OK
{…ровно то же тело, что у POST /memories, с "role" из приглашения…}
```

Отдаётся всё воспоминание целиком, чтобы приложение открыло экран загрузки сразу, без второго
запроса. Уже участник — тоже `200`, роль остаётся прежней: ссылка это вход, а не способ сменить
уровень. Отозванный и несуществующий токен — один и тот же `404 {"error":"not found"}`: по
старой ссылке нельзя узнать даже того, что она когда-то работала.

Пуш здесь **не** шлётся: человек пришёл сам и знает, куда попал.

### `DELETE /memories/:memoryId/members/:userId`

За `app.authenticate` + `app.requireMembership`. Исключение и выход — это одно действие над одной
строкой, и разница только в том, себя удаляют или другого:

| Кто           | Кого                | Что                                              |
|---------------|---------------------|--------------------------------------------------|
| `organizer`   | любого другого      | `200 {"ok":true}`                                 |
| любой участник| себя (выход)        | `200 {"ok":true}`                                 |
| не `organizer`| другого             | `403 {"error":"forbidden"}`                       |
| `organizer`   | себя                | `409 {"error":"organizer cannot leave the memory"}`|

Организатор выйти не может: не осталось бы никого, кто может исключать, удалять чужое медиа и
заказывать ролик, а передача роли — вне MVP (doc-01). Кого в воспоминании нет — и `userId`, который
вовсе не uuid, — это `404 {"error":"not found"}`, тем же телом, что и всё остальное в этом
семействе маршрутов.

**Материал уходит вместе с человеком.** В той же транзакции, что и строка `memory_members`,
пропадает всё, что он загрузил в это воспоминание: записи `media_items`, счётчики воспоминания и
его `user_usage` — вниз, задачи `media_preview` — из очереди. Оригиналы и деривативы удаляются из
хранилища **после** коммита (`architecture.md`, «Выход / исключение участника»).

Уже смонтированные ролики не трогаются, даже если там его кадры (m-2). Материал остальных
участников остаётся на месте — уходит ровно то, что принёс уходящий.

Там же и его лейблы: личные уходят с ним, общие остаются, хозяином им становится организатор —
см. «Лейблы — как это устроено».

Порядок «сначала база, потом хранилище» не случаен: у R2 нет отката, поэтому объект, удалённый до
коммита, при откате оставил бы записи, указывающие в пустоту. Наоборот — остаются байты, на которые
никто не ссылается, и это стоит только места. Если хранилище не ответило, записей уже нет, а строка
об осиротевших ключах уходит в лог: выход из воспоминания не может упереться в недоступный R2.

### Загрузка медиа — как это устроено

Байты в API **не приходят**. Приложение говорит «хочу загрузить», получает подписанные ссылки и
льёт файл прямо в хранилище, а потом сообщает, что закончило:

1. `POST /memories/:memoryId/media` — проверяются права и лимиты, заводится запись `media_items`
   в статусе `pending_upload`, в ответ — подписанные ссылки на куски (multipart).
2. Приложение шлёт `PUT` на каждую ссылку своим куском файла и запоминает заголовок `ETag`
   каждого ответа.
3. `POST /memories/:memoryId/media/:mediaId/complete` со списком кусков и их `ETag` — API
   собирает объект в хранилище, переводит запись в `processing`, двигает счётчики и ставит
   воркеру задачу `media_preview`.

Ссылки живут час (`R2_UPLOAD_TTL_SECONDS`). Протухли — `GET /memories/:memoryId/media/:mediaId/upload`
выдаёт новые **для той же записи и той же multipart-загрузки**: уже отправленные куски
остаются в хранилище, догрузка продолжается с места обрыва, а не начинается заново.

### `POST /memories/:memoryId/media`

За `app.authenticate` + `app.requireMembership`. Порог — `contributor`: `viewer` получает
`403 {"error":"forbidden"}` (матрица даёт ему смотреть, но не приносить).

```
{"kind": "photo", "size_bytes": 4194304, "captured_at": "2026-09-02T19:30:00+03:00"}
```

| Поле               | Обязательно     | Что это                                                     |
|--------------------|-----------------|--------------------------------------------------------------|
| `kind`             | да              | `photo` или `video`                                          |
| `size_bytes`       | да              | размер файла целиком; по нему считается число кусков          |
| `captured_at`      | нет             | момент съёмки из галереи, RFC 3339 со смещением; `null` — файл без даты |
| `duration_seconds` | **для видео**   | длительность; без неё видео не принять — нечем проверить лимит |
| `file_name`        | нет             | как файл называется на телефоне, до 255 символов; показывается в «Сведениях о кадре» |

`file_name` необязателен и останется таким: приложение начнёт его слать отдельной задачей, а всё
загруженное до того живёт без него. Хранится как пришло — его никто не разбирает, только
показывают; вырезается лишь NUL (его не держит ни одна `text`-колонка), пробелы по краям
срезаются, и пустая строка после этого — то же самое, что «не прислали».

```
201 Created
{"id":"…","status":"pending_upload",
 "upload":{"key":"originals/…","upload_id":"…","part_size":8388608,
           "parts":[{"part_number":1,"url":"http://…&X-Amz-Signature=…"}],
           "expires_at":"2026-09-03T12:00:00.000Z"}}
```

Файл режется на куски по `part_size`, кусок номер N уходит на `parts[N-1].url` методом `PUT`.
Ключ оригинала — по id записи, и он приходит в ответе: собирать его на клиенте не нужно.

Отказы по лимитам — до того, как что-либо записано: **записи и ключа в хранилище не остаётся**.

| Ответ | Тело                                                        | Когда                          |
|-------|-------------------------------------------------------------|--------------------------------|
| `413` | `{"error":"file is too large","limit_bytes":1073741824}`     | файл больше потолка            |
| `413` | `{"error":"video is too long","limit_seconds":300}`          | видео длиннее потолка          |
| `409` | `{"error":"memory is full","limit_files":1000}`              | в воспоминании больше нельзя файлов |
| `409` | `{"error":"memory is out of space","limit_bytes":10737418240}` | не хватает объёма            |
| `400` | `{"error":"duration_seconds is required for a video"}`       | видео без длительности         |
| `503` | `{"error":"storage not configured"}`                         | не заданы `R2_*`               |

Счётчики воспоминания двигаются в момент завершения загрузки, а не выдачи ссылки, поэтому пачка
загрузок «в полёте» может перебрать потолок на то, что летит. Следующая заявка тогда откажет.

### `GET /memories/:memoryId/media/:mediaId/upload`

За `app.authenticate` + `app.requireMembership`. Та же запись, та же multipart-загрузка, свежие
подписи. Тело — как у `POST` выше.

Новой записи не заводится и уже загруженные куски не теряются — это и есть докачка.

Чужая запись, запись из другого воспоминания, несуществующая и кривой `mediaId` — общий
`404 {"error":"not found"}`. Доделать загрузку может только тот, кто её начал: это не про роль, а
про владение. Запись, которая уже не `pending_upload`, — `409
{"error":"upload is already finished","status":"processing"}`.

### `POST /memories/:memoryId/media/:mediaId/complete`

За `app.authenticate` + `app.requireMembership`, та же проверка владения. Куски — все, что были
отправлены, с их `ETag` из ответов хранилища.

```
{"parts": [{"part_number": 1, "etag": "\"254a7725306413d2a8e39ad05ffa018a\""}]}
```

```
200 OK
{"id":"…","status":"processing","first_upload":true}
```

Внутри одной транзакции: запись переходит в `processing`, у воспоминания растут `storage_bytes` и
`media_count`, у загрузившего — строка `user_usage`, в `jobs` встаёт задача `media_preview`, и —
если он стоял в `not_started` или в `nothing` — его `contribution_status` переходит в
`more_coming`.

`first_upload` — это «переход из `not_started` только что случился»: по нему приложение задаёт
вопрос «всё загрузили или ещё будете?» (doc-06) и шлёт ответ в
`POST /memories/:memoryId/contribution-status`. Приходит в каждом ответе, `false` во всех
остальных случаях — второй загрузкой, повторным колбэком и статусами `more_coming` и `done`.

Сказал «ждать нечего» и всё-таки что-то залил — статус чинится сам (`nothing` → `more_coming`),
но вопрос не задаётся: `first_upload` остаётся `false`. Своё слово человек уже сказал, а ростер
организатора после этого перестаёт врать.

**Повторный вызов безопасен** — телефон, не дождавшийся ответа, зовёт снова и получает то же
самое: счётчики не сдвигаются второй раз, вторая задача не ставится и `first_upload` приходит
`false`. В ответе — текущий статус записи, каким бы он к тому моменту ни стал (воркер мог уже
увести её в `ready`).

Записывается **тот размер, который хранилище реально держит**, а не заявленный в первом шаге:
заявленный проверяется лимитами, но занизить его в счётчиках нельзя. Если объекта в хранилище
нет — `409 {"error":"the upload is not in storage"}`, запись остаётся `pending_upload`, и загрузку
можно доделать.

### `GET /memories/:memoryId/media`

За `app.authenticate` + `app.requireMembership`. Галерея воспоминания — **весь** материал, чей бы
он ни был. Читает её любой участник, `viewer` в том числе: матрица даёт ему «смотреть галерею».

```
200 OK
[{"id":"…","kind":"photo","status":"processing","uploaded_by":"…",
  "size_bytes":"4096","captured_at":"2026-09-02T16:30:00.000Z",
  "width":null,"height":null,"duration_seconds":null,"created_at":"…",
  "label_ids":["…","…"],
  "thumbnail_url":"http://…&X-Amz-Signature=…","preview_url":null,
  "screening_rejected":true,"screening_reason":"blur"}]
```

Порядок — **по времени съёмки**, а для файла без даты по времени загрузки: то же правило, по
которому воркер расставляет кадры в ролике (`architecture.md`, «Montage-пайплайн»), чтобы галерея
читалась в том же порядке, в каком ролик играет.

Записи в статусе `pending_upload` в список **не попадают** — байтов за ними ещё нет. `failed`
попадают: клиент рисует плейсхолдер и предлагает повторить.

Ссылки — только на **деривативы** и только подписанные, живут `R2_DOWNLOAD_TTL_SECONDS` (15 минут).
Пока воркер не сделал превью, `thumbnail_url` и `preview_url` — `null`; это не ошибка, а «ещё не
готово». Оригинал отсюда не отдаётся: галерея показывает лёгкую версию, а оригинал уходит только
тогда, когда его попросили, — двумя маршрутами `/download` ниже. Протухли — клиент просто
запрашивает список заново.

**Лейблы кадра** — `label_ids`: в каких коробках он лежит (doc-13). Только в тех, что **видны
спрашивающему**: общие лейблы воспоминания и его собственные личные. Чужой личный лейбл не
оставляет здесь следа — ни id, ни лишней длины массива. Кадр, не лежащий нигде, приходит с пустым
массивом. Состав и порядок галереи от лейблов не зависят вовсе, и кадр не дублируется, сколько бы
лейблов на нём ни было: это подзапрос-массив, а не join. Порядок внутри массива — тот же, что у
`GET /memories/:memoryId/labels`: сперва общие, внутри по названию. Отбирать галерею по лейблу
сервер не умеет и не должен: она приходит без параметров и фильтруется на телефоне.

**Автоматический отсев брака** (doc-03) приходит теми же двумя полями: `screening_rejected` —
отбраковал ли анализ этот кадр, `screening_reason` — почему (`unreadable`, `blur`, `exposure` и
что воркер научится видеть дальше; у оставленного кадра — `null`). Пишет их воркер, ровно как
`thumbnail_key`/`preview_key`, а API только отдаёт. Пока анализ до кадра не дошёл, оба поля —
`null`, и это «ещё не посчитано», а не «кадр годный»: `false` означало бы, что анализ посмотрел и
оставил. Это **предложение**, а не решение — организатор правит его перед заказом ролика, и на то,
какие кадры войдут в ролик, поля сами по себе не влияют: воркер при заказе судит каждый файл заново
тем же анализом. Предел длины ролика по ним при этом считается — отсеянное в него не идёт (см.
«Длина — число секунд в пределе воспоминания» у заказа).

Словарь причин — воркера (`projects/montage/screening.py`), здесь он только перечислен. `duplicate`
в это поле не приходит **никогда**: дубль определяется сравнением кадра с соседями, а не по нему
одному, и решается это при заказе ролика, а не на самой записи.

Не заданы `R2_*` — `503 {"error":"storage not configured"}`: подписать нечем, и список из одних
`null` был бы неправдой. Не участник, несуществующее воспоминание и кривой id — общий
`404 {"error":"not found"}`.

### `GET /memories/:memoryId/media/:mediaId`

За `app.authenticate` + `app.requireMembership`. Лист «Сведения о кадре» (doc-02, макет
`design/screens/SheetFrameInfo.html`) — всё про один кадр, чего не видно по самой картинке. Читает
любой участник, `viewer` в том числе: матрица даёт ему «смотреть галерею», а это один её кадр
словами.

```
200 OK
{"id":"…","file_name":"IMG_4471.HEIC","size_bytes":"4404019",
 "captured_at":"2026-09-13T18:47:00.000Z","created_at":"2026-09-15T09:12:00.000Z",
 "width":4032,"height":3024,
 "camera_model":"iPhone 15 Pro","focal_length_mm":24,"aperture":1.8,
 "latitude":55.518,"longitude":37.53,
 "uploaded_by":{"id":"…","username":"mark","name":"Марк Ковалёв","media_count":96},
 "montages":[{"id":"…","duration_seconds":90,"start_seconds":72.5}]}
```

Ссылок здесь нет и хранилище не спрашивается: лист открывается поверх кадра, который приложение уже
показывает, — миниатюра пришла с галереей. Поэтому `503` у этого маршрута не бывает.

| Поле                        | Что это                                                        |
|-----------------------------|----------------------------------------------------------------|
| `file_name`                 | имя файла с телефона; **ключа нет**, если имени нет             |
| `size_bytes`                | размер в байтах, строкой (bigint без округления)               |
| `captured_at`               | время съёмки; `null` — файл без даты                            |
| `created_at`                | когда кадр принесли                                            |
| `width`, `height`           | размеры в пикселях; `null`, пока воркер не измерил              |
| `camera_model`              | модель камеры: `iPhone 15 Pro`                                  |
| `focal_length_mm`           | фокусное расстояние в мм                                        |
| `aperture`                  | диафрагменное число: `1.8` — это «f/1.8»                        |
| `latitude`, `longitude`     | координаты съёмки                                               |
| `uploaded_by`               | кто принёс: `id`, `username`, `name` — и `media_count`          |
| `montages`                  | в каких готовых роликах кадр стоит и на какой секунде           |

`file_name` приходит, только если он есть: у кадров, загруженных до того, как приложение начало
слать имя, ключа в ответе просто нет — строка на экране не рисуется, и клиенту не приходится
отличать «имени нет» от пустого.

`uploaded_by.media_count` — сколько кадров этот человек принёс **в это воспоминание** («всего 96
кадров» на макете), а не всего в продукте: считаются те же записи, что показывает галерея, то есть
`pending_upload` не в счёт.

«Место» — это координаты, и только они. Названия («Усадьба «Остафьево»» на макете) здесь нет:
превратить координаты в название может только внешний геокодер, а это платный сервис и регистрация
— нужно ли продукту название, решает chief.

`montages` — только **готовые** ролики этого же воспоминания, новые сверху, как и в списке роликов.
`duration_seconds` там — длина самого ролика, `start_seconds` — секунда, на которой в нём стоит
этот кадр. Имени у ролика пока нет: шаблоны заводит веха Montage order, а до неё клиент собирает
«Ролик на 1:00» из длительности.

Кадр из другого воспоминания, несуществующий, `mediaId`, который вовсе не uuid, и запись в
`pending_upload` (байтов за ней ещё нет, и в галерее её тоже нет) — общий
`404 {"error":"not found"}`.

### Сведения о кадре — что пишет воркер

Камеру, место и раскладку по роликам API не вычисляет: их пишет **montage-воркер**
(`projects/montage`) — ровно так же, как он пишет `width`, `height` и `thumbnail_key`. Контракт
между репозиториями — имена таблиц и колонок.

`media_items` — таблица API, воркер обновляет в ней колонки:

| Колонка           | Тип                | Что это                                    |
|-------------------|--------------------|--------------------------------------------|
| `camera_model`    | `text`             | модель камеры из метаданных: `iPhone 15 Pro` |
| `focal_length_mm` | `double precision` | фокусное расстояние в мм: `24`             |
| `aperture`        | `double precision` | диафрагменное число: `1.8`                 |
| `latitude`        | `double precision` | широта съёмки                              |
| `longitude`       | `double precision` | долгота съёмки                             |

Готовой строкой «iPhone 15 Pro · 24 мм · f/1.8» это не хранится: единицы в ней — слова, и ставит их
приложение на языке читателя (`users.language`). Ничего не нашлось в файле — колонка остаётся
`null`, и для читателя это то же самое, что «воркер ещё не смотрел».

`montage_frames` — таблица API, воркер вставляет в неё строки, когда собирает ролик:

| Колонка            | Тип                         | Что это                              |
|--------------------|-----------------------------|--------------------------------------|
| `montage_id`       | `uuid NOT NULL`             | ролик, `montages.id`, каскад при удалении |
| `media_id`         | `uuid NOT NULL`             | кадр, `media_items.id`, каскад при удалении |
| `start_seconds`    | `double precision NOT NULL` | на какой секунде ролика кадр стоит   |
| `duration_seconds` | `double precision NOT NULL` | сколько секунд он в нём держится     |
| `created_at`       | `timestamptz NOT NULL`      | по умолчанию `now()`                 |

Первичный ключ — `(montage_id, media_id, start_seconds)`: один кадр может законно стоять в ролике
дважды (клип, разрезанный надвое; фотография, вернувшаяся в конце). Индекс
`montage_frames_media_idx (media_id)` — под единственный вопрос, который задаёт ей API: «в каких
роликах этот кадр». Пересобрал ролик — удали его строки и вставь новые; удалять ролик или кадр
руками не нужно, обе внешние ссылки каскадные.

Таблица одна на все вехи: это раскладка ролика, и второй её копии в чужом журнале быть не должно.
API в неё только читает — маршрутом выше («в каких роликах этот кадр») и журналом монтажа
(`files[].places`, «где этот кадр лёг в этом ролике»), и больше нигде.

### `GET /memories/:memoryId/media/:mediaId/download`

За `app.authenticate` + `app.requireMembership`. Подписанная ссылка на **оригинал** одного файла —
то самое «скачать». Порога по роли здесь нет: матрица даёт скачивать оригиналы каждому участнику,
`viewer` в том числе, и стоять в воспоминании — это всё, что проверяется.

```
200 OK
{"url":"http://…&X-Amz-Signature=…"}
```

Ссылка живёт `R2_DOWNLOAD_TTL_SECONDS` (15 минут) — тот же срок и по той же причине, что у ссылок
галереи: она не должна пережить членство того, кому её выдали. Протухла — клиент просит новую.
Байты идут из хранилища напрямую, API на их пути нет — ровно как при загрузке.

Записи в `pending_upload` отсюда не отдаются: байтов за ними ещё нет, подписывать нечего, а для
вызывающего это ровно «нет такой записи». Она, запись из другого воспоминания, несуществующая и
`mediaId`, который вовсе не uuid, — общий `404 {"error":"not found"}`. Не заданы `R2_*` — `503
{"error":"storage not configured"}`.

### `GET /memories/:memoryId/media/download`

Там же и с тем же порогом. Ссылки на оригиналы **всей** галереи одним ответом: клиент сохраняет
файлы сам, и просить ссылку по одной значило бы отдельный запрос на каждый файл.

```
200 OK
[{"id":"…","kind":"photo","url":"http://…&X-Amz-Signature=…"}]
```

Отбор и порядок — те же, что у `GET /memories/:memoryId/media`: `pending_upload` не попадает,
`failed` попадает (оригинал у него есть, не хватает только превью), сортировка по времени съёмки, а
для файла без даты по времени загрузки. Так скачанное на телефон ложится в том же порядке, в каком
лежало на экране. Пустая галерея — пустой массив, а не `404`.

Все ссылки списка подписаны в один момент и протухают вместе, через те же 15 минут: скачивание
стоит начинать сразу, а не откладывать, — на протухшие клиент запрашивает список заново, как и в
галерее. Отказы — те же, что у маршрута на один файл: `503` без `R2_*`, общий `404` от проверки
прав.

Два маршрута различаются одним сегментом — `/media/download` и `/media/:mediaId/download`. Роутер
предпочитает буквальный сегмент параметру, поэтому «вся галерея» не читается как запись с id
`download`; порядок объявления на это не влияет.

### `DELETE /memories/:memoryId/media/:mediaId`

Там же. Удаляет **тот, кто загрузил** — это владение, а не роль, — и `organizer`, которому матрица
даёт любое медиа:

| Кто                        | Что                                    |
|----------------------------|----------------------------------------|
| загрузивший (любой роли)   | `200 {"ok":true}`                      |
| `organizer`                | `200 {"ok":true}` на любое медиа       |
| участник, но не тот и не он| `403 {"error":"forbidden"}`            |

Поэтому `viewer` может удалить своё (если оно у него есть), а `contributor` не может удалить
соседское. Нет такой записи, запись из другого воспоминания и `mediaId`, который вовсе не uuid, —
`404 {"error":"not found"}`, тем же телом, что и всё в этом семействе.

Если удаляемый кадр стоял обложкой воспоминания, обложка снимается сама: `memories.cover_media_id`
держит внешний ключ с `ON DELETE SET NULL`, поэтому правило живёт в базе, а не в маршруте — материал
уходит из воспоминания двумя путями (поштучно и вместе с ушедшим участником), и правило, записанное
в одном из них, второй однажды забудет. Само воспоминание при этом целое, только без обложки.

В одной транзакции: строка `media_items` пропадает, `storage_bytes` и `media_count` воспоминания
уменьшаются, `user_usage` загрузившего — тоже, задача `media_preview` снимается с очереди. Оригинал
и деривативы уходят из хранилища **после** коммита — про порядок и про то, что бывает, если
хранилище не ответило, см. «Материал уходит вместе с человеком» выше.

Запись, которая так и не догрузилась (`pending_upload`), счётчиков не двигала — значит и при
удалении они не двигаются. Иначе счётчики ушли бы ниже факта.

### Лейблы — как это устроено

Лейбл (doc-13) — коробка с названием и цветом внутри одного воспоминания: участник раскладывает по
ним кадры. Лейбл **общий** — его видят все участники — или **личный**, и тогда его не видит никто,
кроме хозяина: ни названия, ни состава, ни следа в галерее. Один кадр лежит в нескольких лейблах
сразу, в одном и том же — один раз; кадр при этом не копируется и из воспоминания никуда не
девается. Прав лейбл не даёт и не отнимает: положить в свою коробку чужой кадр можно, и это не
делает его твоим — удаление кадра живёт по своему правилу (`DELETE
/memories/:memoryId/media/:mediaId`).

Цвет — **номер ячейки палитры, 1–8**, а не краска: восемь цветов держит клиент
(`design/screens/SheetLabelNew.html`), и светлая тема перекрашивает их у себя, ничего не спрашивая
у базы. Уникальности названий нет: на воспоминание она выдавала бы чужие личные названия («занято»
— это ответ о том, чего спрашивающий видеть не должен), а тёзки ничему не мешают — лейбл
различается по id.

Две таблицы: `labels` (воспоминание, хозяин, название, цвет, общий ли) и `label_media` (связь
кадра с лейблом, с подписью — кто положил). У связи есть и `memory_id`, и он там не для красоты:
на нём висят два составных внешних ключа, и вдвоём они и есть «лейбл не выходит за своё
воспоминание» — не обещание маршрута, а то, чего база просто не даст записать. Тем же каскадом
удалённый кадр — поштучно или уходом участника — **сам** пропадает из всех лейблов, и в коде
удаления на это нет ни строки. Сам лейбл при этом остаётся.

Подпись «кто положил» (`added_by`) — записанный факт, и только: прав она не даёт, правило ниже её
не спрашивает. Уйдёт человек — связь остаётся, и кадр из чужой коробки не выпадает; не станет самой
учётной записи — забудется только подпись.

**Кадры кладут и убирают пачкой.** В режиме выбора человек отмечает несколько кадров и кладёт их
одним запросом; повторный тап по той же строке листа их оттуда убирает. Предел пачки — **файловый
предел воспоминания** (`MEMORY_MAX_FILES`, по умолчанию 1000): пачка длиннее, чем воспоминание
вмещает файлов, называет что-то дважды или является мусором. Уже лежащий кадр в пачке — не ошибка
и не дубль; кадр соседнего воспоминания, несуществующий и ещё не долетевший (`pending_upload`) —
отказ всей пачке, с именами, и ничего не кладётся наполовину.

#### Кто что может (decision-12)

Решение человека: «права на лейбл общие — могу изменять все, личные только человек», и про
зрителя — «заводить не даём — у него только просмотр». Общий лейбл общий для всех участников,
личный — только хозяина. В коде правило **одной функцией** (`labelDenial` в
`src/media/labels.ts`), и спрашивают её все: и маршруты записи, и поля `can_edit`/`can_add_media`
в списке.

| Что делают                             | Общий лейбл                                   | Личный лейбл |
|----------------------------------------|-----------------------------------------------|--------------|
| завести                                | любой участник, кроме `viewer`                | любой участник, `viewer` тоже |
| положить кадры                         | любой участник, `viewer` тоже                 | хозяин       |
| убрать кадры                           | любой участник, `viewer` тоже, кто бы кадр ни положил | хозяин |
| переименовать, перекрасить, удалить    | любой участник, `viewer` тоже                 | хозяин       |

Ни создатель общего лейбла, ни организатор здесь ничем не выделены. Зритель (`viewer`) правит и
наполняет общие лейблы наравне со всеми и заводит себе личные, но завести общий не может — `403
{"error":"forbidden"}`, так решил человек. **Чужой личный лейбл на любую запись — `404
{"error":"not found"}`, как будто его нет, организатору тоже:** «нельзя» было бы ответом о том,
что он существует.

**Ушёл участник или его исключили:** личные лейблы этого воспоминания уходят вместе с ним — их всё
равно никто больше не видел, — а общие остаются стоять, и хозяином им становится организатор. Всё
это в той же транзакции, что и строка `memory_members`. Кадры живут по своему правилу: принесённые
ушедшим удаляются и пропадают из всех коробок каскадом, чужие кадры в его коробках остаются лежать
в галерее.

### `GET /memories/:memoryId/labels`

За `app.authenticate` + `app.requireMembership`. Лейблы воспоминания глазами спрашивающего: общие
и его собственные личные. Читает любой участник, `viewer` в том числе — свои коробки есть у
каждого, кто стоит в воспоминании.

```
200 OK
[{"id":"…","title":"Лучшее","color":1,"shared":true,"mine":true,
  "can_edit":true,"can_add_media":true,"media_count":23},
 {"id":"…","title":"Любимые","color":6,"shared":false,"mine":true,
  "can_edit":true,"can_add_media":true,"media_count":9}]
```

`shared` — общий или личный, `mine` — завёл ли его спрашивающий, `media_count` — сколько кадров в
коробке лежит. Число считается по связям, поэтому оно всегда равно тому, что в ней есть на самом
деле.

`can_edit` (переименовать, перекрасить, удалить) и `can_add_media` (положить кадры) — **что
спрашивающему можно с этим лейблом**, по тому же правилу прав, по которому отказывают маршруты
записи. Считает их та же функция, поэтому приложению не нужно повторять правило у себя: кнопки
правки рисуются там, где сервер сказал «можно». И это не то же самое, что `mine` — общий лейбл
правит и наполняет любой участник, а не только тот, кто его завёл.

**Чужих личных лейблов в ответе нет ни в каком виде** — ни строкой, ни в подсчётах: их не видно
и из соседнего ответа не вычислить, потому что запрос их попросту не читает. Это закреплено
автотестом снаружи, через HTTP (`src/media/labels.test.ts`).

Порядок — сперва общие, внутри по названию, тёзки по id: ровно так лист «В лейбл» и разложен на
две группы (`design/screens/SheetLabels.html`). Тот же порядок у `label_ids` в галерее, чтобы
клиенту не пришлось пересортировывать одно под другое.

Лейблов нет — пустой массив, а не `404`. Не участник, несуществующее воспоминание и кривой id —
общий `404 {"error":"not found"}`.

### `POST /memories/:memoryId/labels`

За `app.authenticate` + `app.requireMembership`. «Новый лейбл»
(`design/screens/SheetLabelNew.html`) — и сразу с отмеченными кадрами, если его заводят из режима
выбора: кнопка там так и называется, «Создать и положить 4 кадра».

```
POST /memories/:memoryId/labels
{"title":"Лучшее","color":1,"shared":true,"media_ids":["…","…"]}

201 Created
{"id":"…","title":"Лучшее","color":1,"shared":true,"mine":true,
 "can_edit":true,"can_add_media":true,"media_count":2}
```

Отвечает строкой списка — той же, что придёт в `GET …/labels`: лист, с которого лейбл завели,
вставляет её себе, ничего не переспрашивая.

`title` — обязательное, непустое (одни пробелы не название), до 100 символов, края обрезаются.
`color` — номер ячейки палитры, целое от 1 до 8. `shared` — обязательное: общий лейбл или личный,
и **после создания это не меняется**. `media_ids` — необязательная пачка; лейбл и его кадры
появляются вместе или не появляются вовсе (одна транзакция).

| Код   | Тело                                                          | Когда |
|-------|---------------------------------------------------------------|-------|
| `400` | стандартная ошибка валидации Fastify                           | пустое название, длиннее предела, цвет вне 1–8, не сказан `shared`, пачка пустая или с повторами |
| `400` | `{"error":"no such media in this memory","media_ids":["…"]}`   | в пачке кадр соседнего воспоминания, несуществующий или ещё не долетевший |
| `403` | `{"error":"forbidden"}`                                        | `viewer` заводит общий лейбл |

### `PATCH /memories/:memoryId/labels/:labelId`

Переименовать и перекрасить. Присылается то, что человек тронул; чего нет в теле, то остаётся как
было. Отвечает той же строкой списка.

```
PATCH /memories/:memoryId/labels/:labelId
{"title":"Смешное","color":4}

200 OK
{"id":"…","title":"Смешное","color":4,"shared":true,"mine":true,
 "can_edit":true,"can_add_media":true,"media_count":2}
```

Пустое тело — `400`: это не правка, и `200` сказал бы, что она была. `shared` у этого маршрута
нет вовсе — присланный, он молча отбрасывается (ajv у Fastify работает с `removeAdditional`), и
лейбл остаётся каким был: общий ↔ личный после создания не переключается, макет этого не рисует, а
перевод общего в личный спрятал бы от всех чужие кадры, которые в нём лежат.

### `DELETE /memories/:memoryId/labels/:labelId`

Удалить коробку — `200 {"ok":true}`. Связи уходят с ней каскадом, **кадры не трогаются**: они
лежат в воспоминании и в галерее ровно там же, где лежали, и галерея от этого не меняется ничем,
кроме опустевшего `label_ids`.

### `POST /memories/:memoryId/labels/:labelId/media`

Положить пачку в коробку. Отвечает строкой списка с новым `media_count`.

```
POST /memories/:memoryId/labels/:labelId/media
{"media_ids":["…","…"]}

200 OK
{"id":"…","title":"Лучшее","color":1,"shared":true,"mine":false,
 "can_edit":true,"can_add_media":true,"media_count":5}
```

Уже лежащий кадр — не ошибка и не дубль. Чужой кадр положить можно: он не становится твоим и прав
на него не меняет. Кадр соседнего воспоминания, несуществующий и ещё не долетевший — `400
{"error":"no such media in this memory","media_ids":["…"]}` на всю пачку, и ничего не кладётся
наполовину.

### `DELETE /memories/:memoryId/labels/:labelId/media`

Убрать пачку из коробки — тело то же, `{"media_ids":[…]}`, ответ тот же. Убирают **из лейбла, а не
из воспоминания**: кадры остаются в галерее на своих местах. Кадра, которого в коробке и не было,
это не касается — убирать нечего, и это не ошибка.

Кто что может — таблица выше. Право одно на весь лейбл, а не на каждый кадр: кому можно убирать из
этого лейбла, тот убирает любой кадр в нём, кто бы его ни положил.

### Ролики — как это устроено

Ролик монтирует не API, а сосед — **montage-воркер** (`projects/montage`). API владеет таблицей
`montages` и делает ровно три вещи: заводит строку по заказу организатора, показывает список
участникам и рассылает пуш, когда воркер сказал «готово». Плюс принимает свой трек организатора,
если тот хочет монтировать под него, — «Свой трек» ниже. И отвечает на «итог перед монтажом» — что
войдёт в ролик и сколько ждать, — не записывая при этом ничего (`POST …/montages/preview` ниже).

1. `POST /memories/:memoryId/montages` — проверяются права и материал, в `montages` появляется
   строка в статусе `queued`, в `jobs` — задача `montage` со ссылкой на её `id`.
2. Воркер берёт задачу, ведёт строку `queued` → `processing` → `ready` (или `failed`), сам пишет в
   неё `video_key`, `poster_key`, `duration_seconds`, `error_text`.
3. Готово — воркер стучится в `POST /internal/montages/:montageId/ready`, и API шлёт пуш «ролик
   готов» **всем** участникам воспоминания.
4. Упало — у организатора кнопка «повторить»: та же строка возвращается в `queued`, и в очередь
   встаёт новая задача.

Статусы ролика — те же четыре слова, что у медиа, но своя цепочка: `queued` (заказан, ждёт
воркера), `processing` (монтируется), `ready` (можно смотреть), `failed` (упал, можно повторить).
Ролики живут **отдельно от галереи** и в неё не подмешиваются (doc-03).

#### Контракт с воркером

Единственное, что связывает два репозитория, — это оно, и меняется только вместе с ними обоими:

| Что                | Чьё            | Как именно                                                      |
|--------------------|----------------|-----------------------------------------------------------------|
| таблица `montages` | заводит API (миграция) | воркер читает и пишет строку по `id`, как `media.py` уже делает с `media_items` |
| задача в `jobs`    | таблица montage | тип — ровно `montage`, `ref` — `montages.id` строкой            |
| `status`           | пишут оба      | API ставит только `queued`; всё дальше — воркера                 |
| `video_key`, `poster_key`, `duration_seconds`, `error_text` | воркер | API их только читает и подписывает ссылки |
| `params`           | пишет API      | `{"target_seconds": 60, "music_tracks": []}` — эти два есть в каждом новом заказе — плюс `story_text`, `include_media_ids`, `exclude_media_ids`, `music_note`, `orientation` — то из них, что назвали. У заказов старше `music_tracks` поля нет вовсе, и там встречаются `music_track_id` / `music_track_key` |
| таблица `music_uploads` | заводит API (миграция) | воркер её не читает: свои треки он берёт из хранилища по ключам `music/…` из `params.music_tracks` |
| `/internal/montages/:id/ready` | API | воркер дёргает его после того, как записал `ready`               |
| `montage_journal_entries`, `montage_stages` | заводит API (миграция) | воркер пишет в них рассказ о сборке — «Журнал монтажа» ниже |

Каталог треков (`bright`, `warm`, `calm`, `night`, `road` — в порядке экрана «Под что монтировать»)
общий на оба сервиса: здесь по нему проверяется вход в заказ и подписывается ссылка на
предпрослушку (`GET /music/tracks/:trackId` ниже), сами файлы лежат у воркера
(`projects/montage/tracks/README.md` — источник и лицензия каждого), а копии для прослушивания он же
выкладывает в хранилище под ключами `tracks/<id>.mp3` (`python -m montage tracks`).
Свой трек организатора лежит в том же хранилище, что и материал,
и приходит воркеру ключом в том же списке `music_tracks` — скачать объект по ключу это всё, что с
треком делается.

### `GET /memories/:memoryId/montage-templates`

За `app.authenticate` + `app.requireMembership`. Отдаётся **только `organizer`**: `contributor` и
`viewer` получают `403 {"error":"forbidden"}`, не участник — `404`, как везде за этой проверкой.

Шесть готовых роликов с экрана «Каким будет ролик» (`design/screens/MontageTemplate.html`).
Шаблон — это **заранее заполненное тело заказа** и ничего сверх него: что пришло отсюда, то
приложение и шлёт в `POST /memories/:memoryId/montages`, выбросив `id` и поправив по дороге всё,
что человек захочет поправить (doc-03, «Автопилот»). Своих строк в базе у шаблонов нет.

```
200 OK
[{"id":"for_myself","story_text":"Ролик для себя о «Свадьба Лизы и Марка». 2 сентября 2026 г., …",
  "target_seconds":180,"orientation":"landscape","music_tracks":["calm"],"music_note":null}, …]
```

| Шаблон       | Длина | Формат | Музыка            |
|--------------|-------|--------|-------------------|
| `for_myself` | 3:00  | 16:9   | `calm`            |
| `quick`      | 1:00  | 16:9   | `bright`          |
| `report`     | 2:00  | 16:9   | `calm`            |
| `short_form` | 0:30  | 9:16   | `bright`          |
| `parents`    | 2:30  | 16:9   | `warm`            |
| `dopamine`   | 0:45  | 9:16   | `bright`, `road`  |

Порядок ответа — порядок карточек на экране и меняться не должен. Названия карточек («Для себя»,
«Дофаминовая бомба») и подписи под ними сервер **не отдаёт**: они живут в словаре приложения по
`id` и переводятся вместе с остальным интерфейсом (doc-8). «Настроить самому» — не шаблон, а
пустой заказ, и маршрут про него ничего не знает.

**Длина зажимается по материалу этого воспоминания** — по тем же границам, что проверяет заказ:
шаблон на три минуты в воспоминании с пределом в сорок секунд отдаёт `40`. Считается всё
готовое, кроме отсеянного автоотсевом (как и в заказе без пожеланий): вычеркнутых и возвращённых
кадров на этом шаге ещё нет, и приложение пережмёт длину само, когда они появятся.

**Где заказ всё равно откажут за нехваткой материала, отказывает и список.** Меньше трёх готовых
файлов или предел в ноль секунд — маршрут отвечает тем же `409` и тем же телом, что
`POST …/montages` без вычеркнутых кадров, и по той же проверке:

```
409 Conflict
{"error":"not enough material for a montage","ready_items":2,"need":3}
```

Шести карточек, ведущих к отказу на последнем шаге, приложение не получает. Права проверяются
раньше материала: `contributor` и `viewer` и здесь получают `403`.

**История собирается здесь, а не приложением:** заготовка шаблона плюс то, что сервер знает про
воспоминание, — название (подставляется как есть), даты одним числом или периодом и от скольких
человек в материале готовые кадры. Это ровно `people` из «итога перед монтажом» (`POST
…/montages/preview` ниже) и считается тем же запросом: кто ничего не принёс — участник или зритель, —
в «от N человек» не входит, и тот, чьи кадры все отсеяны, тоже. Вычеркнутых кадров здесь ещё нет,
поэтому шаблон считает всё готовое, кроме отсеянного, а итог — то, что осталось после
`exclude_media_ids` и возвращённого через `include_media_ids`. Язык — `users.language`
того, кто спросил; русский и английский написаны руками, английский не перевод (doc-8). Текст
влезает в поле «История ролика» на экране — не длиннее 600 символов с самым длинным названием.
Ничего, чего сервер не знает — имён, повода, — в тексте нет.

`music_note` — пожелание, как играть эти треки; `null` там, где сказать нечего. Поле есть всегда,
чтобы приложению не гадать, отдали его или забыли.

### `POST /memories/:memoryId/montages`

За `app.authenticate` + `app.requireMembership`. Заказать ролик может **только `organizer`**:
`contributor` и `viewer` получают `403 {"error":"forbidden"}`. Материал приносят все, а что из него
собрать — решает организатор (`architecture.md`, «Проверка прав»).

```
{"target_seconds": 90, "story_text": "Как мы ехали на дачу",
 "include_media_ids": ["8f1c…"], "exclude_media_ids": ["3ab0…"],
 "music_tracks": ["music/7d2e…", "calm"], "music_note": "Свой трек первым",
 "orientation": "portrait"}
```

| Поле                 | Обязательно | Что это                                                     |
|----------------------|-------------|--------------------------------------------------------------|
| `target_seconds`     | нет         | желаемая длина, целое число секунд; границы считаются по материалу — ниже |
| `story_text`         | нет         | история ролика словами организатора, до 2000 символов        |
| `include_media_ids`  | нет         | id медиа этого воспоминания, которые войти должны            |
| `exclude_media_ids`  | нет         | id медиа этого воспоминания, которых в ролике быть не должно |
| `music_tracks`       | нет         | треки в порядке проигрывания: id с полки (`bright`, `warm`, `calm`, `night`, `road`) и ключи своих загруженных, вперемешку; до 50, без повторов |
| `music_note`         | нет         | пожелания, как использовать треки, до 500 символов; только вместе с треками |
| `orientation`        | нет         | `landscape` или `portrait`; не задана — ролик горизонтальный  |

Оба списка — про **`ready`-медиа этого же воспоминания**: id из чужого воспоминания,
несуществующий и тот, чьё медиа ещё грузится или обрабатывается, отклоняются с перечнем
виноватых, а не пропускаются молча — ролик без кадра, на котором настояли, выглядит собранным, и
никто не скажет обратного. Один и тот же id в обоих списках — тоже отказ: «обязательно и ни в коем
случае» это два распоряжения, и выбрать за организатора одно из них не наше дело. Регистр id не
важен — записывается нижний, тот, в котором их отдаёт база. Один id можно прислать и без массива:
схема свернёт его в список из одного.

**Длина — число секунд в пределе воспоминания.** Предел — это ролик, который воркер соберёт из
всего материала целиком: сумма длительностей готовых видео плюс 2,5 секунды на каждое готовое фото
**минус полсекунды на каждую склейку** (кадров N — склеек N − 1), но не больше десяти минут. Склейки
вычитаются, потому что воркер накладывает каждый кусок на предыдущий на полсекунды и ролик из всего
выходит ровно на столько короче суммы (`assembly.CROSSFADE_SECONDS` и `assembly.length_of` в
`projects/montage`): сорок фото — это 80,5 секунды, а не 100. Округляется вниз до целых секунд —
обещать больше, чем выйдет, нельзя. Кадры из `exclude_media_ids` в счёт не идут ни секундами, ни
склейками — ролик собирается из того, что осталось. Видео, длительность которого воркер ещё не
измерил, добавляет ноль (а его склейка — минус полсекунды); ниже нуля предел не опускается, и
предел, вышедший нулём, — это `409` «мало материала», а не ролик на 0 секунд. Нижняя граница —
10 секунд, но если материала меньше, она опускается до верхней: воспоминание из трёх фото
заказывается ровно на 6 секунд (7,5 минус две склейки). Вне границ — `400` с обоими числами, чтобы
приложение поставило ползунок на край, а не угадывало, где он.

**Отсеянное автоотсевом в предел не идёт** — ни секундами, ни склейками. Это кадры с
`screening_rejected = true` (см. галерею): воркер при заказе судит каждый файл заново тем же
анализом на той же копии (`selection.judge`, `projects/montage/screening.py`) и отсеянное не
берёт. Кадр, который организатор вернул — назвал в `include_media_ids`, — считается снова:
«включить» воркер слушается. Кроме отсеянного как `unreadable`: в таком файле нет ни одного кадра,
и воркер не ставит его в ролик даже названным. Кадры, до которых анализ ещё не дошёл (`null`), и
оставленные им (`false`) считаются как раньше: там предел приблизительный, и это честно —
угадывать вердикт, которого ещё нет, API не берётся. Итого предел —
`floor(min(600, Σ длин видео + 2,5 с × фото − 0,5 с × (N − 1)))`, где видео, фото и N — готовые
кадры этого воспоминания, кроме исключённых и отсеянных (возвращённые из отсева — в счёте, кроме
`unreadable`).

**Музыка — список любой длины.** В нём вперемешку id с полки воркера и ключи своих загруженных
треков этого воспоминания; порядок списка — порядок проигрывания и записывается как прислали.
Пустой список или отсутствие поля — ролик **без музыки**. Неизвестный id, ключ из чужого
воспоминания и недогруженный трек отклоняются поимённо. `music_note` — пожелания к этим трекам —
принимается только вместе с непустым списком. Другого способа назвать музыку нет: старые
`music_track_id` и `music_track_key` отклоняются ошибкой схемы, а не отбрасываются, как выдуманное
поле, — заказ, просивший музыку, не должен молча остаться без неё.

Тело целиком необязательно: `{}`, `null` и запрос вовсе без тела — это один и тот же «без
пожеланий». Одна оговорка про третий вариант: «без тела» значит и без заголовка
`Content-Type: application/json`. Заголовок при пустом теле — это `400`
`FST_ERR_CTP_EMPTY_JSON_BODY` от самого Fastify, ещё до нашей схемы; клиенту, который ставит этот
заголовок всегда, надёжнее слать `{}`.

Незаданная длина записывается в строку значением по умолчанию (`MONTAGE_TARGET_SECONDS`, 60 с),
зажатым в границы этого воспоминания: у воспоминания на 6 секунд в строке будет 6. Невыбранная
ориентация не пишется: отсутствие поля воркер читает как `landscape`, ровно как у роликов,
заказанных до того, как поле появилось. Записывается только выбранная. Пустая история и пустой
список кадров — это «не сказали»: клиент, очищающий поле, шлёт его пустым, а не выбрасывает, и в
`params` такой ключ не попадает (история к тому же обрезается по краям). Исключение одно —
`music_tracks` пишется **всегда, даже пустым**: по нему воркер отличает «без музыки» от заказа,
сделанного до появления поля, где музыку он выбирал сам. Неизвестные поля отбрасываются, в
`params` попадает только то, что здесь описано.

```
201 Created
{"id":"…","memory_id":"…","ordered_by":"…","status":"queued","duration_seconds":null,
 "params":{"target_seconds":90,"story_text":"Как мы ехали на дачу",
           "include_media_ids":["8f1c…"],"exclude_media_ids":["3ab0…"],
           "music_tracks":["music/7d2e…","calm"],"music_note":"Свой трек первым",
           "orientation":"portrait"},"error_text":null,
 "created_at":"…","updated_at":"…","video_url":null,"poster_url":null}
```

| Ответ | Тело                                                        | Когда                          |
|-------|-------------------------------------------------------------|--------------------------------|
| `403` | `{"error":"forbidden"}`                                      | участник, но не организатор    |
| `409` | `{"error":"not enough material for a montage","ready_items":2,"need":3}` | после вычета исключённых и отсеянных остаётся меньше трёх `ready`-медиа или предел длины выходит 0 |
| `400` | `{"error":"a media item cannot be both included and excluded","media_ids":["…"]}` | один и тот же кадр в обоих списках |
| `400` | `{"error":"no such ready media in this memory","media_ids":["…"]}` | id не из этого воспоминания или медиа ещё не `ready` |
| `400` | `{"error":"target_seconds out of range","min_seconds":10,"max_seconds":63}` | длина вне предела этого воспоминания |
| `400` | `{"error":"no such music track","music_tracks":["…"]}` | id не с полки, ключ не из этого воспоминания или трек не догружен |
| `400` | `{"error":"music_note needs music_tracks"}`                  | пожелания к музыке без самой музыки |
| `400` | ошибка схемы                                                 | длина не целая, ориентация не `landscape`/`portrait`, история длиннее 2000 символов, пожелание длиннее 500, треков больше 50 или один дважды, в списке кадров не id или один и тот же дважды, старые `music_track_id` / `music_track_key` |

Меньше трёх готовых файлов — отказ **до** записи: ни строки, ни задачи не остаётся. Считаются
только `media_items` в статусе `ready`: то, что ещё грузится или обрабатывается, воркеру нечем
монтировать (`architecture.md`, «Montage-пайплайн»). Порог держится по тому, что останется в
ролике: из числа `ready`-медиа вычитаются кадры из `exclude_media_ids` и отсеянные автоотсевом
(кроме возвращённых — ровно как в пределе выше), поэтому воспоминание из пяти с тремя
вычеркнутыми или отсеянными — тот же отказ, что и воспоминание из двух, а `ready_items` в ответе —
остаток этого заказа, не всё, что лежит в воспоминании. Так же считает и воркер: его второй порог
после отсева — три годных кадра, где отсеянное идёт в счёт, только если его вернули. Списки проверяются раньше порога: если в
них назван чужой или неготовый кадр, ответом будет `400` про него. Клиент показывает это своими
словами — «недостаточно материала для ролика»; тело ответа, как и везде здесь, английское и с
числами.

Строка, задача в очереди, `memories.montage_count` и `user_usage.montage_count` двигаются **одной
транзакцией**: счётчик считает заказанное, а не смонтированное, и разойтись со строками не может.
Числа роликов на воспоминание не ограничиваем (doc-03).

### `POST /memories/:memoryId/montages/preview`

«Итог перед монтажом» (doc-03): что войдёт в ролик, до какой длины можно и сколько примерно ждать —
**до** нажатия «Начать монтаж». Тот же заказ, только не заказ.

Тело — **ровно то же**, что у `POST /memories/:memoryId/montages`, все поля необязательные. Права
те же (только `organizer`, остальным `403`, не участнику `404`) и проверки те же, в том же порядке
и с теми же телами ответов: итог, который согласился на то, что заказ отклонит, хуже отсутствия
итога. Отличие одно: **ничего не пишется** — ни строки в `montages`, ни задачи в `jobs`, ни
счётчиков. Экран можно открывать сколько угодно раз.

```
200 OK
{"photos":168,"videos":46,"people":5,"min_seconds":10,"max_seconds":443,
 "target_seconds":150,"orientation":"landscape","estimate_minutes":15}
```

| Поле               | Что это                                                                  |
|--------------------|---------------------------------------------------------------------------|
| `photos`, `videos` | сколько фото и видео войдёт: готовые за вычетом `exclude_media_ids` и отсеянного |
| `people`           | от скольких разных людей эти кадры                                        |
| `min_seconds`, `max_seconds` | предел длины по этому же материалу — как в заказе                |
| `target_seconds`   | длина, которую записал бы заказ: названная или умолчание, зажатое в предел |
| `orientation`      | `landscape` или `portrait`; не названа — `landscape`                      |
| `estimate_minutes` | сколько примерно монтировать, в минутах, не меньше одной                  |

Кадры из `include_media_ids` считаются наравне с прочими: «войти должен» закрепляет кадр в ролике,
а к материалу добавляет его, только если возвращает из отсева (кроме `unreadable` — см. предел
у заказа). Медиа не в статусе `ready` не в счёт — воркеру с ними нечего делать.

**`estimate_minutes` — ориентир, а не обещание.** Грубая прикидка по числу кадров и длине ролика
(по три секунды на кадр плюс полторы на каждую секунду готового видео, вверх до целых минут),
выверенная по макету `design/screens/MontageSummary.html` — «214 кадров на 2:30 ≈ 15 минут». Никто
не держит воркера в этих рамках: очередь может быть занята, нейросеть — медленной, а сборка вообще
упасть. Приложение так и говорит: «соберём примерно за столько-то».

Ответы об отказе — те же, что у заказа, той же таблицей: `403` не организатору, `409` «мало
материала», `400` на противоречивые и чужие списки кадров, длину вне предела, неизвестный трек,
пожелание к музыке без музыки и ошибки схемы. Тело ответа совпадает с тем, что на то же самое тело
вернул бы сам заказ.

### Свой трек — как это устроено

«Музыка: библиотека треков… и возможность добавить свою» (doc-03). Своя — это аудиофайл, который
организатор заливает **тем же путём, что и материал**: заявка, подписанные куски, «загружено».
Байты в API не приходят и здесь.

1. `POST /memories/:memoryId/music` — заводится запись `music_uploads` в статусе `pending_upload`,
   в ответ — подписанные ссылки на куски и ключ будущего объекта.
2. Приложение шлёт `PUT` на каждую ссылку и запоминает `ETag` ответов.
3. `POST /memories/:memoryId/music/:trackId/complete` — API собирает объект, переводит запись в
   `ready` и возвращает ключ.
4. Этот ключ приложение кладёт в `music_tracks` при заказе ролика — рядом с id треков с полки.

Своя таблица, а не третий `kind` в `media_items`: трек — не материал воспоминания. В галерею он не
попадает, в те самые «три готовых файла» не считается, превью с него никто не снимает. У записи
всего два состояния, `pending_upload` и `ready`: воркер трек не обрабатывает — только скачивает.

Ссылок **не перевыдаём**: трек — небольшой файл, а час (`R2_UPLOAD_TTL_SECONDS`) — долгий срок.
Протухли — заводится новая заявка. Размер трека в счётчики воспоминания (`storage_bytes`,
`media_count`) не идёт: те считают галерею, а вернуть их назад некому — трек не удаляется.
Потолок на файл общий с медиа (`MEDIA_MAX_FILE_BYTES`).

### `POST /memories/:memoryId/music`

За `app.authenticate` + `app.requireMembership`. Только **`organizer`**: трек — это пожелание к
ролику, а ролик заказывает он (`contributor` и `viewer` получают `403 {"error":"forbidden"}`).

```
{"size_bytes": 4194304}
```

```
201 Created
{"id":"…","status":"pending_upload",
 "upload":{"key":"music/…","upload_id":"…","part_size":8388608,
           "parts":[{"part_number":1,"url":"http://…&X-Amz-Signature=…"}],
           "expires_at":"2026-09-03T12:00:00.000Z"}}
```

Ключ — по id записи, и он приходит в ответе: собирать его на клиенте не нужно, и именно он потом
уходит в `music_tracks`.

| Ответ | Тело                                                        | Когда                          |
|-------|-------------------------------------------------------------|--------------------------------|
| `403` | `{"error":"forbidden"}`                                      | участник, но не организатор    |
| `413` | `{"error":"file is too large","limit_bytes":1073741824}`     | файл больше потолка            |
| `503` | `{"error":"storage not configured"}`                         | не заданы `R2_*`               |

Отказ по потолку — **до** записи: ни строки, ни загрузки в хранилище не остаётся.

### `POST /memories/:memoryId/music/:trackId/complete`

Там же. Доделать загрузку может только тот, кто её начал: это не про роль, а про владение. Куски —
все, что были отправлены, с их `ETag`, тело — как у медиа-колбэка.

```
200 OK
{"id":"…","status":"ready","key":"music/…"}
```

**Повторный вызов безопасен**: трек уже `ready` — приходит тот же ответ, второй записи не
заводится.

Записывается **тот размер, который хранилище реально держит**. Объекта в хранилище нет — `409
{"error":"the upload is not in storage"}`, запись остаётся `pending_upload`, загрузку можно
доделать. Объект оказался больше потолка (заявили мало, прислали много) — `413`, и тогда уходят и
запись, и объект: подписанный кусок своей длины не несёт, и поймать это можно только здесь.

Чужая запись, запись из другого воспоминания, несуществующая и кривой `trackId` — общий
`404 {"error":"not found"}`. Не заданы `R2_*` — `503 {"error":"storage not configured"}`.

### `GET /music/tracks/:trackId`

За одним `app.authenticate`. «Послушать» на экране «Под что монтировать»: подписанная ссылка на
трек **с полки** — тот самый файл, под который смонтируется ролик, до того как ролик заказан.

```
200 OK
{"url":"http://…&X-Amz-Signature=…"}
```

Вне `/memories/:memoryId` намеренно: полка одна на весь продукт, одни и те же пять треков для всех,
и проверять тут нечего, кроме того, что человек вошёл — ни членства, ни роли, ни воспоминания.
Ключ — `tracks/<id>.mp3`, файлы туда выкладывает воркер (`python -m montage tracks`). Ссылка живёт
`R2_DOWNLOAD_TTL_SECONDS`, и байты идут из хранилища напрямую — как у медиа.

`trackId` — один из пяти, тем же списком, которым проверяются id в `music_tracks` заказа: чего нельзя
заказать, того нельзя и послушать. Любой другой — `404 {"error":"not found"}` (не `400`: трека
попросту нет). Не заданы `R2_*` — `503 {"error":"storage not configured"}`.

### `GET /memories/:memoryId/montages`

За `app.authenticate` + `app.requireMembership`. Список роликов воспоминания, **новые сверху**.
Читает любой участник, `viewer` в том числе: матрица даёт ему «смотреть галерею и ролики».

```
200 OK
[{"id":"…","memory_id":"…","ordered_by":"…","status":"ready","duration_seconds":58.5,
  "params":{"target_seconds":60,"orientation":"portrait"},"error_text":null,
  "created_at":"…","updated_at":"…",
  "video_url":"http://…&X-Amz-Signature=…","poster_url":"http://…&X-Amz-Signature=…",
  "stages":null}]
```

`video_url` — подписанная ссылка на готовый ролик, живёт `R2_DOWNLOAD_TTL_SECONDS` (15 минут, тот
же срок, что у галереи). У всего, что не `ready`, она `null` — это «ещё не готово», а не ошибка;
протухла — клиент запрашивает список заново. Ключ ролика наружу не отдаётся, только ссылка.

`poster_url` — то же самое для кадра-постера, который клиент показывает до запуска ролика:
подписывается из `poster_key` тем же способом и на тот же срок. `null` не только у неготового —
у ролика, смонтированного до того, как воркер научился резать кадр, постера нет и не появится, и
клиент рисует такой ролик без превью.

`stages` — куда дошла сборка: **пять этапов в порядке пайплайна**, у каждого своё состояние
(`pending` / `running` / `done` / `failed`). Из них карточка на ленте сама считает «3 из 5» и красит
шкалу из пяти полосок (`design/screens/MemoryFrames.html`), а упавший этап красит по-своему —
открывать журнал каждой карточки для этого не нужно.

```json
"stages":[{"stage":"screening","state":"done"},{"stage":"understanding","state":"running"},
          {"stage":"directing","state":"pending"},{"stage":"rhythm","state":"pending"},
          {"stage":"assembly","state":"pending"}]
```

Этапов у ролика либо пять, либо ни одного: воркер заводит все пять разом, в `pending`, как только
взял ролик, — до первой записи и первого скачанного файла. `null` — когда этапов нет (ролик
`queued`, то есть заказан или поставлен повторить, или отказан воркером раньше, чем тот завёл
этапы), и у **готового**: шкала ему не нужна, и его этапы список не читает. Что за этапы и в каком
состоянии они у упавшего — раздел «Журнал монтажа», «Этапы» ниже. На весь список этапы читаются
**одним запросом**, и чтение списка никого не отмечает смотрящим — это делает только маршрут
журнала.

У упавшего в `error_text` лежит то, что сказал воркер, — рядом с ним клиент рисует «повторить».

Не заданы `R2_*` — `503 {"error":"storage not configured"}`, как и у галереи: подписать нечем.
Не участник, несуществующее воспоминание и кривой id — общий `404 {"error":"not found"}`.

### `POST /memories/:memoryId/montages/:montageId/retry`

Там же, и снова **только `organizer`**. Повторяет **упавшую** сборку: та же строка возвращается в
`queued`, `error_text` обнуляется, в `jobs` встаёт новая задача `montage`. Ответ — обновлённая
строка в той же форме, что в списке, только без `stages`: этапы досчитывает список. Той же
транзакцией стираются записи журнала и этапы прошлой попытки — повтор встаёт в очередь с чистым
листом, без этапов в списке и с пустым журналом; смотрящих это не трогает.

| Ответ | Тело                                                        | Когда                          |
|-------|-------------------------------------------------------------|--------------------------------|
| `200` | строка ролика                                                | был `failed`, теперь `queued`  |
| `403` | `{"error":"forbidden"}`                                      | участник, но не организатор    |
| `409` | `{"error":"montage has not failed","status":"queued"}`       | ролик не падал                 |
| `404` | `{"error":"not found"}`                                      | нет такого ролика, он из чужого воспоминания или `montageId` не uuid |

Проверка «был `failed`» стоит в самом `UPDATE`, а не только в условии перед ним: две нажатые
подряд кнопки двигают строку один раз, и вторая получает `409`. Иначе на одной строке оказались бы
две задачи.

### `POST /internal/montages/:montageId/ready`

**Не за `app.authenticate`** — за этим маршрутом нет человека и сессии. Стучится montage-воркер,
когда ролик выложен и строка уже переведена в `ready`; API делает то единственное, чего воркер не
может, — доносит новость до телефонов.

```bash
curl -X POST http://localhost:3000/internal/montages/<id>/ready \
  -H "Authorization: Bearer $INTERNAL_WORKER_TOKEN"
```

Авторизация — общий секрет `INTERNAL_WORKER_TOKEN` в заголовке `Authorization: Bearer`. Не совпал,
не пришёл вовсе или не задан в окружении — `401 {"error":"unauthorized"}`. Сверка идёт по хешам
через `timingSafeEqual`: обычное сравнение строк выдаёт префикс секрета тому, кто его меряет.

Ответ — `200 {"ok":true}`, **даже если пуш не дошёл ни до кого**: ролик готов независимо от
уведомления, а сказать воркеру «не вышло» значило бы отправить его повторять задачу, вся работа
которой сделана. Несуществующий, кривой `montageId` — и строка, которая ещё не `ready`, —
`404 {"error":"not found"}`: маршрут умеет сказать только «ролик готов», и над строкой в `queued`,
`processing` или `failed` ему нечего объявлять. Поэтому порядок обязателен — сперва записать
`ready`, потом стучаться, — и повторный стук по той же строке безопасен.

Тело у запроса не читается: `video_key`, `poster_key`, `duration_seconds` и `status` воркер уже
записал сам.

### Журнал монтажа — как это устроено

Режиссёр рассказывает вслух, как собирает ролик: что за кадр держит в руках, что на нём видит, берёт
или проходит мимо и почему (doc-03, «Монтаж в прямом эфире»). Рассказ лежит **вместе с роликом** и не
исчезает после сборки: «как собирался» открывает любой участник воспоминания и через полгода.
Экраны — `design/screens/MontageLive.html`, `MontageLiveStage.html`, `SheetLiveFile.html`,
`MontageLiveDone.html`.

Уговор тот же, что и с самим роликом: **схему заводит API, содержание пишет воркер**. Своя строка у
API здесь ровно одна — `montage_viewers`, и пишется она самим фактом чтения журнала.

Три таблицы (миграция `130.do.montage-journal.sql`):

| Таблица                   | Кто пишет | Что это                                               |
|---------------------------|-----------|-------------------------------------------------------|
| `montage_journal_entries` | воркер    | реплики режиссёра, за попытку только дописываются     |
| `montage_stages`          | воркер    | по строке на этап, пять на ролик                      |
| `montage_viewers`         | API       | кто смотрит сборку сейчас                             |

Все три привязаны к `montages (id) ON DELETE CASCADE`: **ушёл ролик или воспоминание — журнал ушёл с
ним**. А `media_id` в записи — единственная в этой базе ссылка на `media_items` **без внешнего
ключа**, и это намеренно: ушёл кадр или участник со всем, что принёс, — запись о нём **остаётся**,
просто без сведений о файле.

#### Этапы

Пять, строго в этом порядке; в базе — коды, названия приложение показывает на своём языке:

| Код             | Про что                     |
|-----------------|-----------------------------|
| `screening`     | Отсев брака                 |
| `understanding` | Разбираем, что на кадрах    |
| `directing`     | Режиссёр строит историю     |
| `rhythm`        | Раскладываем в ритм трека   |
| `assembly`      | Склеиваем                   |

Все пять строк воркер **заводит разом, в `pending`, в самом начале сборки** — до первого скачанного
файла и первой записи журнала, с оценкой времени на каждый. Дальше этап только обновляет свою
строку: `running`, пока идёт, `done`, когда кончился. Ключ — `(montage_id, stage)`, строки заводятся
через `INSERT … ON CONFLICT (montage_id, stage) DO UPDATE`: новая попытка того же ролика (повтор
очереди после сбоя или «повторить») их не удаляет, а переписывает на месте — все пять снова
`pending` с новой оценкой, а записи прошлой попытки стёрты.

Отсюда — что видит читающий:

- **ни одного этапа** — у ролика `queued` («повторить» стирает этапы сам, той же транзакцией), у
  собранного до появления журнала и у отказанного до начала журнала: `processing` воркер ставит
  на несколько проверок заказа раньше, чем заводит этапы, и отказ на них — неизвестный трек,
  неизвестная ориентация, меньше трёх готовых файлов — оставляет ролик `failed` без журнала;
- **пять в `pending`** — воркер ролик взял, первый этап ещё не начался;
- **пять `done`** — у готового;
- **пять у упавшего** — `failed` тот этап, который шёл, когда ролик назвали упавшим; до него
  `done`, после — `pending`. Отказ между этапами — годного после отсева меньше трёх, своего трека
  нет в хранилище или он не читается — упавшего этапа не оставляет: пять этапов без `failed`. Пока
  очередь даёт ролику ещё попытку, этап, на котором он сломался, остаётся `running`.

| Колонка       | Что в ней                                                                  |
|---------------|-----------------------------------------------------------------------------|
| `state`       | `pending` / `running` / `done` / `failed`                                   |
| `started_at`, `finished_at` | когда этап начался и кончился                                 |
| `eta_seconds` | сколько этап займёт, а у идущего — **сколько осталось**; пусто — оценки нет |
| `done_count`, `total_count` | «61 из 212 разложено»; `total_count` пуст, пока не посчитано   |
| `outcome`     | итог этапа свободным `jsonb` (ниже)                                         |

`outcome` — свободный, потому что итог у каждого этапа свой, а фразу из него строит приложение.
Ключи, на которые оно рассчитывает (лишние не мешают, отсутствующие просто не рисуются):

| Этап            | Ключи `outcome`                          | Во что это на экране          |
|-----------------|------------------------------------------|-------------------------------|
| `screening`     | `kept`, `of`, `reasons` (код → сколько)  | «212 из 214 годятся»          |
| `understanding` | `faces`, `people`, `animals`             | «37 лиц, 5 людей в главных»   |
| `directing`     | `parts`, `frames`, `part_titles`         | «3 части, 61 кадр»            |
| `rhythm`        | `track`, `bpm`, `cuts`                   | «"Тёплая" → "Спокойная"»      |
| `assembly`      | `cuts`, `seconds`                        | «цвет, звук, титры»           |

Счётчики «взял N / мимо N / мысли N» воркер **не пишет**: их считает API по самим записям, чтобы
второй счёт не разошёлся с первым.

#### Запись журнала

За попытку сборки только дописывается, новая попытка начинает с чистого листа («Этапы» выше);
`id` — `bigserial`, и он же курсор. Всё, кроме `stage`, необязательно.

| Колонка               | Что в ней                                                                |
|-----------------------|---------------------------------------------------------------------------|
| `stage`               | один из пяти кодов выше                                                   |
| `media_id`            | про какой кадр; пусто — мысль про план в целом                            |
| `thought`             | мысль текстом, **до 500 символов**                                        |
| `decision`            | `take` («беру») / `skip` («мимо») / пусто — чистая мысль без решения       |
| `reason`              | почему мимо, кодом: `blur`, `exposure`, `unreadable`, `duplicate`, `excluded`, `no_room`, … — словарь воркера, до 40 символов, `CHECK` на него нет |
| `series_size`         | «взял 1 из N» — сколько кадров было в серии                               |
| `story_part`, `story_part_title` | номер части истории и её название (**до 80 символов**)         |
| `source_from_seconds`, `source_to_seconds` | какой кусок исходника взят, в секундах от его начала |
| `focus_x`, `focus_y`, `focus_w`, `focus_h` | рамка «куда смотрит» — **долями 0..1**, не пикселями; либо все четыре, либо ни одной |
| `labels`              | метки «что увидел» — `text[]`, **до 12 штук и до 240 символов всего**      |
| `created_at`          | когда легла                                                               |

Потолки стоят `CHECK`-ами в базе, а не в коде API: пишет-то воркер, и порция в двести записей должна
уместиться в один опрос приложения раз в секунду-две.

### `GET /memories/:memoryId/montages/:montageId/journal`

За `app.authenticate` + `app.requireMembership`. Читает **любой участник**, `viewer` в том числе:
матрица даёт ему «смотреть галерею и ролики». Посторонний, чужой ролик, несуществующий и не-uuid —
один и тот же `404 {"error":"not found"}`, как везде за этой проверкой.

Приложение **опрашивает этот маршрут раз в 1–2 секунды**, пока ролик собирается, и передаёт
`after` с наибольшим уже показанным `id` — тогда в ответе едут только новые записи. Всю порцию
целиком тянуть на каждом опросе не нужно.

| Параметр   | По умолчанию | Что делает                                                     |
|------------|--------------|-----------------------------------------------------------------|
| `after`    | —            | записи **новее** этой, и из них — **ближайшие к курсору** (курсор «что легло с прошлого опроса») |
| `before`   | —            | записи **старее** этой, и из них — ближайшие (листать назад по журналу) |
| `limit`    | `200`        | сколько записей отдать, потолок `500`                            |
| `stage`    | —            | сузить до одного этапа                                           |
| `media_id` | —            | сузить до одного файла                                           |

Записи в ответе всегда идут **от свежих к старым**, в обоих направлениях курсора: именно так их
рисует экран. Выбираются они при этом с разных концов — порция всегда та, что **примыкает к
курсору**.

**Правило клиента:** курсор следующего запроса — **наибольший `id` отданной порции**; `has_more` —
есть ли ещё в ту сторону, куда просили, и если да, спрашивать надо **сразу, не дожидаясь следующего
опроса**.

Ближайшая порция, а не самая свежая, — потому что между двумя опросами может лечь **больше записей,
чем лимит**: этап «разбор кадров» пишет по записи на файл разом, экран открыли в середине сборки,
телефон спал. Отдай маршрут «самые новые 200 из новых», клиент двинул бы курсор на их максимум — и
всё между старым курсором и этой порцией не запросил бы уже никогда, а понять, что посередине дыра,
ему неоткуда.

```json
{
  "montage": { "id": "…", "status": "processing" },
  "stages": [
    { "stage": "screening", "state": "done", "started_at": "…", "finished_at": "…",
      "eta_seconds": 0, "done_count": 214, "total_count": 214,
      "outcome": { "kept": 212, "of": 214 }, "updated_at": "…",
      "taken_count": 0, "skipped_count": 2, "thought_count": 0 }
  ],
  "entries": [
    { "id": 1042, "stage": "directing", "media_id": "…",
      "thought": "Марк роняет кольцо — беру 3 секунды",
      "decision": "take", "reason": null, "series_size": 4,
      "story_part": 2, "story_part_title": "Клятвы и объятия",
      "source_from_seconds": 4, "source_to_seconds": 7,
      "labels": ["Бабушка", "смех"],
      "focus": { "x": 0.3, "y": 0.05, "w": 0.25, "h": 0.5 },
      "created_at": "…" }
  ],
  "has_more": true,
  "files": [
    { "id": "…", "kind": "video", "uploaded_by": "…", "captured_at": "…",
      "duration_seconds": 12.5, "thumbnail_url": "https://…",
      "places": [ { "start_seconds": 0, "duration_seconds": 2.25 },
                  { "start_seconds": 12.5, "duration_seconds": 3 } ] }
  ],
  "viewers": [ { "id": "…", "username": "anya" } ]
}
```

`stages` — все пять в порядке пайплайна или пусто, пока воркер ролик не взял («Этапы» выше): «этап
3 из 5» на экране — это позиция в этом списке. Три счётчика от API (`taken_count`, `skipped_count`,
`thought_count`) считаются по всем записям этапа, а не по отданной порции. Отсев пишет записи только
на отсеянное, поэтому его `taken_count` — ноль, а сколько годится, говорит `outcome`.

`entries[].id` — число и курсор; четыре доли рамки собраны в один `focus` (или `null`).

`files` — сведения **только о тех файлах, что встретились в отданной порции**: журнал ролика это
сотни записей об одних и тех же кадрах, и подписывать ссылки на весь материал на каждом опросе не за
чем. `thumbnail_url` подписана как в галерее и живёт `R2_DOWNLOAD_TTL_SECONDS`; хранилище не
настроено — `null`, а не `503`: здесь ссылки одно поле рассказа, а не весь ответ. **Кадра уже нет —
запись остаётся, а сведений о нём в `files` просто не будет; это не ошибка.**

`files[].places` — **где этот кадр лёг в этом ролике**: `start_seconds` — секунда, с которой он
стоит, `duration_seconds` — сколько держится (длина самого файла — это `duration_seconds` рядом, у
файла). Список, а не одно место: один кадр законно стоит в ролике дважды — клип, разрезанный
надвое, фотография, вернувшаяся в конце, — и порядок в списке это порядок в ролике. **Раскладки ещё
нет или кадр в ролик не вошёл — `[]`, а не ошибка**: пока идёт отсев, пусто у всех.

Журнал раскладку **не хранит**: она лежит в общей таблице `montage_frames` («Сведения о кадре» выше)
и здесь только присоединяется — по файлам отданной порции и по этому ролику, не по всему материалу.
Соседний ролик того же воспоминания в `places` не попадает, а статус ролика не важен: места
появляются по ходу сборки, про неё рассказ и идёт.

`viewers` — кто спрашивал за последние `MONTAGE_VIEWER_WINDOW_SECONDS` секунд, **свой запрос тоже**.
Отдельного «я смотрю» приложение не шлёт: пока ролик `queued` или `processing`, сам запрос читающего
и есть отметка, один `upsert` на опрос. У `ready` и `failed` не отмечается никто.

### Журнал монтажа — снимки и записанные ответы

Тест `src/montages/journal.golden.test.ts` ведёт через настоящие маршруты api не написанный руками
журнал, а **настоящий вывод воркера**: ролик грузится в базу из снимка, читается `GET …/journal`,
`GET …/montages`, повторяется и удаляется. Данные лежат в `src/montages/golden/`:

| Файл                                                  | Что это                                                                |
|-------------------------------------------------------|-------------------------------------------------------------------------|
| `journal_director.json`                               | снимок сборки, которую режиссировала нейросеть (записанным ответом): 13 файлов, ролик 15 с |
| `journal_algorithm.json`                              | снимок сборки без нейросети (отсев и ритм): 12 файлов, ролик 10,07 с     |
| `responses_director.json`, `responses_algorithm.json` | ответы api по этим двум сборкам — для приложения (ниже)                  |

**Снимки — копии.** Их пишет воркер (`projects/montage/fixtures/journal_*.json`; формат и
нормализация — в README montage, «Золотой снимок журнала»), а здесь лежат закоммиченные копии.
Между репозиториями ничто не следит, что копии свежие: воркер перезаписал свои снимки, а здесь их не
обновили — тест зелёный на старом выводе. Этот разъезд — условие связи, устранить его api не может.
Обновить копии:

```sh
cp ../montage/fixtures/journal_*.json src/montages/golden/
npx biome format --write src/montages/golden       # воркер пишет свой формат, biome его переписывает
npm test -- src/montages/journal.golden.test.ts    # упадёт на записанных ответах, если вывод изменился
```

**Записанные ответы** тест по умолчанию только **сверяет** с закоммиченными и падает с
построчной разницей по имени шага; молча не перезаписывает никогда. Перезапись — только явно:

```sh
JOURNAL_RECORD_RESPONSES=1 npm test -- src/montages/journal.golden.test.ts
npx biome format --write src/montages/golden
```

Затем посмотреть разницу в `src/montages/golden` — изменившиеся ответы читает приложение, поэтому
это повод сказать ему, а не только закоммитить.

#### Формат записанных ответов

`responses_<сценарий>.json` — самодостаточный JSON, знать TypeScript для чтения не нужно:

```json
{ "format": 1, "scenario": "director", "source": "journal_director.json",
  "steps": [
    { "name": "live_poll_3",
      "request":  { "as": "organizer", "method": "GET",
                    "path": "/memories/00000000-0000-4000-8000-a00000000001/montages/00000000-0000-4000-8000-b00000000001/journal",
                    "query": { "after": 4, "limit": 4 } },
      "response": { "status": 200, "body": { "montage": {}, "stages": [], "entries": [], "has_more": true, "files": [], "viewers": [] } } } ] }
```

- `steps` — **по времени**: так они шли в одном прогоне; `live_*` — это одна сборка, опрос за
  опросом, проигрывать по порядку. `name` уникален в файле.
- `request.as` — кто спрашивает: `organizer`, `contributor`, `viewer`, `stranger` (не участник) или
  `null` (без токена). Токенов в записи нет. `method` — всегда `GET`, `path` — как есть, `query` —
  параметры строки запроса (`limit`, `after`, `media_id`).
- `response.status` — код ответа, `response.body` — тело **как его отдал api** (форма — «Журнал
  монтажа» и «Список роликов» выше), с нормализацией ниже.

Нормализация — чтобы запись не менялась от прогона к прогону:

- **Все id — фиксированные uuid** вида `00000000-0000-4000-8000-<буква><11 цифр>`: воспоминание
  `a…01`; ролики `b…01` (ролик из снимка), `b…02` (старый готовый, собранный до журнала — журнал
  пуст), `b…03` (стоит в очереди); люди `c…01` организатор `anya`, `c…02` участник `marko`, `c…03`
  зритель `lena`, `c…04` посторонний `ivan`; файлы `f…NN`, где `NN` — `position` файла в снимке
  (`f1` → `f…01`). Файлы с нечётным `position` привёз организатор, с чётным — участник.
- **`entries[].id` — номер записи `n` из снимка** (1, 2, 3… в порядке записи), а не bigserial из
  базы. Курсоры в `query.after` и `query.before` — тоже эти номера; `0` — «с начала».
- **Ссылки** (`thumbnail_url`, `video_url`, `poster_url`) — без подписи и срока: `<хост>/<бакет>/<ключ>?signed`.
  Настоящие подписаны и живут 900 секунд; в записи они лишь показывают, что ссылка есть и куда ведёт.
- **`files` отсортированы по id**: порядок файлов в ответе api не обещает.
- **Времена не менялись**, они и так фиксированы: записи и этапы — метки снимка (секунды от
  `2026-01-01T00:00:00Z`), `captured_at` файла — `2025-12-31T18:00:00Z` плюс `captured_after_seconds`
  из снимка, `created_at` роликов задан тестом.
- **Что настоящее, что смоделировано.** Записи и итоговые строки этапов — вывод воркера, из
  снимка. Порядок, в котором они ложатся в базу, тест ведёт так, как воркер (`journal.py`,
  `montage.py`), — строка этапа не появляется, а только меняется:
  1. **`begin`** — до первого скачанного файла и первой записи все пять этапов сразу, в `pending`:
     `started_at` и `finished_at` пусты, `done_count` `0`, `total_count` пуст, `outcome` `{}`,
     `eta_seconds` — оценка воркера по числу файлов снимка и заказанной длине ролика (`screening`
     1,5 с на файл, `understanding` 0,8, `directing` 0,5, `rhythm` 0,2 с на файл и 0,1 на секунду
     ролика, `assembly` 1,4 с на секунду ролика; округление как у Python). Эти числа — копия ручки
     воркера `journal.ESTIMATE` в тесте, а не часть снимка (закрытый этап стоит с нулём), так что
     с копиями снимков они ездят вместе: воркер подстроил ручку — обновить её и в тесте.
  2. **Этап начался** — `UPDATE` той же строки: `running`, `started_at`, `total_count`; оценка та же,
     что поставил `begin`.
  3. **По ходу** — двигают счётчик только два этапа. Отсев — по файлу: после записи о файле
     `done_count` равен номеру файла в порядке съёмки (`position`), а `eta_seconds` пересчитан по
     факту (прошло ÷ сделано × осталось). Склейка — по готовому куску; опрос — на середине.
     «Разбор» и «режиссёр» ничего не двигают: пока этап идёт, `done_count` `0`, оценка — с `begin`,
     а записи ложатся порциями по пять. У ритма и склейки записей нет вовсе.
  4. **Этап кончился** — `done`, `finished_at`, `eta_seconds` `0`, `done_count` равен `total_count`,
     `outcome` из снимка.

  Раскладка кадров (`montage_frames`) ложится между ритмом и склейкой. Времена — метки снимка;
  `begin` стоит в ту же секунду, с которой начинается первый этап, а середина склейки — на
  пропорциональной доле её отрезка. Тест **не умеет завести этап**: `start`, `progress`, `finish`
  только `UPDATE`-ят и падают, если строки нет, — поэтому «этап появился по ходу сборки» в записи
  попасть не может: в `live_first_open_empty` пять этапов в `pending`, и во всех опросах после — те
  же пять. Записи ложатся порциями по пять, опрос — `limit=4`, поэтому после порции видно
  `has_more: true`, а на следующем опросе — хвост. В первом опросе отсев
  стоит `running` с `done_count`, равным `total_count`: отсеянные файлы в снимках — последние по
  порядку съёмки, и счётчик доходит до конца раньше, чем воркер закрывает этап, — это не ошибка
  записи.

Шаги (в порядке записи):

| `name`                                                      | Что это                                                        |
|-------------------------------------------------------------|-----------------------------------------------------------------|
| `journal_of_old_ready_montage`, `journal_of_queued_montage` | ролик без журнала — `stages: []`, `entries: []`                  |
| `live_first_open_empty`                                     | экран открыли до первой записи, когда воркер уже завёл этапы: записей нет, курсор дальше — `0`, этапов пять и все `pending` с `eta_seconds` |
| `live_poll_1` … `live_poll_N`                               | опросы `after=<наибольший id прошлого ответа>`, `limit=4`; пока `has_more` — спрашивать сразу; в каждом ответе все пять этапов; ответ без записей — у этапа сменилось состояние или счётчик. Хвост после опроса, где `directing` стал `done`, — пять опросов без записей: ритм `running`, ритм `done`, склейка `running` (`0` из N, оценка с `begin`), склейка на середине (`done_count` — половина, оценка пересчитана), склейка `done` |
| `montage_list_while_building`                               | список роликов, пока сборка идёт: у собирающегося пять этапов со своими `state`, у ждущего и старого готового — `stages: null` |
| `live_viewer_opens_mid_build`                               | зритель открыл сборку посередине: первая загрузка без `after`, свежие сверху, `has_more: true`, в `viewers` рядом организатор |
| `journal_after_ready_nothing_new`                           | ролик собран, курсор тот же — записей нет, `viewers: []`         |
| `journal_of_ready_montage`                                  | готовый ролик — весь журнал за один запрос (`limit` по умолчанию 200) |
| `journal_of_one_file`                                       | тот же ролик, суженный до одного файла (`media_id`)              |
| `montage_list_after_ready`                                  | список роликов после сборки: у готового `stages: null`, `video_url` есть |
| `journal_of_stranger`                                       | посторонний: `404 {"error":"not found"}`                         |

Что тест проверяет за собой, а не только записывает: по курсору с малым `limit` ничего не потеряно,
не задвоено, порядок сохранён; этапов в каждом ответе живого сеанса ровно пять, а состояние каждого — то, что воркер оставил в базе на этот миг; после «готов» журнал совпадает со снимком запись в запись (по смыслу
полей, а не по id), этапы — с тем, что записал воркер; `files[].places` — раскладка снимка, у файла
вне раскладки пусто; читают организатор, участник и зритель, а посторонний, чужой ролик и чужое
воспоминание — `404`, без токена — `401`; упавший ролик (`failed` с упавшим этапом) повторяет только
организатор, после повтора журнал пуст, этапы в списке `null`, в очереди одна задача; удалён кадр —
записи о нём остались без сведений о файле, мест в раскладке у него нет; удалён ролик — журнала нет.

Ролик без журнала — собранный раньше, чем журнал появился, ещё стоящий в очереди или отказанный
раньше, чем воркер завёл этапы, — отвечает **пустым ответом, а не ошибкой**: `stages: []`,
`entries: []`, `files: []`. Взятый воркером отвечает пятью этапами в `pending` ещё до первой
записи. Журнал готового ролика читается так же, как идущий, сколько бы времени ни прошло; у
упавшего — то, что успело записаться.

### `POST /me/push-tokens`

За `app.authenticate`. Приложение отдаёт сюда свой Expo push token.

```
{"token": "ExponentPushToken[xxxxxxxxxxxxxxxxxxxxxx]", "platform": "ios"}
```

`platform` необязателен и принимает только `ios` или `android` — он для чтения таблицы глазами,
ветвлений по нему нет. Ответ — `200 {"ok":true}`.

Ключ таблицы — сам токен, поэтому повторная регистрация того же устройства идемпотентна, а
устройство, сменившее владельца, **переезжает** к новому: иначе телефон продолжал бы получать
уведомления о чужих воспоминаниях.

### Пуши

Типов в MVP два, и оба уходят одним и тем же путём — `fetch` прямо в Expo
(`src/memories/push.ts`), одним запросом на все устройства получателей (Expo берёт не больше 100
сообщений за раз и на 101-е отвечает `400` целой пачке, поэтому длинные рассылки режутся на сотни —
у приглашения адресат один, а у «ролик готов» это все участники):

- **«вас позвали в воспоминание»** (decision-06) — приглашённому, только при добавлении **по нику**
  и только когда человек действительно добавился;
- **«ролик готов»** (doc-03) — всем участникам воспоминания разом, по стуку воркера в
  `/internal/montages/:montageId/ready`. Не только заказавшему: ролик и есть награда за то, что
  люди скинули медиа.

```
«<кто позвал> приглашает вас в «<название>» — загрузите свои фото и видео»
“<кто позвал> invites you to “<название>” — add your photos and videos”
                                                        + data: {"memoryId": "…"}
«Ролик из «<название>» готов — посмотрите и поделитесь»
“The movie from “<название>” is ready — take a look and share it”
                                       + data: {"memoryId": "…", "montageId": "…"}
```

**Каждому на его языке.** Текст выбирается по `users.language` получателя, а не по языку того, кто
вызвал отправку: одно уведомление о ролике уходит сразу всем участникам, а гости одной свадьбы не
обязаны читать на одном языке. Поэтому обе строки пишутся до отправки, а язык подставляется на
каждое устройство отдельно — токены читаются джойном на `users`. На разбиение по сотне это не
влияет: в массиве Expo каждый элемент — целое сообщение со своим текстом, так что и русские,
и английские едут в одном запросе, а потолок остаётся один на устройство. `data` у всех одно и то
же — там идентификаторы, а не слова.

Обе строки написаны руками, как и письмо входа: английская — не перевод русской, а то же самое
по-английски. Готовый ролик по-английски — **movie**, и это не случайность: строка приглашения
просит у людей их `videos`, и то единственное, что продукт из них делает, обязано называться другим
словом — «ролик» в русской паре так же отличается от «видео». Название воспоминания остаётся на том
языке, на котором его написал автор.

**Формулировка без рода.** «добавил вас в» врало бы половине зовущих (в самом decision-06 пример —
«Аня добавила»), а «добавил(а)» читается как бланк. Настоящее время ни с кем не согласуется, поэтому
одна строка верна для любого организатора; менять её на прошедшее нельзя. Призыв загрузить медиа —
часть уведомления, а не украшение: ради него оно и шлётся (decision-06).

Зовущий подписывается своим `name`, а если его нет — ником; нет и его — «Кто-то» в русской строке
и «Someone» в английской. Заменитель имени выбирается там же, где и остальной текст: это слово
*внутри* строки, и на языке читателя должно быть оно, а не только всё вокруг него.
`data.memoryId` — это и есть deep link: приложение по нему открывает нужное воспоминание на экране
загрузки.

**Пуш не может уронить то, о чём сообщает.** Членство коммитится первым и отдельно, отправка идёт
после и целиком снаружи транзакции; у ролика то же самое — воркер стучится, уже записав `ready`.
Отправка глотает всё — нет токенов, нет сети, Expo ответил не 200, пуши выключены — и пишет строку
в лог. Человек оказывается участником, а ролик готовым, независимо от того, дошло уведомление или
нет.

Без `EXPO_PUSH_URL` (или без единого зарегистрированного устройства) в лог уходит `invite push not
sent` / `montage push not sent` с телом, которое **должно было** уйти, — на машине без пушей
разработчик видит ровно это. Первое слово в строке лога — это и есть тип уведомления.

⚠️ **Вживую не проверено.** Ни устройства, ни доступов к Expo в этом окружении нет: путь отправки
покрыт тестами (в том числе на мёртвый хост), но что уведомление реально долетает до телефона,
никто не видел. Первый прогон с реальным dev-билдом — за мобильным клиентом.

`ponytail:` повторов нет. Потерянный пуш потерян насовсем — членство при этом на месте, ролик тоже,
так что цена ровно одна: человек найдёт их сам при следующем заходе. Начнут теряться заметно — путь
переезжает на очередь `jobs`, у которой ретраи с backoff уже есть.

## Аутентификация

Своя, по модели данных из `architecture.md`. Сессия — непрозрачный случайный токен (32 байта из
`node:crypto`), в базе только его SHA-256. Транспорт — заголовок `Authorization: Bearer <токен>`:
клиент нативный, куки и CSRF не нужны. Провайдеров в MVP три — код на email, Apple и Google, —
и все три кончаются одним и тем же: строкой в `auth_identities` и сессией из `src/auth/session.ts`.

Аккаунты **не** сращиваются по совпадению email: первая встреча пары (провайдер, id у провайдера)
заводит нового пользователя. У Apple адрес бывает скрытым релеем — он меняется и может быть выдан
другому человеку, так что склейка по нему рано или поздно пустила бы одного в аккаунт другого.

Apple и Google проверяются через `jose` (`src/auth/providers.ts`): `createRemoteJWKSet` держит
ключи провайдера с их ротацией, `jwtVerify` сверяет подпись, `iss`, `aud` и `exp`. Руками из
токена берётся только `sub` — им и связывают, — плюс `name` и `email`, если они там есть.

### Как повесить проверку сессии

`app.authenticate` — готовый `preHandler`. Он сидит на корневом инстансе, поэтому доступен в любом
маршруте и импортировать нечего:

```ts
app.get("/memories", { preHandler: app.authenticate }, async (request) => {
  return listMemoriesOf(request.user.id);
});
```

Что он делает: читает `Authorization: Bearer <токен>` (схема регистронезависима), считает SHA-256,
ищет сессию без `revoked_at` и с непрошедшим `expires_at`. Нашёл — кладёт пользователя в
`request.user` и пускает дальше. Не нашёл — заголовка нет, схема другая, токен чужой, протухший
или отозванный — **сам** отвечает `401 {"error":"unauthorized"}`, и хендлер не вызывается.

`request.user` — ровно четыре поля и ничего больше:

| Поле       | Тип              | Что это                                        |
|------------|------------------|------------------------------------------------|
| `id`       | `string` (uuid)  | стабильная ссылка на человека — ссылайтесь на неё |
| `username` | `string \| null` | ник; `null`, пока человек его не занял         |
| `name`     | `string \| null` | имя                                            |
| `email`    | `string \| null` | адрес, с которым вошли                         |

Тип объявлен на `FastifyRequest` как всегда присутствующий — так удобнее в защищённом хендлере,
но заполняется он **только** за `app.authenticate`. На маршруте без этого `preHandler` там
`undefined`, и TypeScript об этом не предупредит.

### Как повесить проверку прав на воспоминание

Это раздел для m-1, m-2, m-5 и m-6: всё, что живёт под конкретным воспоминанием, вешает готовую
проверку `app.requireMembership` и ничего своего не пишет.

`app.requireMembership` — второй `preHandler`, тоже на корневом инстансе (`src/memories/plugin.ts`).
Он идёт **после** `app.authenticate` и без него не работает: ему нужен `request.user`.

```ts
app.post(
  "/memories/:memoryId/media",
  { preHandler: [app.authenticate, app.requireMembership] },
  async (request, reply) => {
    if (request.membership.role === "viewer") {
      return reply.code(403).send({ error: "forbidden" });
    }
    return upload(request.membership.memory, request.user.id);
  },
);
```

Параметр маршрута называется **`:memoryId`** — ровно так, проверка читает его по имени.

Что он делает: берёт `:memoryId`, ищет строку `memory_members` этого воспоминания на вызывающего.
Нашёл — кладёт в `request.membership` и пускает дальше:

| Поле                       | Тип                                          | Что это                        |
|----------------------------|----------------------------------------------|--------------------------------|
| `request.membership.role`  | `"organizer" \| "contributor" \| "viewer"`   | роль вызывающего в этом воспоминании |
| `request.membership.memory`| строка `memories` целиком                    | `id`, `organizer_id`, `title`, `event_start`, `event_end`, счётчики, `created_at`, `cover_media_id` |
| `request.membership.status`| `"not_started" \| "more_coming" \| "done" \| "nothing"` | статус вклада вызывающего — см. «Статус вклада» |

Воспоминание уже загружено — второй раз его доставать не нужно. `status` — тот, что был **до**
этого запроса: он читается в начале, и именно поэтому по нему видно, что текущая загрузка у
человека первая.

#### Матрица прав

Из `architecture.md` («Проверка прав»), это источник истины; здесь копия, чтобы не ходить:

| Роль          | Может                                                                |
|---------------|----------------------------------------------------------------------|
| не участник   | ничего                                                               |
| `viewer`      | смотреть галерею и ролики, **скачивать** оригиналы                   |
| `contributor` | + загружать медиа, ставить себе статус вклада, звать людей (поиском и ссылкой) |
| `organizer`   | + удалять любое медиа, исключать участников, **заказывать ролик**, менять название, даты и обложку |

Своё загруженное медиа может удалить каждый — это не роль, а владение: проверяется по тому, кто
загрузил, а не по `role`.

Проверка выдаёт роль и на этом останавливается: различать по ней — дело маршрута, у каждого своя
строка матрицы. Хелпера «не ниже роли X» нарочно нет — пока ни один маршрут его не просит,
а роль в `if` читается и так.

#### Домашнее правило: `404` один на всех

**Не участник, несуществующее воспоминание и кривой id получают побайтово одинаковый ответ:**

```
404 Not Found
{"error":"not found"}
```

Это правило наследуется, а не переизобретается: всякая фича, которая вешает эту проверку,
сохраняет такое поведение и **не** заводит своё «403, вы не участник» и своё «404, нет такого».
Разница между этими двумя ответами — это ответ на вопрос «а такое воспоминание вообще есть?»,
и по нему чужие воспоминания перебираются по id.

По той же причине сама проверка не отвечает `403`: `403` на маршруте — это уже про роль
(участник есть, но `viewer` не может загружать), и он законен только за пройденной проверкой.

Кривой id (не uuid) отсекается там же и тем же ответом: без этого он доехал бы до Postgres
ошибкой приведения типа и вернулся `500`.

### Как войти в разработке

Ключа Resend для этого не нужно, но нужны два условия: переменная `EMAIL_LOGIN_DEV_BYPASS=1`
в окружении API и адрес на домене `test.test`. Тогда код входа несёт сам ответ, никакого доступа
к машине сервера не требуется:

```bash
# в .env сервера (локально), либо EMAIL_LOGIN_DEV_BYPASS=1 npm run dev
EMAIL_LOGIN_DEV_BYPASS=1

curl -X POST http://localhost:3000/auth/email/start \
  -H 'content-type: application/json' -d '{"email":"you@test.test"}'
# {"ok":true,"code":"043117"}
```

Адрес любой, лишь бы на `test.test`: `you@test.test`, `kubik@test.test` — каждый заводит своего
пользователя, как настоящий. На `you@example.com` кода не будет: без ключей почты — `503
{"error":"mail not configured"}`, с ключами — настоящее письмо.

Не задана переменная — обхода нет ни для кого, что бы ни стояло в `NODE_ENV` и есть ли ключи почты.
`NODE_ENV=production` запрещает обход поверх всего: там `test.test` и включённая переменная не
значат ничего.

Дальше код либо вводится в приложении на экране входа, как его вводил бы человек из письма, либо
меняется на сессию руками:

```bash
curl -X POST http://localhost:3000/auth/email/verify \
  -H 'content-type: application/json' -d '{"email":"you@test.test","code":"043117"}'
# {"token":"42HDiF7t…","user":{…}}

curl http://localhost:3000/me -H "Authorization: Bearer 42HDiF7t…"
```

Ошибиться кодом можно `EMAIL_LOGIN_MAX_ATTEMPTS` раз (пять), после чего он мёртв и для верных цифр
тоже — нужен новый `POST /auth/email/start`. В разработке это ловится так же, как в бою, и это не
ошибка окружения.

### Ошибки

Свои отказы эндпоинты отдают как `{"error": "…"}`. Отказы, которые формирует сам Fastify
(валидация тела, неизвестный маршрут), приходят в его стандартной форме — `statusCode`, `code`,
`error`, `message`.

Всё, что упало на сервере, наружу уходит как `500 {"error":"internal"}`, а настоящая ошибка
пишется в лог: иначе отвалившаяся база отвечала бы постороннему своим SQLSTATE и текстом запроса.

### Отзыв сессий

`src/auth/session.ts`: `revoke(sessionId)` гасит одну сессию по id, `revokeByToken(token)` — ту,
которой сейчас пользуются (это и есть выход из аккаунта). Отзыв проставляет `revoked_at`, строка
остаётся; `app.authenticate` перестаёт её принимать сразу.

Наружу это выведено как `GET /auth/sessions`, `POST /auth/sessions/:id/revoke` и
`POST /auth/logout`. `revoke(sessionId)` про владельца ничего не знает — принадлежность сессии
проверяет маршрут, до вызова.

Свой токен можно достать из заголовка тем же способом, каким его читает проверка сессии:
`bearerToken(request.headers.authorization)` из того же модуля. Разбор заголовка живёт в одном
месте, чтобы «какая из этих сессий — текущая» и `app.authenticate` не разошлись.


`authPlugin` и `memoriesPlugin` вызываются из `buildApp` напрямую, а не через `app.register`:
Fastify инкапсулирует плагины, и `authenticate` или `requireMembership`, объявленный внутри
зарегистрированного, снаружи был бы не виден — а оба существуют ровно затем, чтобы их вешали
отовсюду.

Шага сборки нет: Node исполняет `.ts` напрямую, срезая типы. Значит, `enum`, `namespace` и
параметры-свойства конструктора не работают — `tsconfig.json` включает `erasableSyntaxOnly`,
так что `npm run typecheck` поймает это раньше рантайма.

Сервер слушает `0.0.0.0`, чтобы телефон или симулятор в той же сети мог до него достучаться.
